# Community-API (Cloudflare Worker + D1)

Login (Google/Microsoft), Kommentare, Abzeichen, Kurator pro Land, Web-Push und E-Mail-Digest für dub.m365.fm.
Läuft unter `https://api-dub.m365.fm`. Schlüssel (Session, VAPID, Cron) erzeugt der Workflow selbst.

## Einmalig einrichten (alles als GitHub-Secrets im Repo)
1. **Cloudflare**: Die Domain m365.fm muss im selben Cloudflare-Konto liegen. API-Token erstellen (Profil → API-Tokens → Vorlage „Edit Cloudflare Workers“, zusätzlich Rechte *D1: Edit* und *Zone → DNS: Edit* für m365.fm). Secrets: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` (Account-ID steht rechts im Dashboard).
2. **Google-Login**: console.cloud.google.com → APIs & Dienste → Anmeldedaten → OAuth-Client-ID (Webanwendung). Autorisierte Weiterleitungs-URI: `https://api-dub.m365.fm/auth/callback/google`. Secrets: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`.
3. **Microsoft-Login**: entra.microsoft.com → App-Registrierungen → Neu; Kontotypen „Konten in allen Organisationsverzeichnissen und persönliche Microsoft-Konten“; Web-Redirect-URI `https://api-dub.m365.fm/auth/callback/microsoft`; unter Zertifikate & Geheimnisse ein Client-Geheimnis (Wert!). Secrets: `MS_CLIENT_ID` (Anwendungs-ID), `MS_CLIENT_SECRET`.
4. **E-Mail (Cloudflare Email Service)**:
   - [x] Workers-Paid-Plan ist aktiv. Email Sending ist Beta; monatlich sind 3.000 E-Mails inklusive, danach 0,35 $ je 1.000.
   - [x] `m365.fm` ist unter **Email Service → Email Sending** als Absender-Domain eingerichtet. Cloudflare setzt SPF/DKIM-DNS-Einträge selbst.
   - [x] Der Worker nutzt das `EMAIL`-Binding; dafür ist kein API-Token nötig. `MAIL_FROM` steht in `wrangler.toml`. `RESEND_API_KEY` kann optional als Resend-Rückfall in GitHub-Secrets hinterlegt werden.
   - [ ] Nach dem Deploy als Admin `POST https://api-dub.m365.fm/api/admin/mail/test` mit der Admin-Session und `X-Requested-With: m365` aufrufen. Die Testmail geht an die bestätigte Benachrichtigungsadresse des angemeldeten Admins (max. 3 pro Stunde).
   - Nur falls später aus GitHub Actions per REST versendet wird, einen Token mit *Email Sending: Edit* als GitHub-Secret hinterlegen, nie im Code oder Chat.
5. **LinkedIn-Login**: developer.linkedin.com → Create app (LinkedIn-Seite des Unternehmens verknüpfen) → Reiter Products → „Sign In with LinkedIn using OpenID Connect“ anfordern → Reiter Auth: Authorized redirect URL `https://api-dub.m365.fm/auth/callback/linkedin`. Secrets: `LINKEDIN_CLIENT_ID`, `LINKEDIN_CLIENT_SECRET` (Client ID und Primary Client Secret).
6. Optional `ADMIN_SUBS` = `google:<sub>`, `microsoft:<sub>`, `linkedin:<sub>` oder `github:<id>` (Moderator; die ID siehst du in D1 in der Tabelle users; bei GitHub die numerische Konto-ID, nie der Login-Name).
7. **GitHub-Login**: github.com → Settings → Developer settings → OAuth Apps → New OAuth App. Application name `M365.FM`, Homepage URL `https://www.m365.fm`, Authorization callback URL `https://api-dub.m365.fm/auth/callback/github`. Client ID kopieren, Client Secret erzeugen und beides als Repo-Secrets `GH_OAUTH_CLIENT_ID` und `GH_OAUTH_CLIENT_SECRET` anlegen (GitHub-Secrets duerfen nicht mit `GITHUB_` beginnen). Danach den Workflow „Community-API … einrichten“ neu starten; der Knopf „Weiter mit GitHub“ erscheint automatisch (`/api/providers`). Scope `read:user`, Nutzer `github:<numerische ID>`.
8. **Community-Agent** (`agents/`, Workflow „Community-Agent prüfen und veröffentlichen“): Das Signier-Secret `SESSION_SIGNING_SECRET` erzeugt der erste Deploy selbst und behält es danach. Optional kann es als GitHub-Secret `AGENT_SESSION_SIGNING_SECRET` (≥ 32 zufällige Zeichen) vorgegeben werden; nach einem Wechsel müssen Clients neu verbinden.
7. Workflow **„Community-API … einrichten“** starten (Actions → Run workflow). Er legt die D1-Datenbank `m365-dub` an, sichert sie (`backup-d1.sql`, als Artefakt 14 Tage nur verschlüsselt mit dem Secret `D1_BACKUP_KEY`, ohne Secret kein Artefakt; das Repo ist öffentlich), wendet die Migrationen aus `migrations/` an (`wrangler d1 migrations apply`, Stand in Tabelle `d1_migrations`), setzt Secrets, veröffentlicht den Worker.

## Claude und AI Gateway

- [ ] In Cloudflare unter **AI → AI Gateway** das Gateway `m365fm` anlegen. `AI_GATEWAY_ID` ist eine GitHub-Variable (Standard `m365fm`) und wird beim Worker-Deploy übernommen; ohne Gateway-Konfiguration bleibt der direkte Anthropic-Aufruf als Rückfall aktiv.
- [ ] `CRON_KEY` als GitHub-Secret setzen und den Worker-Deploy erneut ausführen, damit derselbe Wert im Worker und in Actions liegt. Actions verwenden ihn für Budgetabfrage und Verbrauchsmeldung; ohne ihn werden Haiku-Läufe in Actions sicherheitshalber übersprungen.
- [ ] **Authenticated Gateway** aktivieren und den Gateway-Token als GitHub-Secret `CF_AIG_TOKEN` hinterlegen. Worker-Deploy und Actions übernehmen das Secret; ohne Token wird direkt Anthropic verwendet.
- [ ] Falls Cloudflare AI Gateway Ausgabenlimits anbietet, dort zusätzlich ein Limit als zweite Schutzschicht setzen.

Das Haiku-Budget beträgt standardmäßig 5 € je UTC-Tag. Preise und Wechselkurs stehen als Worker-Variablen `HAIKU_USD_PER_MTOK_IN`, `HAIKU_USD_PER_MTOK_OUT`, `AI_DAILY_EUR_HAIKU` und `USD_PER_EUR` in `wrangler.toml`; für Actions können die entsprechenden Haiku-Preis- und Kurswerte als GitHub-Variablen gesetzt werden. Der Verbrauch erscheint im Admin-Bereich unter **Schalter**.

## Verzeichnis-Karte (optional)
- Google Cloud: Maps JavaScript API und Geocoding API aktivieren. Den Browser-Schlüssel per HTTP-Referrer auf `https://m365.fm/*` und `https://*.m365.fm/*` beschränken und ein Tageskontingent setzen. Als Worker-Variable `GOOGLE_MAPS_API_KEY` hinterlegen; sie wird erst nach Klick auf „Karte laden“ ausgeliefert.
- Den serverseitigen Geocoding-Schlüssel als Worker-Secret `GOOGLE_GEOCODING_KEY` hinterlegen. Er wird nur beim Speichern oder beim auf 50 Einträge pro Lauf begrenzten Geocode-Backfill verwendet und nie an den Browser ausgegeben.

Ohne Zugangsdaten tut der Workflow nichts; die Website blendet die Community-Bereiche automatisch aus, solange die API nicht erreichbar ist.

## Betrieb
- Täglicher Digest: Cron `0 6 * * *` (UTC). Der erste Lauf markiert vorhandene Folgen nur als bekannt (kein Massenversand).
- Manuell testen: `curl -H "x-cron-key: <CRON_KEY>" "https://api-dub.m365.fm/api/admin/run-daily?dry=1"` (`dry=1` sendet nichts). Den Schlüssel nicht als `?key=` in die Adresse schreiben, Adressen landen in den Worker-Logs. CRON_KEY wird nur in GitHub gepflegt; der Worker-Deploy überträgt ihn in den Worker (ein nur in Cloudflare geänderter Wert wird beim nächsten Deploy überschrieben). Ob beide gleich sind, zeigt der Workflow „Secrets prüfen“.
- D1-Sicherung zurückholen: Artefakt `d1-backup-<Lauf>` laden, dann `openssl enc -d -aes-256-cbc -pbkdf2 -iter 600000 -in backup-d1.sql.enc -out backup-d1.sql -pass env:D1_BACKUP_KEY` (Schlüssel aus dem Passwort-Manager). Ohne Artefakt: Cloudflare → D1 → m365-dub → Time Travel (30 Tage).
- Tarif: Workers Paid ($5/Monat) seit 10/2026: 1.000 Subrequests und 30 s CPU je Aufruf; D1 im Paid-Plan (Profil-Export und Import-Batches brauchen das).
- Schema: `migrations/0001_baseline.sql` ist der Ausgangsstand; jede Aenderung ist eine neue Datei `migrations/000N_name.sql` (nur idempotente Anweisungen; neue Spalten in bestehenden Tabellen weiterhin per ensure*-Funktion, SQLite kennt kein ADD COLUMN IF NOT EXISTS). Vor jedem Deploy laufen `node --check`, `npm test` und die MCP-Abdeckung; rot heisst kein Deploy.
- Lokal: `cd worker && npm i && npx wrangler dev` (mit `.dev.vars`: `SESSION_SECRET`, `DEV_LOGIN=1`).

## Event-Import (Community Days, Sessionize)
- Lauf: `runEventImport` (`src/eventimport.js`) im `*/15`-Cron zur Minute 15 und 45, nie im Aufruf der Digests, und dort erst nach den Themen-Benachrichtigungen. Jeder Lauf ist hart gedeckelt (`CAP`: 12 Abrufe, 12 Community-Days-Events, 3 Sessionize-Events, 100 Sessions) und schreibt gebündelt (`db.batch`); gemessen rund 20 bis 110 D1-Aufrufe je Lauf. Was nicht hineinpasst, folgt im nächsten Lauf (`meta communitydays_state`, `events.sessionize_state='partial'`, Inhalts-Hash je Session in `session_source.hash`).
- Zeilen in `events` erkennen: importiert `source<>''` (`communitydays` | `sessionize`), ohne Veranstalter `unclaimed=1` (dann `owner_id=0`), vergangen `retired=1` (bleibt `public=1`), zusammengeführt `merged_into<>0` (ID des verbleibenden Events, `public=0`), von Hand gepflegt `edited_at>0` oder `owner_id<>0`/`org_id` gesetzt. Unbekannt bei Import-Events: `free=-1` (Export `free: null`) und `tz=''` (keine Session-Erinnerungen). Wer Events auswählt (z. B. für andere Kanäle), filtert mit `merged_into=0 AND unclaimed=0 AND retired=0`.
- Zusammenführen: automatisch nur bei starker Identität (eigene Quelle bzw. eigene Adresse des Events ohne Datums- oder Namenswiderspruch, oder gleicher Name + gleicher Tag + gleiche Stadt); jede Zusammenführung steht in `merge_log` und lässt sich im Admin-Bereich zurücknehmen, „getrennt lassen“ (`dedupe_queue.status='separate'`) gilt dauerhaft. Tabellen, die an einem Event hängen, stehen an einer Stelle: `EVENT_TABLES` in `src/eventmerge.js` (Zusammenführen, Zurücknehmen und Löschen nutzen sie; ein Test meldet jede Tabelle mit `event_id`, die dort fehlt).
- Wiedererkennen: Ein Datensatz einer Quelle wird an seiner eigenen Geschichte erkannt, nicht am heutigen Namen oder Termin des Events hier: `event_source` hält an der Zeile des Datensatzes (dem Event, das aus ihm entstand, oder seiner ausgeblendeten Zeile) Kennung, Name, Tag und Inhalts-Hash, wie ihn die Quelle zuletzt lieferte. Ausgeblendete Zeilen zählen bei der Suche für das Event, in dem sie aufgegangen sind. Ein vom Veranstalter umbenanntes, ein (auch von einem Admin) zusammengeführtes oder ein in der Quelle verlegtes Event wird deshalb aufgefrischt und nie neu angelegt. Ob eine Kennung in der Quelle genau einen Datensatz bezeichnet, sagt der Importer (`sole`, Community Days liest dafür die ganze Liste): nur dann gilt „neuer Termin“ (höchstens 180 Tage, alter Termin noch nicht vorbei) oder „neuer Name am selben Tag“ als derselbe Datensatz; teilen sich mehrere Einträge eine Adresse, ist sie nur ein Hinweis für die Admins.
- Änderungen der Quelle: Für ein Import-Event, das niemand pflegt, ist genau eine Quelle maßgeblich: der Datensatz der Veranstaltungsliste (Community Days, `LEAD_KIND`), auch wenn er erst später dazukam; sonst der Datensatz, aus dem das Event entstand. Ändert ihn die Quelle (Hash), folgen Titel, Termin, Ort, Texte und Links; die Adresse (`handle`) bleibt, Koordinaten werden neu geholt. Fehlt in der Quelle nur eine Angabe, löscht das nichts. Datensätze anderer Quellen ergänzen nur, gepflegte Events (`protectedEvent`) ändert kein Import. Was ein Event nachträglich von einem zusammengeführten Datensatz übernimmt, steht im Protokoll dieser Zusammenführung und geht beim Zurücknehmen mit zurück.
- Ohne Veranstalter (`unclaimed=1`) gibt es keine Anmeldung und keinen Session-Vorschlag über M365.FM (Seite, Routen und MCP lehnen ab, `error: unclaimed`); nach dem Übernehmen geht beides. Zusammengeführte Zeilen sind über keine Adress-Route erreichbar; Zeilen, die der Import gleich beim Anlegen zusammenführt, tragen eine technische Adresse (`~…`) und belegen keine echte.
- Eigentum: Was ein Mitglied, ein Veranstalter oder ein Admin eingetragen oder geändert hat, überschreibt kein Import (`protectedEvent`, `event_sessions.edited_fields`). Gelöschte Import-Events und vom Veranstalter gelöschte Sessions hinterlassen eine Löschmarke (`event_tombstone`, ohne Personenbezug) und kommen nicht zurück; Sessions kehren nach „Verbindung lösen“ und erneutem Verknüpfen zurück.
- Datensparsamkeit: von Speakern nur Name und Sessionize-Kennung (`speaker_ref`); keine Kurzvorstellungen, Fotos, Slogans oder Link-Listen, nichts wird in den Bucket kopiert. Das gilt auch für den Abruf-Cache (`import_cache`, höchstens zwei Tage): Sessionize-Antworten werden vor dem Speichern auf das Verwendete gekürzt (`slimAllView`), Profilseiten von Speakern gar nicht gespeichert. Löscht ein Mitglied sein Konto, verschwinden auch seine Speaker-Identität (sobald keine Session mehr auf sie verweist) und sein Eintrag in den Ständen des Protokolls (`merge_log.snapshot`). Ein Mitgliedsprofil wird an einer Speaker-Identität nur gemerkt, wenn die Sessionize-Seite selbst auf das M365.FM-Profil verlinkt.

## Community-Wiki und Editoren
- Auf den Glossar-Begriffsseiten (de/en) gibt es unter der Kurzinfo ein Community-Wiki (Tabelle `wiki_rev`). Beitraege sind reiner Text (keine Links), je Nutzer ein offener Vorschlag, Limit 6/Stunde.
- Neue Mitglieder: Beitrag wartet auf Pruefung. Sofort live: Admin, Editoren und Mitglieder ab 25 Punkten. 3 Meldungen blenden eine Fassung aus (die vorherige kommt zurueck).
- Editor ernennen: auf der Community-Seite (als Admin angemeldet) im Bereich **Team** nach dem Namen suchen und „Zum Editor machen“. Editoren pruefen Beitraege direkt unter dem jeweiligen Begriff; sie erhalten das Abzeichen ✏️ Editor. Wer einen veroeffentlichten Beitrag hat, bekommt 📖 Wiki-Autor.
- Freigegebene Texte exportiert `GET /api/wiki/export?lang=de`; der Seitenbau uebernimmt sie statisch (indexierbar).

## Contribution Collector
- Quellen und Beiträge verwaltest du mit `add_contribution_source`, `update_contribution_source`, `delete_contribution_source`, `add_contribution`, `update_contribution`, `delete_contribution`, `list_my_contributions` und `export_contributions` über MCP (persönlicher KI-Token). Quellen sind standardmäßig privat; RSS/Atom-Feeds werden alle 30 Minuten geprüft und es werden nur Metadaten wie Titel, Link, Datum und Themen übernommen.
- Der Export liefert CSV und eine Kopiervorlage; `from` und `to` filtern inklusive Datumsgrenzen. Die öffentliche Profilansicht folgt in einem separaten Ticket.
- YouTube-Aufrufe benötigen die bereits konfigurierte YouTube-Verbindung (`YT_REFRESH_TOKEN`). Spreaker-Downloads werden bei eigenen veröffentlichten Folgen und bestätigten Gastauftritten erfasst, wenn `SPREAKER_TOKEN` gesetzt ist.
