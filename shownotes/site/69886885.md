## Key takeaways

- Power Automate should be governed as an automation control plane, because the platform enforces configuration, not intent.
- Separate probabilistic decisions from deterministic execution: keep orchestration thin and put every side effect into idempotent child flows with receipts and bounded retries.
- Measure explainability and ownership, such as mean time to explain, ownership coverage and API budget adherence, instead of counting flows and runs.

## FAQ

**What is a Christmas tree flow in Power Automate?**

A Christmas tree flow is one mega flow that keeps absorbing exceptions as nested conditions, switches, loops and scopes. Decision logic and side effects get mixed, the flow ends in multiple places and behavior can no longer be enumerated. The result is unreliable testing, rising change failure rates and a mean time to explain that grows from minutes to days.

**Why should Power Automate side effects run in child flows?**

Child flows give you a deterministic execution boundary where each side effect happens once with proof. Treated as execution units, they take a transaction identity, enforce idempotency and bounded retries, and return receipts like record IDs or ticket numbers. That allows reuse without duplicated actions, real testing of single units and governance rules applied where authority turns into action.

**Which KPIs should be used to govern a Power Automate estate?**

Measure explainability and ownership instead of counting flows or runs. The episode recommends mean time to explain as the primary metric, plus ownership coverage, the share of side effects inside execution units, retry rate versus failure rate, API budget adherence and explainability coverage, meaning how many production automations stamp a correlation ID and emit receipts.
