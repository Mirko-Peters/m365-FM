## Key takeaways

- Excel is a great tool for analysis and prototyping, but without schema, transactions, audit and role-based security it fails as the data backbone of a multi-user Power App.
- Dataverse enforces data types, relationships, business rules, security roles and auditing at the platform level, so data quality no longer depends on careful humans.
- Migrate in phases (inventory, model, import pipeline, security, validation, freeze and cutover with rollback criteria) and keep analytics in Fabric while Dataverse governs operations.

## FAQ

**Why is Excel a poor data source for a multi-user Power App?**

Excel lacks schema enforcement, transactions, auditing and role-based security. When two people edit the same row, the last save wins and the other change disappears without warning. Columns change type on paste, nothing forces valid relationships, and version history is no field-level change record, so a connected Power App serves stale or overwritten data.

**When should I use Microsoft Fabric or SQL instead of Dataverse?**

Use Dataverse for operational work such as CRUD, workflows and approvals, Microsoft Fabric and the lakehouse for analytics across millions of rows and historical snapshots, and SQL Server or Azure SQL for specialized transactional workloads or immovable legacy schemas. The episode recommends landing curated exports in OneLake rather than running giant reports against Dataverse.

**How do you cut over from Excel to Dataverse without losing data?**

Run a phased cutover with predefined rollback criteria. Deploy the schema through solutions, preload historical data while the Excel app still runs, then freeze Excel as read-only, delta-load recent changes and switch the app's data source. Dual-run for a defined period and declare success or roll back based on reconciliation, error rates and user sign-off.
