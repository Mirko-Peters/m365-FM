## Key takeaways

- Modern Microsoft 365 breaches bypass MFA by combining consent phishing with adversary-in-the-middle token theft rather than breaking passwords.
- OAuth app consent and refresh tokens survive password resets, so remediation must revoke grants, remove service principals, invalidate tokens and remove malicious inbox rules.
- Disabling user consent, enforcing the admin consent workflow, turning on token protection and risk-based Conditional Access, plus Sentinel playbooks on consent, forwarding and download events break the chain.

## FAQ

**Why doesn't MFA stop Microsoft 365 account takeover?**

Because adversary-in-the-middle phishing kits capture the session cookie after MFA has already completed. The reverse proxy relays the sign-in to Microsoft, the user satisfies MFA, and the attacker replays the stolen cookie from another device. Sign-in logs then show authentication requirements satisfied, often from a new country minutes later.

**Does a password reset remove an attacker who used OAuth consent phishing?**

No. App consent and refresh tokens survive a password reset, so the attacker keeps access through the malicious app. The episode's remediation is to revoke the consent and remove the service principal, invalidate refresh tokens and force sign-out, rotate secrets of affected sanctioned apps, and delete malicious inbox rules.

**Which logs show a Microsoft 365 consent phishing attack?**

Entra ID audit logs show consent to application, service principal created and app role assignment events. Sign-in logs reveal cookie replay from a new device or country, Exchange mailbox audit shows new inbox rules and forwarding, and the unified audit log shows file downloads stamped with the app ID instead of Outlook or a browser.
