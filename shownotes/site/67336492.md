## Key takeaways

- Apps that work in a permissive dev tenant often fail in production because enterprise consent policies restrict which Graph permissions users can grant.
- Delegated permissions act within a signed-in user's rights, while application permissions let an app act on its own across the organization and therefore require admin consent.
- Requesting only the narrowest scopes, piloting with trusted users and preparing admin approval early keeps Graph-based rollouts on track.

## FAQ

**What is the difference between delegated and application permissions in Microsoft Graph?**

Delegated permissions act on behalf of a signed-in user and can only reach what that user can already access. Application permissions let the app call Graph as itself, without a user, often across the whole organization. That far broader reach is why application permissions are treated as high risk and need admin consent.

**Why does my Microsoft Graph app work in dev but require admin approval in production?**

Your dev tenant is permissive and you are usually its admin, so every consent screen passes. Production tenants restrict which permissions users may grant, and broad scopes that reach beyond the signed-in user always need an admin. Tenant consent policies, security defaults or Conditional Access can block even low-risk requests.

**How can I get Microsoft Graph permissions approved faster?**

Request only the narrowest scopes your app actually uses, such as read instead of write and single-user instead of tenant-wide access. Plan admin consent before coding, explain why each permission is needed, pilot with trusted users and request additional scopes incrementally as features need them. Lean permission lists pass security reviews faster.
