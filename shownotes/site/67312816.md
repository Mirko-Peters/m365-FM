- App-only permissions give an application its own identity in [Microsoft Graph](https://www.m365.fm/entity/graph/?utm_source=podcast&utm_medium=shownotes&utm_campaign=using-microsoft-graph-for-custom-app-integrations-why-delegated-permissions-break-automation-and-how-app-only-access-fixes-it), enabling least-privilege access, unattended runs and cleaner audit trails.
- A reliable setup requires registering the app, choosing only the needed application permissions, confirming admin consent and storing and rotating secrets securely.

## FAQ

**Why do Power Automate flows using delegated permissions suddenly fail?**

They fail because delegated permissions tie every API call to a real user's session and credentials. When that person logs out, resets a password, loses a license or leaves the company, the automation stops, sometimes with an authentication error and sometimes silently, until someone notices missing reports or failed jobs the next morning.

**What is the difference between delegated and application permissions in Microsoft Graph?**

Delegated permissions assume a signed-in user and inherit what that person can do, while application permissions let the app act as its own identity with no user present. For background services and scheduled jobs, application permissions are the right choice, combined with least privilege so the app only gets access it actually needs.

**Why does my app still get insufficient privileges after adding Graph permissions?**

Usually admin consent was never finalized, even if the portal looks ready. Application permissions only take effect after an administrator grants organization-level consent, which can involve approvals depending on tenant policy. Check the granted permissions under enterprise apps, and verify the chosen permission actually matches the SharePoint resource the app is calling.
