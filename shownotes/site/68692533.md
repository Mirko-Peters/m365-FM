This episode walks architects and governance teams through three real failure cases and the fixes that hold: per-agent identities, an RBAC model, output DLP and a red teaming checklist.

## Key takeaways

- Defend against prompt injection in code with tool allow lists, enforced JSON schema outputs, secret filters and fail-closed handling rather than relying on system prompts.
- Give every agent its own service principal with scoped, time-bound roles and environment-separated connectors instead of shared credentials or tenant-wide scopes.

## FAQ

**How do you protect a LangChain4j agent against prompt injection?**

Put the guardrails in code instead of trusting the system prompt. Register tools in an allow list with schemas, require JSON schema outputs and reject anything that does not validate, check tool argument types and ranges before execution, filter outputs for secrets, and fail closed with explicit exceptions rather than retrying poisoned input.

**Should every AI agent have its own service principal?**

Yes, each agent should get a dedicated service principal, even when two agents call the same API. Shared credentials mean a shared blast radius. Tag each identity with owner, purpose, environment and expiration, grant the smallest OAuth scopes the tool needs, and keep development credentials away from production endpoints so misconfigured calls fail closed.

**What belongs in a red teaming checklist for AI agents?**

A repeatable checklist covers injection, access and audit tests. Try role confusion, fake tool names, schema bypass and data exfiltration prompts; request actions outside the agent's role and rotate secrets mid-session; then confirm one correlation ID reconstructs prompt to action. Missing schemas or tenant-wide scopes should automatically block the release.
