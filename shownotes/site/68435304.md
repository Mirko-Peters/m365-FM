## Key takeaways

- Applied Steps in [Power Query](https://www.m365.fm/entity/power-query/?utm_source=podcast&utm_medium=shownotes&utm_campaign=power-bi-query-folding-order-of-operations) describe a logical order, while the engine builds a dependency tree and executes an optimized physical plan that can defer, reorder or skip steps.
- Query folding pushes transformations back to the source; one non-foldable step such as a custom function or index column makes every downstream step run locally and can turn seconds into minutes.
- Keep queries foldable by checking View Native Query and query diagnostics, separate source, staging and load queries, avoid uncontrolled query references, and move heavy logic into SQL views or [Fabric](https://www.m365.fm/entity/fabric/?utm_source=podcast&utm_medium=shownotes&utm_campaign=power-bi-query-folding-order-of-operations).

## FAQ

**Does Power Query run Applied Steps in the order they are listed?**

No. Applied Steps are a logical description, not a procedural recipe. Power Query builds a dependency tree, defines each step without running it, and executes an optimized plan when data is requested. Steps without direct dependencies can move, an early filter may apply late, and unreferenced steps may never execute at all.

**Why does one step make my Power BI refresh so much slower?**

Usually because that step broke query folding. Once a step cannot be translated for the source, such as a custom function, text manipulation or index column, every later step runs locally. Power BI then pulls far more rows across the network and processes them in memory instead of letting the database filter first.

**How can I check whether my Power Query steps still fold?**

Right-click a step and choose View Native Query; if the option is grayed out, folding has stopped. Query diagnostics show which steps ran at the source and which were engine-only. The episode suggests a diagnostic query that mirrors your transformation chain and testing each new step before trusting production volumes.
