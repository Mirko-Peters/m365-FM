## Key takeaways

- DAX should only express analytics; any logic that changes who can see or infer data belongs to identity in Microsoft Entra, not to measures.
- Business definitions, keys and cross-boundary benchmarks must live upstream with Purview labels and DLP that can actually block exports, blends and notebook writes.

## FAQ

**Why can DAX measures leak data even when row-level security works?**

Because RLS only constrains base tables, while measures can rewrite filter context afterwards. Functions such as CALCULATE with ALL or REMOVEFILTERS can compute against unscoped totals, so a user limited to one region may infer restricted numbers by subtraction or variance. The episode treats any measure that changes visibility as illegal in the semantic layer.

**Why are calculated tables in a Fabric semantic model a governance risk?**

They create business definitions inside the model that upstream governance cannot see, label or retire. Sensitivity labels from Microsoft Purview do not propagate into such derived tables the way teams assume, and copies spread through shared datasets. The episode recommends keeping definitions upstream in the warehouse and blocking prohibited calculated artifacts at publication.

**How should Fabric capacity be used for data governance?**

Capacity should be treated as a containment boundary, not a performance setting. The episode argues for separating capacities by risk domain, for example keeping finance, HR or clinical analytics apart from marketing and vendor sandboxes, so a misbehaving workload or incident can be stopped locally without pausing refreshes and exports for unrelated teams.
