Many .NET teams use Entity Framework as a table-to-class generator, then blame EF when their code turns into scattered services and duplicated rules. This episode shows developers how to spot the DTO factory pattern, when a micro-ORM really makes sense and how to model real domain logic with EF Core. The payoff is simpler tests, less duplication and clearer code.

## Key takeaways

- Scaffolding tables into hollow DTO-style entities scatters business logic across services and makes EF feel bloated.
- Micro-ORMs suit narrow read-heavy endpoints, but in complex domains you end up rebuilding change tracking, relationships and concurrency that EF already provides.
- Put behavior into entities and use navigation properties, owned types and the fluent API to keep persistence details out of the domain model.

## FAQ

**When should I use a micro-ORM instead of Entity Framework Core?**

Use a micro-ORM for narrow, read-heavy endpoints where you want fine-grained control of the SQL. In complex domains it is a costly default, because you end up hand-writing change tracking, relationship management, mapping conventions and concurrency handling that EF Core already provides, and those maintenance costs surface as the system evolves.

**How do I know my EF Core entities have turned into a DTO factory?**

Check whether your entities have any methods beyond property getters; if they do not, that is a red flag. Other symptoms are business rules living in services or controllers, the same logic reimplemented in several places, and debugging that requires hopping across multiple files to trace how a single feature really works.

**Which EF Core features keep persistence details out of a rich domain model?**

Navigation properties, owned types and the fluent API do most of the work. Navigation properties handle relationships, owned types wrap concepts such as an address or email into value objects, and fluent API configuration defines database rules like decimal precision outside the entity, so the domain classes can focus on business behavior.
