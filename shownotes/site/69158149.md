- Conditional access and [Purview](https://www.m365.fm/entity/purview/?utm_source=podcast&utm_medium=shownotes&utm_campaign=the-embodied-lie-ai-speaking-agent-entropy) operate at token time and after execution, so they cannot stop an entitled agent from doing the wrong thing at action time.
- Put a deterministic per-tool-call policy gate in front of every side effect, evaluating actor, intent, scope, data class and venue before execution.
- Use idempotency keys with an authoritative state store and split agent identities into read, write and egress lanes to keep failures small.

## FAQ

**Why isn't Conditional Access enough to control AI agents in Microsoft 365?**

Conditional Access decides whether an identity gets a token, not whether a specific delete, share or send is appropriate. Once the token exists, the agent acts inside the workload without another check. The episode argues for a second gate: a per-tool-call policy engine that evaluates every proposed action before it executes.

**What is a per-tool-call policy gate for AI agents?**

It is a deterministic decision point that runs before any side effect. The agent submits a structured request with actor, intent, scope, data class, venue and operation ID, and the policy engine returns allow, deny or transform. Tools only execute with a matching decision artifact, which is stored next to the action as proof.

**Why do retries make agents repeat actions, and how does idempotency help?**

Event-driven systems deliver at least once, so a retry after a lost success response can send an email twice or repeat a deletion. Idempotency fixes this by giving each side-effecting operation an immutable operation ID, persisted in an authoritative state store before execution, so replays return the recorded outcome instead of acting again.
