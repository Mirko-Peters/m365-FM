## Key takeaways

- OAuth consent grants give apps tokens that keep refreshing, so MFA and password resets do not cut off a malicious app; only revoking the grant does.
- Lock down user consent to low-risk scopes, allow it only for verified publishers and route every risky request through the admin consent workflow.
- Hunt for new grants, risky scopes such as offline access with mail or files permissions, and added app credentials in audit logs and via [Microsoft Graph](https://www.m365.fm/entity/graph/?utm_source=podcast&utm_medium=shownotes&utm_campaign=entra-id-oauth-consent-attack-explained), then revoke and verify.

## FAQ

**Why doesn't MFA stop an illicit OAuth consent grant?**

MFA only protects authentication, and a consent grant is an authorization decision. After the user approves the app once, it receives tokens and keeps exchanging refresh tokens for new access tokens. The attacker never signs in as the user, so no MFA prompt ever appears while the app reads mail or files.

**Does a password reset remove a malicious app's access?**

No, password resets, new MFA registrations and forced sign-outs do not revoke OAuth grants. The app keeps calling Microsoft Graph until you remove its permissions in Enterprise applications or delete the OAuth2 permission grant. Then remove its secrets and certificates and confirm the same token now fails with an access error.

**Which Entra settings reduce the risk of consent phishing?**

Restrict user consent to low-risk scopes or turn it off, allow it only for apps from verified publishers, and enable the admin consent workflow with approvers, justification and expiration. Exclude offline access and broad mail, files or directory scopes from user consent, and route every risky request through admin review.
