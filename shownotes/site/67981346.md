Slow R pipelines on SQL Server are usually caused by setup, not algorithms. This episode helps data scientists and SQL professionals fix compute context, batch size, query shape, transformations and factor handling so R-SQL workloads run fast and stay stable.

## Key takeaways

- Use the SQL Server compute context for large data so R runs next to the data instead of pulling every row across the network.
- Tune the batch size step by step while watching memory, and write lean, well-shaped queries so the optimizer can build parallel plans.
- Do transformations in T-SQL views or staging tables before the model loop, and define factor levels up front with colInfo for speed and stable models.

## FAQ

**Why is my R script slow when reading data from SQL Server?**

Most often because it runs in a local compute context, pulling every row across the network into your machine's memory. Switching to the SQL Server compute context runs the R script on the server next to the data. If it is still slow, check query shape next, then the batch size set by rowsPerRead.

**What is a good rowsPerRead value for RevoScaleR on SQL Server?**

There is no single right value, so test in steps. The episode suggests starting at the default of 50,000, then trying 500,000 and, with enough memory, one million while watching runtime and RAM. If memory starts paging, roll back one step. Wide tables or large text and blob columns need smaller values.

**How do I get SQL Server to run R queries in parallel?**

Give the optimizer a lean, well-shaped SQL query instead of just pointing the RevoScaleR data source at a table, and select only needed columns. Check the execution plan in Management Studio for parallel streams. For custom external scripts, enable the parallel option; for rx functions, set numTasks, though server limits decide how many tasks actually run.
