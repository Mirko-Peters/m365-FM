## Key takeaways

- A single generalist copilot running every request on a premium model creates cost, quality and governance debt; a governed fabric of bounded experts fits enterprise work better.
- Make a cheap, structured router the first expert, use small models for routine traffic and escalate to premium reasoning or human review only on clear confidence, ambiguity and risk triggers.
- Let Copilot Studio own the user experience and Foundry own model control, and govern the fabric with Agent 365, Azure Policy model allow lists, traces and named owners.

## FAQ

**What is a system-level mixture of experts in Microsoft Copilot architectures?**

It is an architecture where the application chooses among specialized models, agents, tools and workflows based on the job, instead of one model handling everything. Unlike model-level mixture of experts inside a model, these experts are explicit, so you define each one's purpose, data, owner and stop boundary as a governance decision.

**Should Copilot Studio or Azure AI Foundry host the logic of a copilot?**

Both, with a clear split: Copilot Studio is the face, handling conversation, channels and orchestration at the surface, while Foundry is the brain for model selection, routing, prompt flow logic and evaluation. Putting deep reasoning into the Studio layer hides complexity in the wrong place and makes models harder to test and swap.

**When should a routed copilot escalate to a premium model or a human?**

Escalate on clearly defined triggers that combine low confidence, ambiguity and business risk, not confidence alone. Routine requests stay on cheap paths, harder ones move to a larger model, and actions that change records, move money or commit something externally pause for human review. Escalations should pass along structured evidence and attempted paths.
