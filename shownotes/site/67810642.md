Your LINQ query works perfectly in C#, but the SQL it generates looks like a monster and performance collapses in production. This episode is for .NET developers working with Entity Framework Core. You learn how expression trees, the query provider, caching, null semantics and materialization shape every query, and what to check before it hurts.

## Key takeaways

- EF Core does not execute your LINQ directly; it captures it as an expression tree that the query provider checks against known SQL translation patterns.
- Untranslatable parts can trigger errors or client-side evaluation, so test queries against realistic data volumes and inspect the generated SQL.
- Query caching speeds up repeated query shapes but costs memory when many unique shapes are generated, and null-handling rewrites explain much of EF Core's longer SQL.

## FAQ

**Why does EF Core generate such complicated SQL from a simple LINQ query?**

Much of the extra SQL comes from EF Core protecting correctness, especially around nulls. Because C# and SQL treat null differently, EF Core rewrites equality checks into IS NULL or IS NOT NULL conditions and adds compensating logic, so database results match what your .NET code would return in memory.

**What is client-side evaluation in EF Core and why is it risky?**

Client-side evaluation means EF Core fetches data and runs untranslatable query parts in .NET memory instead of SQL. It is risky because a query that feels fast against a few hundred test rows can pull tens of thousands of rows in production, so performance collapses on the application server.

**How does EF Core query caching affect memory usage?**

Caching reuses the translation work for repeated query shapes, so later executions run faster, but every cache entry takes memory. Dynamically composed queries that produce a slightly different shape on each call create many entries that are never reused, which can raise memory pressure while database load looks normal.
