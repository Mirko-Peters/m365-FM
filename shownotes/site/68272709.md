Many Azure File Sync environments still authenticate with certificates and SAS tokens that can be copied, leaked and reused. This episode is for Azure and hybrid infrastructure admins who want to understand the risk and move to managed identities with a clear, step-by-step migration path via Azure VMs and Azure Arc.

- 00:00 – Why Azure File Sync authentication is rotting
- 01:33 – The legacy model: certificates and SAS tokens
- 04:09 – The "but it still works" syndrome
- 07:43 – Managed identities explained
- 12:27 – Migration playbook: Azure VMs and Azure Arc
- 17:41 – After the switch: security that scales
- 21:28 – Why migration is the only sensible move

## Key takeaways

- Certificates and SAS tokens in legacy Azure File Sync deployments are transferable secrets that grant access to whoever holds them, regardless of identity.
- Managed identities replace both authentication legs with short-lived [Entra ID](https://www.m365.fm/entity/entra-id/?utm_source=podcast&utm_medium=shownotes&utm_campaign=your-azure-file-sync-is-a-time-bomb) tokens and automatic RBAC role assignments, removing manual rotation and extra firewall URLs.
- Migration means updating the sync agent to version 20 or later, enabling system-assigned identities on Azure VMs or via Azure Arc for other servers, then switching the Storage Sync Service to managed identity.

## FAQ

**How does Azure File Sync authenticate without managed identities?**

Legacy deployments use two secrets: server endpoints prove themselves to the Storage Sync Service with locally stored certificates, and the service and servers reach the Azure file share with SAS tokens. Neither is bound to a machine, so anyone holding a copied certificate or token can impersonate a legitimate server.

**What do you need before switching Azure File Sync to managed identity?**

You need Azure File Sync agent version 20 or later on every registered server. Azure VMs then get a system-assigned managed identity from their identity blade, while on-premises or other-cloud servers are connected through Azure Arc first. Only then do you enable managed identity authentication on the Storage Sync Service.

**Which RBAC roles does Azure File Sync assign when you enable managed identity?**

Azure assigns them automatically. The Storage Sync Service's system-assigned identity gets Storage Account Contributor, and each registered server identity gets Storage File Data SMB Share Contributor. If you later move the service or file share to another subscription or resource group, the bindings vanish and must be restored with the provided PowerShell cmdlets.
