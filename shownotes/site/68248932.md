## Key takeaways

- Classic Application Gateway v2 sent [Azure](https://www.m365.fm/entity/azure/?utm_source=podcast&utm_medium=shownotes&utm_campaign=azure-app-gateway-network-isolation-finally-separate-control-plane-and-data-plane-for-true-private-perimeter-security) management traffic through the same public endpoint as user traffic, so even internal-only gateways needed a public IP and outbound internet access.
- Network isolation is enabled by registering a subscription-level feature flag and only applies to gateways deployed after registration; existing gateways keep their old architecture.
- Isolated gateways can be private-only, block all outbound internet traffic, use custom routes and DNS, and keep WAF and TLS termination, with Private Link support as the remaining caveat.

## FAQ

**Why did a private Azure Application Gateway need a public IP?**

Because Application Gateway v2 sent Azure's management traffic, the control plane, through the same public endpoint as user traffic. Even internal-only apps such as HR portals had to expose an external IP and allow outbound internet access so the gateway manager service could handle configuration, monitoring and scaling.

**How do you enable Application Gateway network isolation?**

You register a subscription-level feature flag, in the Azure portal under Preview features as Enable Application Gateway Network Isolation, or via PowerShell or Azure CLI. Despite the preview label, the episode says the capability is generally available. It only applies to gateways created afterwards, so existing gateways must be redeployed.

**Does Application Gateway network isolation support Private Link?**

Not at the time of recording: Private Link is the one remaining limitation, so isolated gateways cannot use private endpoints across unpeered VNets with overlapping address spaces. The suggested workaround is to unregister the flag, deploy a classic gateway with the private endpoint, then register the flag again for future deployments.
