## FAQ

**Why use MCP if Copilot Studio and Logic Apps already have connectors?**

Connectors are plumbing, not governance, so MCP adds a standard tool contract on top of them. The episode argues that MCP tools have fixed names, schemas and descriptions, so a model selects from approved actions instead of guessing endpoints. They can be built once and reused across Copilot Studio, Foundry, VS Code and other agent platforms.

**What is the two-plane model for Copilot Studio and Azure Logic Apps?**

It separates reasoning from execution. Copilot Studio is the reasoning plane: it interprets intent, asks for missing context and selects a tool. Azure Logic Apps is the execution plane: it validates inputs, calls systems of record in a fixed order with retries and compensation, refuses policy violations and keeps run history as audit evidence.

**How should MCP tools be designed for enterprise governance?**

Design MCP tools as narrow business verbs, not generic actions like create record. The episode recommends constrained inputs, allowed values, small structured outputs with a correlation ID, and precise descriptions, because the model uses those descriptions to choose tools. Each tool also needs an owner, versioning and change control, plus a place in a catalog such as Azure API Center.
