## Key takeaways

- Use VAL for fixed scalars evaluated once in the caller's context and EXPR for formulas that must re-evaluate under the filters and iterators inside the function.
- An EXPR parameter does not get context transition automatically, so wrap every evaluation of it in CALCULATE inside the UDF instead of relying on callers.
- When an EXPR is used more than once, materialize it once per entity with ADDCOLUMNS and reuse the column, and choose parameter types that match the math to avoid silent truncation.

## FAQ

**What is the difference between VAL and EXPR parameters in DAX user-defined functions?**

VAL passes a value: the argument is evaluated once in the caller's filter context and the function receives a frozen scalar. EXPR passes the unevaluated formula, which the function evaluates in its own context every time it is used, so it behaves like a measure and reacts to filters and iterators inside the function.

**Why does my DAX UDF ignore the current row even with an EXPR parameter?**

Because an EXPR parameter does not get context transition automatically. Measures carry an implicit CALCULATE inside a row context, but inline expressions do not. If the UDF iterates customers with AVERAGEX or FILTER, wrap every evaluation of the parameter in CALCULATE inside the function, not around the whole iterator and not in the caller.

**How do parameter type hints affect results in DAX UDFs?**

Declared types coerce arguments, which can silently truncate values. In the episode's example, two integer VAL parameters receive 3.4 and 2.4, become 3 and 2, and the function returns 5. For VAL the cast happens before the function runs; for EXPR it happens at each evaluation, so declare decimal for fractional metrics.
