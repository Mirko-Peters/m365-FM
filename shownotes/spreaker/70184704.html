Many organizations believe that picking an EU region or buying a sovereign cloud offering makes them sovereign, while identity, keys and the control plane remain under someone else's authority. This episode is for architects and IT leaders working with Microsoft 365 and Azure and breaks sovereignty into verifiable layers, from the EU Data Boundary and CLOUD Act to Entra, Azure Arc and Azure Local, ending in a default-deny reference architecture.

In this episode

  • 00:00 – The comfortable lie: sovereign cloud as a product
  • 05:11 – The sovereignty stack: five layers you can verify
  • 08:56 – EU Data Boundary and the CLOUD Act: jurisdiction eats geography
  • 17:17 – Key custody, customer-managed keys and confidential computing
  • 26:28 – Entra, Conditional Access drift, the token supply chain and policy rollback
  • 43:22 – Control plane vs data plane, Azure Arc, landing zones and regions
  • 60:49 – Azure Local, Microsoft 365 Local and tenant isolation
  • 78:11 – The default-deny sovereign reference architecture

Key takeaways

  • Sovereignty is not a region, SKU or compliance pack; it is enforceable authority over identity, keys, data and the control plane that can change all three.
  • The EU Data Boundary improves residency but jurisdiction such as the CLOUD Act still reaches the provider, so only external key custody with attested secure key release turns compelled disclosure into unreadable ciphertext.
  • A default-deny design minimizes Conditional Access exceptions, versions and restores identity configuration, scopes Azure Arc and landing zones to sovereignty domains, and uses disconnected Azure Local when no external dependency is acceptable.
