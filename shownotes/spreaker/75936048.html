Many people assume a firewall is a firewall, but a web application firewall reads what traffic says rather than where it goes. This Simply Explained episode is for beginners and Azure admins who want to know what Azure Web Application Firewall catches, where it lives, how its scoring and modes work, what it costs and what it cannot protect.

In this episode

  • 00:00 – What Azure Web Application Firewall actually does
  • 00:32 – Why a website needs its own firewall
  • 01:55 – Where Azure WAF lives
  • 03:34 – How the rules decide what to block
  • 05:25 – Detection mode, prevention mode and tuning
  • 07:09 – Bots, floods and limits
  • 09:06 – What it costs and how to monitor it
  • 12:05 – Where it fits in your Microsoft 365 world

Key takeaways

  • Azure Web Application Firewall reads what web requests say and blocks known attack patterns such as SQL injection and cross-site scripting, based on OWASP-derived managed rule sets.
  • It runs as a policy on Application Gateway for regional apps or Front Door for global apps, and should be tuned in detection mode before switching production to prevention mode.
  • It is not DDoS protection, cannot fix broken access control, needs a locked-down origin, and does not protect your Microsoft 365 tenant, only the apps you host yourself.

Worth quoting

“A firewall mostly watches where traffic is going. While this one reads what the traffic says. That difference is the whole reason it exists, and it's where almost every beginner gets it wrong.” – Mirko Peters (00:11)

“A web application firewall can't fix that one, because broken access control is a logic problem in your own code, and not a pattern in the request.” – Mirko Peters (01:46)
