A one-line change passes every unit test and still breaks orders, notifications and pages in production. This episode is for developers and DevOps teams building Azure apps who want to know which bugs unit, integration and front-end tests each catch, and how to orchestrate all three in one pipeline.

In this episode

  • 00:00 – The domino effect of a safe code change
  • 04:11 – Unit tests: the first line of defense
  • 08:07 – Integration tests: where things get messy
  • 11:27 – Front-end tests: catching what others miss
  • 15:26 – The Azure DevOps pipeline orchestrating all three
  • 19:19 – Testing as confidence, not a checklist

Key takeaways

  • Unit tests are fast and cheap for validating isolated logic, but they cannot catch serialization, configuration or cross-service failures.
  • Integration tests against real queues, databases and bindings expose environment issues such as mismatched queue names or broken connection strings.
  • Front-end tests with Playwright confirm what users actually see, and an Azure DevOps pipeline should run each layer at the stage where it is cheapest.

Worth quoting

“Passing tests aren't evidence that your app will work across distributed services. They only confirm that internal logic works when fed controlled inputs.” – Mirko Peters (06:29)

“But skipping them is dangerous because environment specific issues like mismatched que names or incorrect connection strings are exactly the kinds of failures that unit tests never see.” – Mirko Peters (09:07)
