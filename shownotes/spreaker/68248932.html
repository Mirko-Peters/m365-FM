Your "private" Azure Application Gateway may still expose a public IP just so Azure can manage it. This episode explains to Azure architects and security teams how network isolation separates the control plane from the data plane, how to enable it, and what you can finally lock down.

In this episode

  • 00:00 – A private gateway that still needed a public IP
  • 00:41 – The flawed premise: when private still meant public
  • 03:10 – Control plane versus data plane
  • 06:53 – The magic switch: registering the network isolation flag
  • 11:42 – What you can finally do now
  • 19:00 – The philosophy of isolation
  • 22:02 – Your move toward a truly private cloud

Key takeaways

  • Classic Application Gateway v2 sent Azure management traffic through the same public endpoint as user traffic, so even internal-only gateways needed a public IP and outbound internet access.
  • Network isolation is enabled by registering a subscription-level feature flag and only applies to gateways deployed after registration; existing gateways keep their old architecture.
  • Isolated gateways can be private-only, block all outbound internet traffic, use custom routes and DNS, and keep WAF and TLS termination, with Private Link support as the remaining caveat.

Worth quoting

“Isolation at its core isn't about cutting cables. It's about separating intentions. The control plane should govern, not mingle. The data plane should serve, not gossip.” – Mirko Peters (19:34)

“Turning on Network ISO doesn't toggle a feature in an existing gateway. It defines which architecture will govern all future deployments in your subscription.” – Mirko Peters (07:30)
