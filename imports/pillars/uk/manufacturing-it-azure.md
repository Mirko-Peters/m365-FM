# Azure для виробництва: повний посібник з ІТ-інфраструктури виробництва на Microsoft Azure (листопад 2026)

**Коротка відповідь:** Наприкінці 2026 року Azure для виробництва зводиться до трьох рівнів: Azure IoT Operations на Kubernetes з підключенням через Azure Arc на заводі, Microsoft Fabric (Real-Time Intelligence і OneLake) як платформа даних, а також Microsoft Foundry, Power BI і Copilot для аналітики, ШІ та робочого середовища. Старі складники виведено з експлуатації (Time Series Insights, попередні версії агентів для виробництва) або заплановано до виведення (IoT Central у 2029 році, безпека OT у Defender for IoT). Успіх залежить менше від сервісів, ніж від того, чи володієте ви власною моделлю даних, чи має ваш дизайн безпеки OT відповідність ISA/IEC 62443 та рекомендаціям NIST, і чи обираєте ви сценарії використання з виміряною базовою лінією.

**Ключові висновки**

- Нові підключення заводського обладнання плануйте на **Azure IoT Operations**, а не на IoT Central чи вручну побудованих ланцюжках модулів IoT Edge. Оберіть SKU **Standard**, якщо ваше обладнання працює з OPC UA; Essentials не містить конектора OPC UA.
- Для даних часових рядів використовуйте **Microsoft Fabric Real-Time Intelligence** (Eventstream, Eventhouse, Activator). Time Series Insights було виведено з експлуатації 7 липня 2024 року.
- Не переносьте бізнес-логіку на сервіси в попередній версії. Microsoft вивела з експлуатації свою модель даних для виробництва та попередні версії агента для заводу у 2025 році, приблизно через рік після запуску.
- Уже зараз плануйте заміну **моніторингу OT**. Microsoft повністю виведе з експлуатації безпеку OT у Defender for IoT у жовтні 2029 року; партнерський блог Microsoft називає 31 травня 2028 року як дату завершення підтримки.
- Узгодьте свою програму безпеки з **ISA/IEC 62443** (зони та канали зв'язку) і **NIST CSF 2.0**; постачальникам для оборони також потрібна **CMMC** для систем, які обробляють FCI або CUI.
- Починайте зі сценаріїв використання, які мають базову лінію та відповідального власника: оперативний OEE і простежуваність зазвичай окупаються раніше, ніж предиктивне обслуговування.

## Що таке Azure для виробництва сьогодні

П'ять років тому пошук за запитом "Azure for manufacturing" або "Azure IoT for manufacturing" повертав знайомий перелік: IoT Hub, IoT Edge, Stream Analytics, Time Series Insights та Synapse. Цей перелік уже не описує ситуацію у 2026 році. Microsoft перебудувала свою стратегію промислового IoT у трьох напрямках:

1. **Край замість пристрою:** Збирання даних на заводі тепер виконується на **Azure IoT Operations**, наборі сервісів даних на кластерах Kubernetes, якими керують із хмари через **Azure Arc**. Microsoft описує цей сервіс як "уніфіковану площину даних для краю" [3]. Загальну доступність оголосили у листопаді 2024 року [5].
2. **Платформа даних замість окремих сервісів:** Часові ряди, події та майстер-дані потрапляють до **Microsoft Fabric**, зокрема до Real-Time Intelligence з Eventstream, Eventhouse та Activator. Microsoft вивела з експлуатації Time Series Insights і рекомендує клієнтам цільову міграцію на Fabric Eventhouse [10].
3. **Платформа замість готового застосунку:** У сфері IoT і виробництва Microsoft відходить від власних попередньо налаштованих застосунків. IoT Central припинив приймати нові застосунки 23 вересня 2026 року і буде виведений з експлуатації 20 вересня 2029 року [8], [64]. Галузеві попередні версії "Manufacturing data solutions" і "Factory Operations Agent" були виведені з експлуатації 30 травня 2025 року [2].

Галузева пропозиція тепер називається **Microsoft for Manufacturing** (раніше "Microsoft Cloud for Manufacturing"). Microsoft організовує її у чотири напрями рішень: цифровий інжиніринг, стійкі ланцюги постачання, інтелектуальні заводи та пов'язані клієнти [1]. Для інтелектуального заводу Microsoft називає чотири сценарії: модернізація краю та інфраструктури, оптимізація операцій за допомогою ШІ, залучення та розширення можливостей персоналу, а також технічне обслуговування та якість [1]. Microsoft позиціонує Fabric як платформу для "цифрової нитки" [1].

Для вас як керівника IT, OT або цифрової трансформації це означає, що будівельні блоки стали більш універсальними, а більша частина відповідальності за модель даних, інтеграцію та експлуатацію лежить на вас або ваших партнерах. Цей посібник показує, як структуровано нести цю відповідальність. Він поєднує технології Azure з питаннями, які визначають успіх: модель даних, безпеку, [Industry 4.0](https://www.m365.fm/entity/industry-4-0/) як організаційна тема, KPI та витрати.

### Для кого призначений цей посібник

- **ІТ-керівники та хмарні команди**, які вже працюють з Microsoft 365 та Azure і отримали завдання підключити заводи.
- **Фахівці з OT та автоматизації**, які хочуть розуміти, що Kubernetes, MQTT і Fabric означають для їхнього обладнання.
- **Керівники заводів, якості та технічного обслуговування**, які оцінюють сценарії використання, такі як предиктивне обслуговування або простежуваність.
- **Фінансові та закупівельні команди**, яким потрібно зробити витрати на хмару у виробництві передбачуваними.

### Виробничі терміни для адміністраторів Microsoft 365 та Azure

Якщо ви прийшли з корпоративного ІТ, проєкти у виробництві приносять власну термінологію. Ось ключові терміни, що використовуються в цьому посібнику, кожен одним реченням:

| Термін | Значення | Найближча аналогія в ІТ |
|---|---|---|
| **OT** (operational technology) | Технології, що керують фізичними процесами: верстатами, контролерами, системами керування | Як окремий дата-центр, де збій зупиняє виробництво |
| **PLC** (programmable logic controller) | Промисловий комп'ютер, що керує верстатом у реальному часі | Вбудована система зі терміном служби 15 років і більше |
| **SCADA** | Система нагляду для моніторингу та керування кількома верстатами або лініями | Консоль моніторингу з правом запису |
| **MES** (manufacturing execution system) | Керує виконанням виробничих замовлень на заводі та фіксує їх перебіг | Система робочих процесів між ERP і верстатом |
| **OPC UA** | Незалежний від виробника промисловий стандарт обміну даними з інформаційною моделлю та вбудованою безпекою | REST API плюс схема плюс сертифікати, але для верстатів |
| **MQTT** | Легкий протокол публікації/підписки | Шина повідомлень, подібна до тем Event Grid або Service Bus |
| **Unified namespace (UNS)** | Центральна ієрархічна структура подій, в якій усі системи публікують свій поточний стан | Корпоративний каталог тем |
| **OEE** (overall equipment effectiveness) | Ефективність обладнання, що складається з доступності, продуктивності та якості | SLA доступності, але для верстатів і з урахуванням якості |
| **KQL** (Kusto Query Language) | Мова запитів Fabric Eventhouse та Azure Data Explorer | Та сама мова, яку ви використовуєте в Log Analytics і Microsoft Sentinel |
| **Модель Пердью** (Purdue model) | Референтна модель, що розділяє системи заводу на рівні від польових пристроїв до підприємства; ISA-95 спирається на неї [26] | Модель ієрархії мереж, від VLAN пристроїв до корпоративної WAN |

Рядок про KQL — хороша відправна точка для адміністраторів: якщо ви знаєте KQL із Sentinel або Log Analytics, ви можете одразу запитувати дані верстатів в Eventhouse.

### З чого почати адміністратору Microsoft 365 або Azure

Щоб додати цінності в проєкт на виробництві, не обов'язково ставати інженером з автоматизації. П'ять завдань, як правило, належать центральному ІТ і можуть бути підготовлені до підключення першого верстата:

1. **Ідентифікатори та ролі:** Створіть групи Microsoft Entra ID і ролі Azure RBAC для співробітників OT, партнерів і команд операційної діяльності; використовуйте Privileged Identity Management, щоб обмежити привілейований доступ у часі.
2. **Azure landing zone для заводів:** Визначте структуру підписок і груп ресурсів для кожного заводу та використовуйте Azure Policy для забезпечення тегів (завод, центр витрат, сценарій використання) і дозволених регіонів.
3. **Протестуйте Azure Arc:** Підключіть тестовий сервер або кластер Kubernetes до Arc і разом із мережевою командою погодьте необхідні вихідні кінцеві точки через ланцюжок проксі. У багатьох компаніях саме ці погодження міжмережевого екрана займають найбільше часу.
4. **Основи Fabric:** Визначте ємність, структуру робочих просторів і модель доступу; перенесіть наявне управління Power BI.
5. **Налагодьте робочі відносини з OT:** Зрозумійте модель зон заводу, перш ніж пропонувати зміни в мережі. В OT доступність важливіша за конфіденційність, а вікна обслуговування визначаються графіком виробництва, а не Patch Tuesday.

| **Manufacturing data solutions in Microsoft Fabric** | Модель даних виробництва у Fabric (попередній перегляд з квітня 2024 року) | Статус неясний: повідомлення про вихід з експлуатації називають «Manufacturing data solutions» без суфікса Fabric і не включають та не виключають варіант для Fabric; окремого запису з квітня 2024 року немає. Не закладайте його в нові проєкти; уточніть статус у Microsoft. | [2] |

### Що означає таблиця для вашої архітектури

**По-перше:** плануйте нові підключення заводів на Azure IoT Operations, а не на IoT Central і не на власних ланцюгах модулів IoT Edge, якщо немає конкретної причини. IoT Edge залишається підтримуваним, але це модель середовища виконання для пристроїв; Azure IoT Operations забезпечує роботу з даними заводу через брокер, конектори та модель активів [3]. Під час вибору SKU зауважте, що Essentials не включає конектор OPC UA [3]. Для типового заводу з верстатами OPC UA відправною точкою є Standard.

**По-друге:** тримайте бізнес-логіку подалі від сервісів у попередньому перегляді. Історія рішень Manufacturing data solutions показує, що модель даних виробництва Microsoft може пройти шлях від попереднього перегляду до виведення з експлуатації трохи більше ніж за рік [2]. Ваша модель даних належить вам і має бути задокументована у відкритих форматах (таблиці Delta в OneLake, схеми JSON у брокері, DTDL або інформаційні моделі OPC UA).

**По-третє:** перегляньте свою стратегію безпеки OT. Офіційне повідомлення Azure називає жовтень 2029 року датою завершення безпеки OT у Defender for IoT, тоді як блог партнера Microsoft вказує 31 травня 2028 року як дату завершення підтримки [22], [39]. Плануйте з урахуванням ранішої дати: закупівля, розгортання та приймання нових датчиків у регульованих середовищах часто займають більше року.

**По-четверте:** перегляньте свій парк пристроїв IoT Edge. Пристрої з IoT Edge 1.5 не отримують оновлень безпеки з 10 листопада 2026 року. Microsoft описує перехід на 1.6 LTS як простий, оскільки він не містить великих змін функціональності [12]. Те саме завершення підтримки стосується пристроїв Windows, що працюють з IoT Edge для Linux на Windows (EFLOW) 1.5; на сторінці версій немає EFLOW 1.6 LTS, є лише безперервна лінійка випусків [12]. Уточніть цільовий шлях для цих пристроїв у Microsoft або у свого постачальника обладнання.

> **Примітка щодо актуальності:** ця таблиця є знімком на певний момент. Перед кожним архітектурним рішенням перевіряйте пов'язані сторінки Microsoft і портал Azure Updates, відфільтрований за "Retirements".

## Спочатку модель даних: ISA-95 і уніфікований простір імен

Багато проєктів виробництва зазнають невдачі не через хмару, а тому, що ніхто не визначив, що таке "верстат", "замовлення" чи "подія простою" в моделі даних. Дайте відповідь на це питання, перш ніж розгорнути першу службу Azure.

### ISA-95 і піраміда автоматизації

Серія **ANSI/ISA-95** (міжнародно IEC 62264) описує інтеграцію корпоративних систем і систем керування [26]. ISA описує її як набір стандартів для інтеграції логістичних систем із системами керування виробництвом, побудований на еталонній моделі Пердью, застосовний до дискретних, безперервних і логістичних галузей; серія має вісім частин [26]. Вона дає два елементи, корисні для будь-якої хмарної архітектури:

- **Рівнева модель:** рівні 0–2 охоплюють фізичний процес, датчики, виконавчі механізми та керування (ПЛК, SCADA). Рівень 3 — це управління виробничими операціями (MES, MOM). Рівень 4 — бізнес-планування ([ERP](https://www.m365.fm/entity/enterprise-resource-planning/)). У Європі цю ієрархію часто зображують як "піраміду автоматизації"; у Північній Америці частіше використовується модель Пердью.
- **Об'єктна модель:** ISA-95 визначає такі поняття, як ієрархія обладнання (підприємство, площадка, ділянка, робочий центр, робочий блок), матеріал, персонал, виробничі замовлення та дані про продуктивність. OPC Foundation відобразила цю модель у власній супровідній специфікації для OPC UA [35].

Критика піраміди добре відома: дані рухаються лише рівень за рівнем, кожен інтерфейс є інтеграцією "точка-точка", а нова програма має підключатися до кількох систем. Об'єктна модель, натомість, залишається цінною, оскільки дає ІТ, OT і бізнесу спільну мову.

### Уніфікований простір імен: події замість піраміди

**Уніфікований простір імен (UNS)** — це архітектурний шаблон, а не стандарт. Усі системи публікують свій поточний стан як події в центральний брокер з ієрархічною структурою, як правило MQTT. Споживачі підписуються на потрібні їм теми. Ієрархія тем часто відповідає ієрархії обладнання ISA-95, наприклад:

```
acme/dayton-plant/assembly/line-3/station-20/state
acme/dayton-plant/assembly/line-3/station-20/order
acme/dayton-plant/assembly/line-3/station-20/quality
```

Azure IoT Operations містить edge-нативний брокер MQTT, який підтримує MQTT 3.1.1 та MQTT 5 [40]. Конектор OPC UA публікує дані з серверів OPC UA як JSON у форматі OPC UA PubSub до тем брокера, а також може записувати значення назад у вузли OPC UA; запити на запис використовують шаблон запит/відповідь MQTT 5 [4]. Це дозволяє побудувати UNS на заводі без окремого брокера.

Якщо ви вже використовуєте UNS на іншому брокері, його не обов'язково замінювати: потоки даних можуть пересилати повідомлення до зовнішніх брокерів MQTT [3]. Чи використовувати брокер Microsoft як UNS заводу або як джерело для наявного брокера, є рішенням щодо експлуатації. Важливою є обов'язкова угода про теми та структуру корисного навантаження, незалежна від продукту.

### ISA-95 чи UNS? Обидва.

Продуктивна відповідь така: використовуйте **ISA-95 як словник**, а **UNS як шаблон передачі**. На практиці:

| Питання | Рекомендація |
|---|---|
| Як називати активи? | Ієрархія обладнання ISA-95, однакова для всього підприємства |
| Як структурувати теми? | За ієрархією обладнання, з бізнес-доменами нижче (стан, замовлення, якість, енергія) |
| Як описувати корисне навантаження? | Схеми JSON у реєстрі схем Azure Device Registry [3]; для машин краще використовувати companion-специфікації OPC UA |
| Де зберігаються майстер-дані? | У системі запису (ERP, MES, PLM); UNS лише розподіляє посилання та стани |
| Як вести історію? | Не в брокері, а в Eventhouse або Lakehouse у Fabric |

### Мінімальна модель даних виробництва

Незалежно від інструментів, сценаріям цього посібника потрібна базова модель із семи сутностей:

1. **Актив** (машина, станція, інструмент) з унікальним ідентифікатором і місцем в ієрархії
2. **Сигнал** (тег, виміряна змінна) з одиницею виміру, частотою дискретизації та зв'язком з активом
3. **Стан** (працює, планований простій, непланований простій, переналагодження) з кодом причини
4. **Замовлення** (виробниче замовлення, операція) зі зв'язком з ERP
5. **Матеріал і номер партії/серійний номер** зі зв'язком зі специфікацією матеріалів
6. **Подія** (аварійний сигнал, висновок щодо якості, технічне обслуговування)
7. **Персонал/зміна**, якою мірою це дозволяють правила конфіденційності та трудові угоди

Якщо ви чисто пов'яжете ці сім сутностей, з одного фундаменту даних можна обслуговувати OEE, предиктивне обслуговування, простежуваність і цифровий двійник. Як вивести таку модель з потоку створення цінності, ми розглядаємо в епізоді [Value Stream Mapping as a Live Data Model](https://www.m365.fm/show/episodes/value-stream-mapping-live-data-model/); сам метод описано в нашому посібнику з [картування потоку створення цінності](https://www.m365.fm/en/learn/value-stream-mapping/).

## Референсна архітектура Azure для виробництва

Наведена нижче референсна архітектура узагальнює те, що Microsoft описує в документації Azure IoT Operations [3] та в референсній архітектурі Fabric "Connected Factory" [17], і додає шари, яких ці джерела не охоплюють: безпеку, майстер-дані та робоче місце.

### Модель шарів

| Шар | Функція | Компоненти Azure та Microsoft | Типові рішення |
|---|---|---|---|
| **0: Польовий рівень і керування** | Верстати, PLC, датчики, стенди для випробувань, камери | Компонента Azure не потрібна; сервер OPC UA на контролері або шлюзі, за потреби дооснащення датчиками | Які верстати підтримують OPC UA? Де потрібне дооснащення? |
| **1: Інфраструктура edge** | Обчислення в цеху, сегментація мережі | Промислові ПК або сервери з Kubernetes (наприклад, AKS Edge Essentials на Windows, кластери на базі Ubuntu) [3] або Azure Local [21]; керування через Azure Arc | Одновузловий чи багатовузловий кластер? Хто експлуатує апаратуру? Примітка: версія Essentials обмежена одним вузлом [3] |
| **2: Площина даних edge** | Збирання, нормалізація, буферизація, локальний UNS | Azure IoT Operations: брокер MQTT, конектор OPC UA, конектор HTTP/REST (конектори Akri), потоки даних, середовище операцій, автоматичне виявлення пристроїв і активів [3], [4] | Структура тем, схеми, агрегація на edge, дисковий буфер брокера, поведінка в офлайн-режимі (максимум 72 години, можлива деградація [3]) |
| **3: Керування активами та пристроями** | Який актив є яким? Які точки даних? | Azure Device Registry з просторами імен і реєстром схем [3]; для безпосередньо підключених пристроїв IoT Hub і DPS [8] | Хто підтримує майстер-дані активів? Узгодження із системою технічного обслуговування (CMMS)? |
| **4: Потокова обробка та аналітика в реальному часі** | Прийом подій, їх збагачення, генерація сповіщень | Fabric Real-Time Intelligence: Eventstream, Eventhouse (KQL), Activator, Real-Time Dashboards [17], [18]; альтернативно Azure Event Hubs і Azure Data Explorer [19] | Ємність Fabric чи PaaS Azure? Зберігання гарячих/холодних даних? |
| **5: Платформа даних** | Історія, контекстні дані, data products | OneLake, Lakehouse, Data Factory для даних ERP, MES і змін [17] | Структура medallion, власник data products, модель доступу |
| **6: Семантика та цифровий двійник** | Значення, зв'язки, онтологія | Онтологія Fabric IQ (попередній перегляд) [16], Digital Twin Builder (попередній перегляд) [15] або Azure Digital Twins з DTDL [14] | Чи прийнятний попередній перегляд? Збереження власності над моделлю |
| **7: Аналітика та ШІ** | Моделі, прогнози, агенти | Fabric Data Science [17], Azure Machine Learning, Microsoft Foundry [20] | Де навчати, де виконувати інференс (хмара чи edge)? |
| **8: Робоче місце та процеси** | Інформування людей і можливість діяти | Power BI, Teams (зокрема сценарії для фронтлайн-працівників), Power Apps, Power Automate, Microsoft 365 Copilot, Dynamics 365 | Яка роль що бачить? Мобільні пристрої на виробничій ділянці? |
| **Наскрізно: безпека та управління** | Ідентифікація, мережа, моніторинг, відповідність вимогам | Microsoft Entra ID, Azure Policy, портфель Microsoft Defender, Microsoft Purview, датчики OT (Defender for IoT лише як перехідний варіант, рішення партнерів) [22] | Модель зон відповідно до ISA/IEC 62443, профіль NIST CSF 2.0, порядок повідомлення про інциденти |
| **Наскрізно: витрати** | Прозорість, розподіл, оптимізація | Microsoft Cost Management, метрики ємності Fabric, практики FinOps [25] | Вартість на завод, лінію, сценарій використання |

### Потік даних за десятьма кроками

1. Контролер надає значення процесів через сервер OPC UA.
2. Конектор OPC UA в Azure IoT Operations зчитує налаштовані точки даних активу та публікує їх у топік брокера, наприклад `azure-iot-operations/data/<asset>` [4].
3. Конектор може автоматично виявляти активи на серверах OPC UA та додавати їхню конфігурацію до Azure Device Registry [4].
4. Потоки даних фільтрують, нормалізують, перетворюють одиниці вимірювання та збагачують контекстом [3], [31].
5. Локальні застосунки (наприклад, андон-табло або інлайн-інспекція) підписуються на брокер безпосередньо.
6. Потік даних передає агреговані дані до хмарного endpoint: Event Hubs/Kafka, брокер MQTT Event Grid, Data Lake Storage, Fabric OneLake або Azure Data Explorer [3].
7. У Fabric Eventstream приймає дані, а Eventhouse зберігає їх для запитів KQL [17].
8. Data Factory синхронізує дані ERP, MES, змін і витрат до OneLake [17].
9. Події збагачуються ієрархією активів і топологією ліній; моделі навчаються та оцінюються, а результати зберігаються в OneLake [17].
10. Real-Time Dashboards і Power BI візуалізують дані, Activator сповіщає техніків, а Copilot відповідає на запитання природною мовою [17].

Microsoft оцінює еталонну архітектуру Connected Factory у понад мільйон подій IIoT на годину з 30 000 тегів на 40 фабриках [17]. Сприймайте це як орієнтир, а не як гарантію продуктивності для вашого середовища.

### Уроки з проєктів

Консалтингова компанія b.telligent описує три уроки з проєктів з Azure IoT Operations і Fabric [31]:

- **Налаштуйте сховище брокера:** Без налаштованого персистентного сховища повідомлення, які не вдається переслати, можуть заповнити пам'ять. Microsoft опосередковано підтверджує цей момент: буфер повідомлень брокера на диску можна задати лише під час початкового розгортання, а не пізніше [40]. Визначте профіль пам'яті та буфер до запуску в експлуатацію.
- **Зберігайте стабільність схем:** Зміни структур JSON роблять подальшу обробку крихкою. Єдиний envelope з метаданими та корисним навантаженням допомагає.
- **Консолідуйте Eventstream:** Оскільки кожен Eventstream має поточні витрати, пост рекомендує консолідувати їх на рівні заводу, а не джерела, і виконувати трансформації в Eventhouse за допомогою політик оновлення та KQL, а не в Eventstream.

Ці поради походять із допису за березень 2025 року (оновлено в червні 2025 року); перевірте, чи вони досі актуальні для вашого релізу.

### Альтернативні шляхи

Не кожному виробнику потрібна повна архітектура. Поширені чотири варіанти:

| Варіант | Коли має сенс | Складові |
|---|---|---|
| **Прямо в хмару** | Небагато сучасних, підключених пристроїв; немає вимог до затримки | IoT Hub, DPS, Fabric Real-Time Intelligence |
| **Орієнтовано на edge** | Багато верстатів, OPC UA, локальні рішення, мережа OT без прямого підключення до хмари | Azure IoT Operations на Arc, Fabric |
| **Партнерський edge** | Наявна промислова edge-платформа від постачальника автоматизації | Партнерська платформа плюс Fabric або Azure; Microsoft наводить, наприклад, запуск моделей Azure AI на Siemens Industrial Edge як орієнтир для архітектури [2] |
| **Невеликий старт (середній виробник, один завод)** | Кілька ліній, немає власної команди Kubernetes, перший сценарій — OEE або моніторинг стану | Один кластер з одним вузлом з Azure IoT Operations Standard (через OPC UA), невелика ємність Fabric, Power BI; експлуатація кластера, можливо, через партнера |

Для середнього виробника з одним заводом повна багаторівнева архітектура є цільовою картиною, а не відправною точкою. Почніть із рівнів 1, 2, 4 та 8, а семантику, ШІ та міжзаводське управління додайте після того, як перший сценарій дасть результат.

## Конвергенція IT/OT та безпека

Щойно дані з машин потрапляють у хмару, завод стає частиною поверхні атаки. Водночас зростають регуляторні та споживчі вимоги. CISA відносить до ядра американського **сектору критичного виробництва** [52] виробництво первинних металів, машинобудування, електричного обладнання та компонентів, а також транспортного обладнання, тож багато заводів, які передають дані в Azure, належать до сектору критичної інфраструктури.

Цей розділ починається зі стандартів, що визначають технічний дизайн (ISA/IEC 62443, NIST CSF 2.0, NIST SP 800-82), далі розглядає обов'язки, які стосуються окремих груп виробників (CMMC, SEC, CIRCIA), а для компаній з операціями в ЄС або клієнтами в ЄС — NIS2 і Cyber Resilience Act.

### ISA/IEC 62443: зони, канали зв'язку, рівні безпеки

Серія **ISA/IEC 62443** є еталонною системою для безпеки систем промислової автоматизації та керування. Її ключові поняття: зони (групи активів з однаковими вимогами до захисту), канали (conduits) — контрольовані шляхи комунікації між зонами, та рівні безпеки як цільовий показник для кожної зони, від SL 1 (захист від випадкового або необережного порушення) до SL 4 (захист від досвідчених зловмисників із розширеними ресурсами) [27]. Стандарт також визначає сім базових вимог — від контролю ідентифікації та автентифікації до доступності ресурсів [27]. Для архітектури на Azure це означає:

- **Edge-кластер — окрема зона:** Кластер Kubernetes, на якому працює Azure IoT Operations, не належить ні до офісної мережі, ні безпосередньо до мережі керування, а розміщується в проміжній зоні (часто її називають «промислова DMZ», рівень Purdue 3.5).
- **Лише вихідні з'єднання:** Arc і потоки даних відкривають з'єднання від заводу до хмари. Вхідні з'єднання з інтернету в бік заводу не потрібні й не повинні відкриватися.
- **Багаторівневі мережі:** Microsoft зазначає, що Azure IoT Operations підтримує безпечне керування пристроями в багаторівневих мережах [3]. Plan the proxy and firewall chain early with OT security.
- **Надавайте право запису свідомо:** Коннектор OPC UA може записувати значення назад у контролери [4]. Ця можливість потребує окремої оцінки ризиків і процесу погодження та, бажано, на початку має бути вимкнена.
- **Сертифікати замість паролів:** Для OPC UA доступні автентифікація за логіном і паролем, сертифікати X.509 та анонімний доступ (лише для тестування) [4]. Використовуйте сертифікати та довірений список, а оновлення сертифікатів розглядайте як регулярний експлуатаційний процес.

### NIST CSF 2.0 та NIST SP 800-82: американська базова лінія

Для більшості американських виробників **NIST Cybersecurity Framework (CSF) 2.0** є спільною мовою між заводом, ІТ і правлінням. NIST опублікував його 26 лютого 2024 року; він розширює п'ять функцій — Identify, Protect, Detect, Respond і Recover — новою функцією **Govern** і застосовується до організацій будь-якого сектору та розміру [49]. Фреймворк є добровільним, але клієнти, страховики та аудитори дедалі частіше вимагають профіль CSF.

Два документи NIST конкретизують фреймворк для заводів:

- **NIST SP 800-82 Rev. 3, Guide to Operational Technology (OT) Security** (вересень 2023) охоплює архітектури OT, загрози та заходи протидії й додає OT-оверлей з адаптованими базовими наборами контролів SP 800-53 для OT-систем низького, помірного та високого впливу [50].
- **NIST IR 8183 Rev. 2, Cybersecurity Framework 2.0 Manufacturing Profile**, був опублікований як початковий публічний проєкт 29 вересня 2025 року; період коментарів завершився 17 листопада 2025 року, і станом на листопад 2026 року фінальна версія не вказана [51]. Використовуйте його як проєктну довідку, а не як фінальний стандарт.

Як ці елементи поєднуються в проєкті на Azure:

| Функція CSF 2.0 | Що це означає для виробничої платформи на Azure |
|---|---|
| Govern | Названі відповідальні за платформу заводу, прийняття ризиків для сервісів у попередньому перегляді, перелік постачальників (Microsoft, інтегратор, постачальники OT) |
| Identify | Інвентаризація OT-активів, звірена з Azure Device Registry; карта потоків даних для кожної зони та кожного каналу зв'язку (conduit) |
| Protect | Ролі Entra ID з мінімальними привілеями, PIM, сертифікати OPC UA, лише вихідне з'єднання, доступ на запис вимкнено за замовчуванням |
| Detect | Моніторинг OT-мережі (рішення партнера після Defender for IoT), централізовані журнали з edge і хмари в Sentinel або вашому SIEM |
| Respond | План реагування на інциденти, що охоплює завод і хмару, включно з тим, хто може відключити кластер під час виробництва |
| Recover | Перевірене повторне розгортання edge-кластера (інфраструктура як код), резервне копіювання конфігурації брокера та активів |

Малі та середні виробники не мусять робити це самотужки: National Network програми NIST Manufacturing Extension Partnership (MEP) пропонує самооцінку за CSF, аналіз прогалин, плани коригувальних дій, плани реагування на інциденти та допомогу з вимогами DFARS [58].

### CMMC для постачальників оборонної галузі

Якщо ви виготовляєте деталі або надаєте послуги для Міністерства оборони США, на системи, які обробляють, зберігають або передають Federal Contract Information (FCI) чи Controlled Unclassified Information (CUI), поширюється **Cybersecurity Maturity Model Certification (CMMC)**. Програмне правило (32 CFR Part 170) набуло чинності 16 грудня 2024 року [53]. Правило DFARS, яке вносить CMMC до контрактів, набуло чинності 10 листопада 2025 року, із поетапним впровадженням: фаза 1 почалася цієї дати, фаза 2 — 10 листопада 2026 року, а фаза 3 запланована на 10 листопада 2027 року [54]. Рівні такі: Рівень 1 (самооцінка, FCI), Рівень 2 (самооцінка або оцінка третьою стороною C3PAO, на основі NIST SP 800-171) і Рівень 3 (оцінка DIBCAC, що додає практики NIST SP 800-172) [53], [54].

Що це означає для Azure:

- **Визначайте обсяг за даними, а не за хмарою.** CMMC стосується ваших систем, а не Azure як платформи; сертифіката CMMC для самого Azure не існує [55]. Звичайна телеметрія обладнання може не бути CUI, тоді як креслення, специфікації та деякі технологічні параметри для оборонних деталей можуть ним бути; вирішальними є маркування CUI та умови контракту вашого замовника. Визначте, які дані в UNS і в OneLake входять до обсягу.
- **Свідомо обирайте хмарне середовище.** Microsoft стверджує, що як Azure commercial, так і Azure Government мають авторизації FedRAMP High, які охоплюють NIST SP 800-171, і що ви можете отримати сертифікацію CMMC для рішень в будь-якому з них; Azure Government додатково має авторизації DoD IL4/IL5 і договірні зобов'язання щодо зберігання даних у США та перевіреного персоналу США, і Microsoft вважає його кращим вибором для більшості оборонних підрядників [55]. Зверніть увагу, що сторінку Microsoft про CMMC востаннє оновлено в квітні 2023 року, тож уточніть деталі у свого керівника облікового запису Microsoft.
- **Перевірте доступність функцій.** Не кожна служба з цього посібника доступна в Azure Government або в середовищі Microsoft 365 GCC High. Перевірте доступність Azure IoT Operations, Fabric і Copilot для вашої цільової хмари, перш ніж будувати на них архітектуру [unverified: для окремих служб; перевірте сторінки Microsoft про доступність функцій для державних установ США].

### Звітність SEC і повідомлення про інциденти за CIRCIA

Два режими звітності в США впливають на те, як ви проєктуєте журналювання та реагування на інциденти для виробничої платформи:

- **Публічні компанії:** Відповідно до правил SEC, ухвалених 26 липня 2023 року, емітенти мають розкрити суттєвий інцидент кібербезпеки у Формі 8-K (Пункт 1.05) протягом чотирьох робочих днів після визначення його суттєвості, а також описати управління ризиками кібербезпеки, стратегію і управління в річній Формі 10-K [56]. Програма-вимагач, що зупиняє завод, — типовий кандидат для оцінки суттєвості, тож ваш план реагування на OT-інциденти має швидкий шлях до комітету з розкриття інформації.
- **Критична інфраструктура (CIRCIA):** Закон про звітування про кіберінциденти в критичній інфраструктурі (Cyber Incident Reporting for Critical Infrastructure Act) зобов'язує підпадаючі під нього суб'єкти повідомляти CISA про покриті кіберінциденти протягом 72 годин, а про виплати за вимагачами — протягом 24 годин, але лише після набрання чинності остаточним правилом CISA. Станом на жовтень 2026 року CISA передала остаточне правило до Білого дому на розгляд, і воно ще не було опубліковано [57]. Стежте за остаточним правилом; саме воно визначить, які виробники підпадають під дію закону.

### NIS2 та Акт про кіберстійкість для операцій у ЄС

Якщо ви керуєте заводами в ЄС або продаєте там обладнання, важливими є ще два європейські закони. Приклади з Німеччини нижче взято з оригінального німецького видання цього посібника і показують, як правила ЄС працюють на практиці.

**NIS2 (приклад: Німеччина).** Німецький закон про впровадження NIS2 (NIS2UmsuCG) набув чинності 6 грудня 2025 року; Федеральне відомство з безпеки інформаційних технологій Німеччини (BSI) тепер нагляд здійснює за приблизно 29 500 суб'єктами замість приблизно 4 500 [28]. Компанії підпадають під дію закону, якщо належать до одного з типів суб'єктів, зазначених у додатках 1 і 2 до Закону про BSI, і відповідають порогам з розділу 28: щонайменше 50 працівників або понад 10 мільйонів євро річного обороту та підсумку балансу одночасно [41]. Серед виробничих позицій додатка 2 є медичні вироби, комп'ютери, електронні та оптичні продукти, електричне обладнання, машини та транспортні засоби; хімічна промисловість і харчова промисловість є окремими секторами. Основні зобов'язання:

- **Реєстрація** у два етапи через обліковий запис «Mein Unternehmenskonto» і портал BSI, який відкрився 6 січня 2026 року [28].
- **Управління ризиками** з відповідальністю на рівні керівництва.
- **Технічні та організаційні заходи**, зокрема безпеку ланцюга постачання та багатофакторну автентифікацію.
- **Звітування про інциденти** щодо значних інцидентів: попереднє повідомлення протягом 24 годин після того, як стало відомо про інцидент, повідомлення про інцидент протягом 72 годин, заключний звіт не пізніше ніж через один місяць після повідомлення [41].

Компанії мають самостійно оцінити, чи підпадають вони під дію закону; BSI їх не повідомляє. Відомство пропонує необов'язкову онлайн-перевірку та рекомендує консультацію юриста у неочевидних випадках [41]. Інші держави-члени ЄС мають власні акти про впровадження з подібною структурою.

**Акт про кіберстійкість.** Якщо ви виготовляєте машини або продукти з цифровими елементами та розміщуєте їх на ринку ЄС, також діє **Акт про кіберстійкість (Регламент (ЄС) 2024/2847)**, зокрема для виробників зі США. Із 11 вересня 2026 року виробники мають повідомляти про вразливості, які активно експлуатуються, і серйозні інциденти через єдину платформу звітності ENISA: попереднє повідомлення протягом 24 годин, повідомлення протягом 72 годин і заключний звіт не пізніше ніж через 14 днів після появи виправлення для вразливостей або протягом одного місяця для інцидентів [30]. З 11 грудня 2027 року продукти мають відповідати основним вимогам кібербезпеки до розміщення на ринку; до них належать безпечні налаштування за замовчуванням, перелік компонентів програмного забезпечення (SBOM) і оновлення безпеки протягом заявленого періоду підтримки, як правило щонайменше п'ять років [42]. Для виробників машин, які постачають обладнання разом із хмарними сервісами, ІТ-інфраструктура виробництва стає питанням відповідності продукту.

Для архітектури Azure NIS2, CSF 2.0 і CMMC вказують в одному напрямку: інвентаризація (що підключено до хмари?), журналювання (хто, що і коли змінив?), прозорість ланцюга постачання (які сервіси та партнери задіяні?) і відпрацьований шлях звітування.

### Моніторинг OT після виведення з експлуатації Defender for IoT

2 листопада 2026 року Microsoft офіційно оголосила в Azure Updates, що повністю виведе з експлуатації компонент безпеки OT у Defender for IoT у жовтні 2029 року, після трирічного перехідного періоду [22]. До того часу сервіс отримує оновлення безпеки та виправлення помилок, але нових можливостей для OT не отримує; чинні угоди та поновлення діють до жовтня 2029 року [22]. Корпоративні можливості IoT у Defender for Endpoint, а також виявлення пристроїв і оцінка вразливостей не зачіпаються [22]. Власного рішення Microsoft для заміни немає [39]. Microsoft пропонує коннектори для Armis, Dragos і Forescout, які передають дані про активи OT та вразливості до Microsoft Security Exposure Management і порталу Defender; рішення партнерів потребують власних ліцензій і розгортання [22], [24].

Суперечливі дати: блог партнера Microsoft з листопада 2026 року називає **31 травня 2028 року** як кінець підтримки безпеки OT [39]. На момент написання не було з'ясовано, чи це інша дата для певних типів контрактів, чи помилка.

Рекомендація: якщо ви впроваджуєте моніторинг OT зараз, безпосередньо оцініть рішення партнерів. Якщо ви використовуєте Defender for IoT, сплануйте заміну так, щоб вона була завершена до середини 2028 року, і уточніть дату, що застосовується до вашого контракту, у своєї команди облікового запису Microsoft.

| Планово-попереджувальне технічне обслуговування | Інтервал за часом або лічильником | Години роботи, цикли |
| Технічне обслуговування за станом (моніторинг стану) | Перевищено поріг | Змінні стану (вібрація, температура, струм) |
| Предиктивне технічне обслуговування | Прогноз залишкового ресурсу або ймовірності відмови | Змінні стану плюс розмічена історія відмов плюс операційний контекст |
| Приписувальне технічне обслуговування | Рекомендована дія | Плюс знання про причини та дії |

Багато компаній отримують більшу частину вигоди лише від технічного обслуговування за станом. Предиктивні моделі окупаються тоді, коли відмови є дорогими, достатньо частими та фізично проявляються заздалегідь. [Total Productive Maintenance](https://www.m365.fm/entity/total-productive-maintenance/) задає загальну стратегію; її опори, автономне та планове технічне обслуговування, працюють і без ШІ.

### Передумови щодо даних

Перш ніж навчати модель, ви маєте вміти відповісти «так» на такі запитання:

1. **Чи є історія відмов?** Контрольованій моделі потрібні відмови з позначками часу та типами відмов. Зазвичай вони зберігаються в системі технічного обслуговування (наприклад, SAP PM або CMMS) і рідко кодуються чисто.
2. **Чи синхронізовані позначки часу?** Час датчика, час контролера та час проведення в ERP мають бути зіставними. Не випадково Microsoft додала спеціальні повідомлення про стан для відсутніх або недоступних серверів NTP до сенсорів Defender for IoT [23]; те саме стосується й вашого конвеєра даних. Конектор OPC UA передає вихідну позначку часу кожного значення [4]; використовуйте її, а не час надходження в хмару.
3. **Чи відповідає частота дискретизації типу відмови?** Пошкодження підшипника проявляється в спектрах вібрації в кілогерцовому діапазоні; знос нагрівальних стрічок проявляється у значеннях на рівні хвилин. Тег OPC UA з роздільною здатністю одна секунда достатній для першого, але не для другого.
4. **Чи доступний операційний контекст?** Без інформації про продукт, рецепт, замовлення та стан (переналагодження, виробництво, простій) модель сприйматиме кожну зміну продукту як аномалію.
5. **Чи визначено дію?** Хто реагує на попередження, з яким часовим запасом і як результат повертається назад?

### Шість кроків

1. **Вибір кандидатів:** Активи з високою вартістю відмов, повторюваними видами відмов та наявними датчиками. Аналіз Парето причин простоїв з MES дає вам перелік.
2. **Підключення даних:** Конектор OPC UA в Azure IoT Operations, точки даних для кожного активу, потік даних до Fabric [3], [4]. Агрегуйте високочастотні дані вібрації на периферії в ознаки (RMS, ексцес, енергії смуг).
3. **Спочатку моніторинг стану:** Порогові значення та прості методи виявлення аномалій в Eventhouse та Activator. Activator може безпосередньо повідомляти техніків [17]. Це дає результат за тижні, а не місяці, і одночасно збирає мітки.
4. **Створення міток:** Прив'яжіть заявки на технічне обслуговування з кодами відмов до часових рядів. Саме тут відбувається основна праця. Заплануйте для цього інструмент: Microsoft вивела з експлуатації вбудоване маркування даних в Azure Machine Learning 30 вересня 2026 року і вказує на сторонніх постачальників [38]. Для міток часових рядів з обслуговування часто достатньо Power App, який записує дані назад у систему технічного обслуговування.
5. **Навчання моделі:** У Fabric Data Science або Azure Machine Learning; зберігайте результати в OneLake [17]. Починайте з інтерпретованих методів (градієнтний бустинг на ознаках), перш ніж переходити до глибокого навчання.
6. **Впровадження в експлуатацію:** Надсилайте прогнози як події в процес технічного обслуговування (сповіщення в системі обслуговування, повідомлення в Teams, форма Power Apps для зворотного зв'язку). Відстежуйте якість моделі та дрейф.

### Показники успіху

Вимірюйте операційний вплив, а не точність моделі: незапланований простій, середній час між відмовами (MTBF), середній час ремонту (MTTR), частку планового обслуговування в загальних годинах обслуговування та запаси запчастин. Для цих [KPI](https://www.m365.fm/entity/key-performance-indicator/) потрібна базова лінія до початку проєкту; інакше неможливо довести будь-яку користь. Наш посібник з [виробничих KPI](https://www.m365.fm/en/learn/manufacturing-kpis/) містить визначення.

### Периферія чи хмара для інференсу?

| Критерій | Інференс у хмарі | Інференс на периферії |
|---|---|---|
| Затримка | Секунди до хвилин | Мілісекунди |

| Стійкість | Залежить від зв'язку | Працює офлайн |
| Типове застосування | Залишковий корисний термін, планування обслуговування | Швидке відключення, внутрішньолінійний контроль якості |

Для класичного предиктивного обслуговування інференсу в хмарі на агрегованих даних в більшості випадків достатньо. Починаючи з випуску 2603, Microsoft прямо позиціонує Azure IoT Operations для сценаріїв ШІ ближче до верстату («Physical AI») [6]; для інференсу на периферії перевірте актуальні примітки до випусків [7].

## Сценарій використання 2: Простежуваність і генеалогія

Простежуваність відповідає на питання «Де встановлено цю деталь і з чого вона зроблена?». Генеалогія описує повний ланцюжок походження виробу: матеріал, партія, технологічна операція, верстат, параметри, результат контролю та оператор. У регульованих галузях це обов'язково; в усіх інших випадках вона пришвидшує обробку рекламацій і звужує масштаб відкликань. Епізод [Traceability and Genealogy](https://www.m365.fm/show/episodes/traceability-and-genealogy/) детально розглядає цю тему.

### Вимоги за галузями

| Галузь / правило | Основна вимога до даних | Примітка |
|---|---|---|
| Харчова промисловість, FDA Food Traceability Rule (FSMA, розділ 204) | Ключові елементи даних (KDE) для кожної критичної події відстеження (CTE), наприклад приймання, переробка та відвантаження, пов'язані з кодом партії для простежуваності; записи надаються FDA протягом 24 годин після запиту, а під час спалахів або відкликань — також електронна таблиця з можливістю сортування | [59]; за директивою Конгресу FDA не застосовуватиме правило до 20 липня 2028 року (первинна дата — 20 січня 2026 року) |
| Медичні вироби, FDA QMSR (21 CFR Part 820) | З 2 лютого 2026 року Регламент системи управління якістю включає за посиланням ISO 13485:2016, зокрема його вимоги до ідентифікації та простежуваності | [61] |
| Електронні записи, що регулюються FDA, 21 CFR Part 11 | Захищені, створені комп'ютером, позначені часом журнали аудиту, які фіксують записи та зміни operatorів, не приховуючи попередні записи, зберігаються стільки ж, скільки самі записи | [60]; стосується фармацевтики, медичних виробів і харчових записів, які ведуться в електронному вигляді |
| Автомобілебудування, IATF 16949 | Розділ 8.5.2.1 доповнює вимоги ISO 9001 до ідентифікації та простежуваності (зокрема план простежуваності, заснований на аналізі ризиків); розділ 7.5.3.2.1 стосується зберігання певних записів, яке зазвичай тлумачиться як тривалість постачання виробничих і сервісних запчастин плюс один календарний рік, якщо клієнт або регулятор не вимагає інакше | Текст стандарту платний; подробиці з вторинних джерел. Специфічні вимоги клієнтів OEM (CSR) часто є суворішими |
| Аерокосмічна галузь, AS9100D (EN 9100 у Європі, JIS Q 9100 у Японії) | Простежуваність протягом життєвого циклу виробу, ідентифікація конфігурації, можливість відстежити вироби, виготовлені з тієї самої партії сировини або виробничої серії | AS9100D (2016) є чинною редакцією; EN 9100 — технічно еквівалентне європейське видання [62]. Посилання на пункт (8.5.2) не перевірене за оригінальним текстом стандарту |
| Батареї, що продаються в ЄС, Регламент ЄС про батареї (Регламент (ЄС) 2023/1542) | Електронний паспорт батареї з 18 лютого 2027 року для тягових батарей електромобілів, батарей легких транспортних засобів (наприклад, електровелосипедів, електросамокатів) і промислових батарей понад 2 кВт·год | [29]; терміни за даними Єврокомісії є орієнтовними; стосується американських експортерів до ЄС |
| Продукція, що продається в ЄС за Регламентом про екодизайн (ESPR, Регламент (ЄС) 2024/1781) | Цифровий паспорт продукту залежно від делегованого акта; реєстр DPP ЄС працює з 20 липня 2026 року (спершу з тестовим середовищем); делегований акт для заліза та сталі заплановано на четвертий квартал 2026 року, для текстилю, алюмінію та шин — на 2027 рік; щонайменше 18 місяців перехідного періоду після ухвалення делегованого акта | [29]; терміни за даними Єврокомісії є орієнтовними |

Для аерокосмічної галузі Mirko Peters пояснює у своєму дописі [Aerospace Production Planning: Lead Time and Traceability](https://www.m365.fm/community/u/mirko-p/blog/aerospace-production-planning-lead-time-traceability/), чому там тісно пов'язані терміни виконання та простежуваність; наш посібник з [планування аерокосмічного виробництва](https://www.m365.fm/en/learn/aerospace-production-planning/) охоплює контекст AS9100, FAA та експортного контролю.

### Модель даних генеалогії

Надійна генеалогія потребує трьох типів зв'язків:

1. **Матеріал у матеріалі:** Партія A і компонент B входять до складання C (посилання на BOM, серійний або партійний номер).
2. **Матеріал до процесу:** Складання C оброблено на операції 30 на станції 20 з набором параметрів X зміною Y.
3. **Процес до результату:** Операція 30 дала результат контролю Z і, за наявності, невідповідність.

Ці зв'язки утворюють граф. Його можна представити в Fabric як табличну структуру в Lakehouse і обходити за допомогою KQL або SQL, або змоделювати як граф у цифровому двійнику (онтологія Fabric або Azure Digital Twins) [14], [16]. Головне, що ідентифікація відбувається на джерелі: сканування, RFID або коди Data Matrix на станції, пов'язані з подією замовлення в UNS.

### Реалізація на Azure

- **Збирайте події на периферії:** Сканери та станції публікують повідомлення «деталь X почалася/завершилася на станції Y» до брокера MQTT Azure IoT Operations [3]. Параметри процесу надходять через конектор OPC UA [4]; «dataset triggering» дозволяє одній точці даних ініціювати публікацію інших, наприклад «цикл завершено» [4].
- **Зведіть контекст разом:** У Fabric події об'єднуються з даними замовлень і BOM з ERP та MES [17].
- **Забезпечте незмінність:** Регуляторні записи потребують незмінного сховища або принаймні журналу змін, стійкого до підроблення (для записів, регульованих FDA, вимога журналу аудиту Part 11 [60]). Політика незмінності OneLake наразі застосовується лише до діагностичних журналів, а не до бізнес-даних [43]. Для архівів простежуваності, стійких до аудиту, додайте Azure Blob Storage з політиками незмінного зберігання (WORM); Fabric залишається аналітичним шаром.
- **Забезпечте запити:** Типові запити: пряме простеження (які готові вироби містять партію A?) та зворотне простеження (з чого складається серійний номер S?). Звіт Power BI або Power App для контролю якості робить ці запити доступними без навичок KQL. Згідно з FSMA 204, можливість експортувати сортовану електронну таблицю протягом 24 годин [59] є конкретним критерієм приймання для цього шару.

### Від запису простежуваності до цифрового паспорта продукту

Цифровий паспорт продукту — це, по суті, зовнішньо доступний витяг з вашої генеалогії разом із даними про сталий розвиток і матеріали. Якщо ви створите чисту генеалогію сьогодні, ви виконаєте найскладнішу підготовчу роботу. Переконайтеся, що ідентифікатори унікальні та постійні, і що ви можете розділити, які дані є публічними, які призначені для регуляторів і які лише внутрішніми.

## Сценарій використання 3: Цифрові двійники

Термін [цифровий двійник](https://www.m365.fm/entity/digital-twin/) використовується для дуже різних речей: від 3D-моделі до імітаційної моделі чи живого відображення заводу. Для цілей архітектури корисно розрізняти їх. Наш посібник з [цифрових двійників у виробництві](https://www.m365.fm/en/learn/digital-twin-manufacturing/) виходить за межі погляду Azure.

### Три види двійників

| Вид | Питання | Дані | Інструменти в екосистемі Microsoft |
|---|---|---|---|
| **Інформаційний двійник** | Що де знаходиться і як це пов'язано? | Ієрархія активів, зв'язки, поточні стани | Fabric digital twin builder (попередня версія) [15], онтологія Fabric IQ (попередня версія) [16], Azure Digital Twins [14] |
| **Симуляційний двійник** | Що станеться, якщо …? | Логіка процесів, часи, потужності, поведінка при збоях | Промислові застосунки для моделювання матеріалопотоків і процесів, можливо на інфраструктурі Azure |
| **Інженерний двійник** | Як продукт або машина поводиться фізично? | CAD, CAE, логіка керування | PLM/CAE на Azure; Microsoft публікує рекомендації з архітектури для Siemens NX на Azure Virtual Desktop з GPU VM та Ansys Discovery на GPU VM, серед інших [2] |

[Віртуальне введення в експлуатацію](https://www.m365.fm/entity/virtual-commissioning/) з'єднує інженерного та симуляційного двійників: керуючий код тестується на моделі заводу до того, як з'явиться реальне обладнання.

### Azure Digital Twins чи Fabric?

Сама Microsoft зазначає, що digital twin builder у Fabric — це інший продукт, ніж Azure Digital Twins [14], [15]. Практичні відмінності:

| Критерій | Azure Digital Twins | Fabric digital twin builder |
|---|---|---|
| Статус | Активний, без повідомлення про виведення з експлуатації на сторінці огляду [14] | Попередня версія [15] |
| Моделювання | DTDL (Digital Twins Definition Language), версія 3 [14] | Онтологія з типами сутностей і зв'язками [15] |
| Зберігання | Власний граф двійників; історія через історію даних до Azure Data Explorer [14] | OneLake; дані спочатку мають бути в lakehouse Fabric [15] |
| Інтеграція | Маршрути подій до Event Hubs, Event Grid, Service Bus [14] | Нативна в Fabric Real-Time Intelligence, Power BI |
| Аудиторія | Команди розробників, орієнтовані на API | Команди з даних і бізнесу, low-code |
| Візуалізація | 3D Scenes Studio (попередня версія) [14] | Середовища Fabric, Power BI |

**Рекомендація:** Якщо ваша платформа даних — Fabric і вам потрібні аналітичні двійники для KPI та аналізу першопричин, стежте за digital twin builder та онтологією Fabric IQ і пілотуйте їх, але не робіть свою модель даних залежною від попереднього перегляду. Microsoft ще не задокументувала, як ці два компоненти Fabric розвиватимуться відносно один одного; онтологія вже пережила одну зміну досвіду з обов'язковою міграцією [16]. Якщо сьогодні ви будуєте виробничий застосунок двійника на основі API, Azure Digital Twins — це загальнодоступна служба. У будь-якому разі зберігайте копію вашої онтології у форматі, незалежному від інструментів.

### З чого почати?

Найпоширеніша помилка — почати з 3D-візуалізації. Почніть із запитання, на яке має відповідати двійник, наприклад: «Які замовлення постраждають, якщо станція 20 вийде з ладу?». Це запитання визначає сутності та зв'язки, які вам потрібні. Мірко Пітерс описує цей підхід у статті [Digital Twin in Manufacturing: Where to Start](https://www.m365.fm/community/u/mirko-p/blog/digital-twin-manufacturing-where-to-start/) та шлях від ERP до двійника цеху в статті [From ERP to Shop Floor: Building the Digital Twin](https://www.m365.fm/community/u/mirko-p/blog/erp-to-shop-floor-digital-twin/). Технічну реалізацію на Azure ми обговорюємо в епізоді [Digital Twins on Azure](https://www.m365.fm/show/episodes/digital-twins-on-azure/).

## Сценарій використання 4: KPI в реальному часі, OEE та потоки створення цінності

KPI в реальному часі часто є найшвидшим способом отримати цінність від підключення виробництва. Вони не потребують ШІ, але потребують чіткої моделі станів.

### Правильно розраховуйте OEE

Загальна ефективність обладнання (OEE) є добутком доступності, продуктивності та якості. Формула проста, а визначення — ні:

- **Доступність:** які простої вважаються плановими (перерви, планове обслуговування, відсутність замовлення)? Це рішення може змінити OEE на багато відсоткових пунктів.
- **Продуктивність:** який час циклу є еталонним: проєктне значення, найкращий досягнутий час циклу чи норматив з ERP?
- **Якість:** чи зараховується доопрацювання як придатна деталь чи як браковна?

Погодьте ці визначення між заводами до створення панелі моніторингу. Інакше заводи порівнюватимуть цифри, які не є співставними.

### Архітектура KPI в реальному часі

1. Стани обладнання та лічильники деталей надходять через OPC UA до брокера [4].
2. Потік даних відображає стани на єдину модель статусів (відповідність кодів конкретного обладнання) [3].
3. Eventhouse обчислює ковзні KPI за станцією, лінією та зміною за допомогою KQL.
4. Real-Time Dashboard обслуговує цех; звіти Power BI — для керівництва [17].
5. Activator надсилає сповіщення, коли значення падають нижче порогів [17].

### Потік створення цінності як жива модель даних

Картування потоку створення цінності традиційно є паперовою роботою. Якщо з'єднати процесні блоки потоку створення цінності з даними в реальному часі, отримуємо просту, але ефективну модель даних: час виконання, запаси між процесами, час циклу та вузькі місця стають вимірюваними. Епізод [Value Stream Mapping as a Live Data Model](https://www.m365.fm/show/episodes/value-stream-mapping-live-data-model/) показує, як це працює на практиці. Для детального планування на основі цих даних у гру вступають системи [розширеного планування та диспетчеризації](https://www.m365.fm/entity/advanced-planning-and-scheduling/); див. наш посібник із [виробничого планування та APS](https://www.m365.fm/en/learn/production-scheduling-aps/). Як ці цифри використовуються на щоденних зустрічах бригад, розглядається в нашому посібнику з [управління на виробничій дільниці](https://www.m365.fm/en/learn/shop-floor-management/).

### Стартовий каталог KPI

| KPI | Джерело даних | Деталізація |
|---|---|---|
| OEE та його фактори | Стан обладнання, лічильники, результати контролю якості | Станція, зміна |
| Час виконання | Події замовлень (початок/кінець за операцією) | Замовлення, продукт |
| Незавершене виробництво | Облікові проводки запасів, сканування | Буфер, лінія |
| Доставка в строк | ERP (запланована та фактична дата) | Клієнт, група продуктів |
| MTBF / MTTR | Простої, замовлення на обслуговування | Актив |
| Енергія на придатну деталь | Лічильники енергії, кількість деталей | Лінія, продукт |
| Вихід придатних з першого разу | Результати перевірок | Операція |

## Інтеграція ERP і MES

Дані з виробничої ділянки без контексту замовлень і матеріалів є вимірюваннями, а не інформацією. Інтеграція з ERP і MES визначає цінність усієї платформи.

### Яка система є системою запису?

| Об’єкт даних | Система запису (типова) | Роль платформи Azure |
|---|---|---|
| Матеріал, BOM, маршрут | ERP / PLM | Копія для збагачення, без супроводу |
| Виробниче замовлення (планування) | ERP / APS | Копія; зворотний зв’язок про статус як подія |
| Виконання операцій, підтвердження | MES | Події в UNS, історія у Fabric |
| Стани верстатів, значення процесу | Контролер / edge | Первинне джерело даних |
| Замовлення на обслуговування | ERP maintenance / CMMS | Запускаються прогнозами, історія для міток |
| Результати контролю якості | QMS / MES | Пов’язані з даними процесу |

### Інтеграція з SAP

Існує кілька способів передати дані SAP у Fabric: коннектори Data Factory, рішення відкритого дзеркалювання від партнерів і «SAP Business Data Cloud Connect for Microsoft Fabric», який має робити продукти даних SAP доступними в OneLake без копіювання; загальну доступність останнього було анонсовано на третій квартал 2026 року [44]. Фактичну загальну доступність на момент написання ми не змогли підтвердити [unverified: немає підтвердження з офіційного джерела]; перевірте поточний стан і вимоги до ліцензування на боці SAP, перш ніж планувати. Для інтеграції виробничої ділянки з SAP Digital Manufacturing DSAG (група користувачів SAP німецькомовних країн) опублікувала в квітні 2026 року посібник «SAP DM Shopfloor Integration»; його підсумкова сторінка доступна англійською мовою. За його вступом, він охоплює архітектуру, структури та моделі даних, масштабування, шаблони, операційну модель і закупівлі; повний текст доступний лише членам DSAG [48].基本 правило: підтвердження потрапляють у SAP через MES або визначені API, а не безпосередньо з платформи даних.

### Dynamics 365

Якщо ви використовуєте Dynamics 365 Supply Chain Management, ви отримуєте перевагу від його близькості до екосистеми Microsoft: за допомогою «Link to Microsoft Fabric» дані Dataverse, включно з вибраними таблицями фінансів і операцій, можна зробити доступними у Fabric без власного ETL-конвеєра [45]. Microsoft описує свою пропозицію для виробництва як поєднання можливостей Dynamics 365, Microsoft 365 і Azure [1].

### Наявні історизатори та SCADA

Багато заводів у США вже мають історизатор процесів поруч із SCADA. Розглядайте його як джерело, а не як щось, що потрібно замінити: історизатор і далі обслуговує операторів і інженерів процесів локально, а платформа Azure отримує або необроблені сигнали з рівня OPC UA, або курований набір даних з історизатора. Визначайте для кожного сигналу, який шлях є системою запису для історії, щоб не зберігати й не оплачувати один і той самий часовий ряд двічі, і уточнюйте у постачальника історизатора, які інтерфейси та ліцензії застосовуються, перш ніж проєктувати потік даних.

### Потік даних з виробничої ділянки до ERP

Типовий шаблон:

1. ERP випускає замовлення; подія «замовлення випущено» потрапляє в UNS.
2. MES починає операцію; подія «операцію розпочато» містить станцію та замовлення.
3. Дані верстатів збагачуються в потоці даних поточним номером замовлення.
4. MES підтверджує кількості та час; ERP проводить їх.
5. Fabric об’єднує всі події в повну історію замовлення для аналітики та генеалогії.

## ШІ та Copilot у виробництві

Генеративний ШІ прийшов у виробництво, але не так, як очікувалося у 2024 році. Microsoft у 2025 році припинила попередні версії агентів для виробництва (Factory Operations Agent, Factory Safety Agent) [2] і натомість покладається на загальні будівельні блоки платформи: Microsoft Foundry для агентів і моделей [20], Copilot in Fabric для запитань до даних [17], а також Copilot Studio і Microsoft 365 Copilot для робочих сценаріїв. На конференції Ignite 2025 з'явилися Fabric IQ і Foundry IQ у статусі попереднього перегляду; вони мають дати агентам семантичний шар і базу знань відповідно [34]. Погляд на життєвий цикл продуктів тут також застосовний: prompt flow, широко використовуваний інструмент для ранніх застосунків на основі LLM у Foundry та Azure Machine Learning, буде виведено з експлуатації 20 квітня 2027 року; Microsoft рекомендує перейти на Microsoft Agent Framework [37].

### Реалістичні сценарії

| Сценарій | Будівельні блоки | Передумова |
|---|---|---|
| Запитання природною мовою про виробничі дані («Чому лінія 3 вчора працювала повільніше?») | Copilot in Fabric, агенти даних Fabric, онтологія [16], [17] | Чиста модель даних, зрозумілі назви таблиць і стовпців, визначені KPI |
| Підсумки передач змін і звітів про інциденти | Microsoft 365 Copilot, Teams, Copilot Studio | Структуроване фіксування, наприклад у Power Apps або формах Teams |
| Асистент з технічного обслуговування (пошук у посібниках і історії відмов) | Microsoft Foundry з пошуком за документами, Copilot Studio | Документи в цифровому вигляді й актуальні, дозволи підтримуються |
| Візуальний контроль якості | Моделі комп'ютерного зору, висновування на периферійних пристроях | Розмічені зображення (сторонній інструмент розмітки, оскільки розмітка даних в Azure ML виведена з експлуатації [38]), стабільне освітлення |
| Асистент планування (порівняння сценаріїв) | Галузевий застосунок (APS, симуляція) плюс ШІ | Коректна модель планування |

### Microsoft 365 як міст до виробничого цеху

Для організацій, які вже використовують Microsoft 365, найбільший короткостроковий важіль часто лежить не в Azure, а в з'єднанні подій цеху з робочим середовищем:

- **Teams для працівників першої лінії:** Комунікація змін, завдання, сповіщення від Activator або Power Automate безпосередньо в Teams [17].
- **Power BI:** Звіти KPI для керівництва й керівників заводу, побудовані на тих самих даних Fabric.
- **Power Apps:** Фіксація причин простоїв, результатів контролю якості та зворотного зв'язку від технічного обслуговування на планшетах біля робочого місця. Це створює саме ті мітки, які потрібні для предиктивного обслуговування.
- **Copilot:** Підсумки звітів змін, аналіз відхилень і нотатки нарад від керівників цеху.
- **Завчасно розберіться з ліцензуванням:** Працівники цеху зазвичай отримують ліцензії для працівників першої лінії (Microsoft 365 F1 або F3). Перед впровадженням перевірте, які можливості, наприклад Power Apps або Copilot, вони включають і які додаткові ліцензії потрібні; інакше вдалий пілотний проєкт застрягне під час масштабування.

### Обмеження та управління

- **Жодних керуючих рішень від мовних моделей.** Мовні моделі належать до допоміжних засобів, а не до замкненого контуру керування машиною.
- **Використовуйте систему управління ризиками.** **NIST AI Risk Management Framework (AI RMF 1.0)**, випущена 26 січня 2023 року, є добровільною системою, організованою навколо чотирьох функцій: Govern, Map, Measure і Manage [63]. Це практичний спосіб документувати ризики ШІ в контролі якості або плануванні для замовників і аудиторів.
- **Закон ЄС про ШІ для операцій в ЄС:** Якщо ви експлуатуєте системи ШІ на заводах у ЄС або продаєте там продукти з ШІ, перевірте, чи використовується система як компонент безпеки продукту або для управління працівниками; можуть виникнути обов'язки для систем високого ризику. «Digital Omnibus on AI» (Регламент (ЄС) 2026/1744, чинний з кінця липня 2026 року) відклав ці строки: до 2 грудня 2027 року для окремих систем високого ризику (наприклад, у HR) і до 2 серпня 2028 року для систем, вбудованих у продукти. ШІ в машинах має регулюватися делегованими актами згідно з Регламентом ЄС про машини [46]. Класифікація вашої конкретної системи потребує юридичної експертизи.
- **Персонал і трудові відносини:** Системи, які можуть оцінювати результативність або поведінку працівників, породжують трудові питання. На заводах у США з профспілками перевірте, чи охоплює колективний договір моніторинг результативності; на заводах у Німеччині такі системи, як правило, потребують згоди ради працівників (Betriebsrat), яка має права співвизначення. У будь-якому разі залучайте представників працівників на ранньому етапі.
- **Дозволи:** Copilot показує те, що користувачеві дозволено бачити. Надмірно широкий доступ у SharePoint або Fabric стає видимим через ШІ.

## FinOps для ІТ у виробництві

Хмарні витрати у виробництві поводяться інакше, ніж у класичних ІТ-навантаженнях: обсяги даних зростають із кожною під'єднаною машиною, навантаження працюють цілодобово, а частина інфраструктури розміщена на заводі. FinOps допомагає зробити ці витрати передбачуваними та пов'язати їх із цінністю. Епізод [FinOps for Manufacturing IT](https://www.m365.fm/show/episodes/finops-for-manufacturing-it/) розглядає специфіку галузі.

### Коротко про фреймворк FinOps

Рекомендації Microsoft щодо FinOps базуються на фреймворку FinOps Foundation [25]. Він складається з шести принципів (серед них «Команди мають співпрацювати», «Бізнес-цінність визначає технологічні рішення» та «Використовуйте змінну модель витрат хмари»), трьох фаз життєвого циклу (Inform, Optimize, Operate) і чотирьох доменів [25]:

| Домен | Що це означає для виробництва |
|---|---|
| Розуміння використання та витрат | Зробити видимими витрати за заводом, лінією та сценарієм використання (тегування, окремі ємності або робочі простори Fabric) |
| Кількісна оцінка бізнес-цінності | Вартість на одну придатну деталь, на одну під'єднану машину або на одну годину уникнутого простою |
| Оптимізація використання та витрат | Зменшення обсягу даних на периферії, багаторівневе зберігання історичних даних, точне підбирання розмірів ємностей |
| Управління практикою FinOps | Відповідальність, політики, перенесення витрат на заводи |

Фреймворк рекомендує оцінювати зрілість окремо за кожною спроможністю, а не загалом, і переглядати її кожні три-шість місяців [25].

### Десять найважливіших важелів витрат

1. **Агрегуйте на периферії:** Не кожне значення з роздільною здатністю в одну секунду має потрапляти в хмару. Потоки даних можуть фільтрувати та агрегувати дані [3]. Це найсильніший окремий важіль.
2. **Надсилайте за зміною:** За замовчуванням конектор OPC UA надсилає лише змінені значення та додає періодичні ключові кадри з усіма значеннями, щоб споживачі могли відновити стан [4]. Також перевірте мертві зони в контролері або сервері OPC UA, щоб шум не зараховувався як зміна.
3. **Консолідуйте Eventstreams:** На кожен завод, а не на кожне джерело, з трансформаціями в Eventhouse [31].
4. **Багаторівневе зберігання:** Гарячі дані в кеші Eventhouse протягом днів або тижнів, старіші дані в сховищі OneLake.
5. **Свідомо підбирайте розмір ємності Fabric:** Відстежуйте використання за допомогою застосунку Capacity Metrics, розділяйте робочі навантаження розробки та продуктивного середовища, призупиняйте ємності, які вам не потрібні. Призупинення задокументовано для SKU серії F; під час призупинення накопичені перевитрати одразу виставляються до оплати, а вміст ємності стає недоступним [47]. Ємність, яка обслуговує Eventstream або дашборд заводу, тому не є кандидатом на призупинення.
6. **Оберіть правильний SKU для периферії:** Починаючи з релізу 2610, Azure IoT Operations пропонує дешевший SKU Essentials для розгортань з великими обсягами даних поряд зі Standard; він обмежений одновузловими кластерами та не містить конектора OPC UA [3]. Наприклад, він підходить для майданчиків, чиї дані вже надходять через MQTT або HTTP. Для кожного майданчика перевірте, які функції вам справді потрібні.
7. **Використовуйте резервування та плани заощаджень** для ресурсів Azure, що працюють безперервно.
8. **Розподіляйте витрати:** Забезпечуйте теги для заводу, центру витрат і сценарію використання (Azure Policy).
9. **Запровадьте юніт-економіку:** Звітуйте про вартість хмари на одиницю продукції або на одну під'єднану машину. Лише так можна порівнювати заводи.
10. **Виведіть з експлуатації застарілі рішення:** Мігруйте сервіси, що знімаються з підтримки (IoT Central, IoT Edge 1.5), доки паралельні структури не подвоїли ваші витрати.

### Не забувайте про витрати на периферії

Апаратне забезпечення заводу, експлуатація Kubernetes, ліцензії на сервіси, увімкнені через Azure Arc, і персонал для оновлень належать до того самого розрахунку. Бізнес-обґрунтування, яке розглядає лише рахунок Azure, систематично недооцінює повну вартість. Цей посібник навмисно не наводить цін, адже вони часто змінюються; актуальні моделі ціноутворення для Azure IoT Operations (Standard та Essentials), Azure Arc і Azure Local ви знайдете на сторінках цін Azure та в калькуляторі цін Azure.

## Побудова бізнес-обґрунтування для Azure у виробництві

Загальні твердження про вигоду з галузевих досліджень рідко допомагають отримати затвердження бюджету, оскільки вони не враховують вашу вихідну точку. Надійнішою є логіка розрахунку, яку ви заповнюєте власними цифрами.

### Категорії вигод

| Категорія | Розрахунок | Джерело даних |
|---|---|---|
| Уникнені незапланові простої | Години простою × маржинальний внесок за годину × очікуване скорочення | Історія простоїв MES, фінанси |
| Вищий OEE | Додаткові придатні деталі × маржинальний внесок на деталь | Базовий рівень OEE |
| Нижчі витрати на брак і доробку | Кількість браку × виробнича собівартість × скорочення | QMS |
| Швидша обробка рекламацій | Години на рекламацію × погодинна ставка × скорочення; менший обсяг відкликання | Історія рекламацій |
| Витрати на технічне обслуговування | Запаси запчастин, послуги підрядників, понаднормові | ERP, технічне обслуговування |
| Відповідність вимогам | Уникнені зусилля з ручного збирання доказів (аудити, запити FSMA 204, оцінки CMMC, DPP) | Команда якості та відповідності |

### Категорії витрат

- Периферійне обладнання та експлуатація на кожному заводі
- Споживання Azure та Fabric (постійно)
- Ліцензії (Power BI, Copilot, галузеві застосунки, безпека OT там, де потрібно)
- Впровадження (внутрішнє та зовнішнє)
- Управління змінами та навчання
- Модернізація старіших верстатів датчиками

### Розрахунковий приклад з вигаданими цифрами

Лінія має 120 годин незапланованих простоїв на рік, а маржинальний внесок становить 1 600 доларів США за годину. Якщо моніторинг стану та швидше реагування дозволять уникнути 20 відсотків цих годин, це 24 години × 1 600 доларів США = 38 400 доларів США на рік. Проти цього стоять розподілені витрати: периферійне обладнання та експлуатація, споживання Fabric, ліцензії та внутрішні години. Цифри навмисно прості. Важливо, що кожне припущення має джерело всередині вашої компанії (історія MES, фінанси), а скорочення вимірюється відносно базового рівня через три-шість місяців.

### Практичне правило для визначення пріоритетів

Починайте з варіанта використання, де збігаються три умови: вимірюваний базовий рівень, наявні дані та власник процесу, який хоче використовувати результати. Частіше це оперативний OEE в реальному часі або простежуваність, а не прогнозоване технічне обслуговування.

## Дорожня карта: п'ять етапів до масштабованої платформи Azure для виробництва

Наведена нижче дорожня карта відповідає поширеному підходу «спочатку фундамент і один піlotний варіант використання, потім масштабування». Тривалість є орієнтовною для першого заводу і значною мірою залежить від вашої вихідної точки, погоджень мережі та ресурсів.

### Етап 1: Чіткість (від 4 до 8 тижнів)

- Портфель варіантів використання з оцінками вигод; вибір одного-двох піlotних варіантів
- Поточний стан: парк верстатів, протоколи (чи доступний OPC UA?), мережа, наявні системи
- Цільова модель даних (ієрархія ISA-95, конвенція тем UNS)
- Концепція безпеки, що охоплює безпеку OT, профіль CSF 2.0, область CMMC там, де це актуально, конфіденційність і представників працівників
- Перевірка життєвого циклу всіх сервісів за таблицею статусів цього посібника

### Етап 2: Фундамент (від 6 до 12 тижнів)

- Периферійна інфраструктура на пілотному заводі, підключення Arc, Azure IoT Operations
- Структура робочих просторів Fabric, планування потужностей, модель доступу
- Перші верстати, підключені через OPC UA, активи в Azure Device Registry
- Основи FinOps: теги, бюджети, звіти про витрати для кожного заводу

### Етап 3: Перша цінність (від 8 до 12 тижнів)

- Піlotний варіант використання у виробництві, наприклад оперативний OEE в реальному часі із фіксацією причин простоїв у Power App
- Інформаційна панель на виробничій ділянці та управлінський звіт
- Базовий рівень і перше вимірювання впливу

### Етап 4: Поглиблення (від 3 до 6 місяців)

- Інтеграція контексту ERP і MES, історія замовлень і генеалогія
- Моніторинг стану, збирання міток для прогнозованого технічного обслуговування
- Перші сценарії Copilot на куратованих даних

### Етап 5: Масштабування (від 9 до 15 місяця, залежно від прогресу)

- Розгортання на більшій кількості ліній і заводів з інфраструктурою як кодом і GitOps
- Наскрізні KPI для всіх заводів з однаковими визначеннями
- Прогнозоване технічне обслуговування для вибраних активів, сценарії цифрових двійників
- Операційна модель: команда платформи, власники продуктів даних для кожного домену, управління релізами для зазвичай щомісячних релізів Azure IoT Operations [7]

Ключовий зсув полягає у переході від доказу концепції до мінімально життєздатного продукту: PoC доводить, що технологія працює. MVP доводить, що з нею люди працюють краще. Якщо ви хочете закріпити цей перехід у ширшій програмі вдосконалення, перегляньте наші посібники з [ощадливого виробництва](https://www.m365.fm/en/learn/lean-manufacturing/) та [операційної досконалості](https://www.m365.fm/en/learn/operational-excellence/).

## Поширені помилки в проєктах Azure для виробництва

1. **Технологія раніше за питання:** побудова платформи без бізнес-підрозділу, який хоче розв'язати конкретну проблему.
2. **Preview як фундамент:** розміщення бізнес-логіки на сервісах у попередньому перегляді. Виведення з експлуатації Manufacturing data solutions і factory agents показує цей ризик [2].
3. **Застарілі будівельні блоки зі старих гайдів:** планування нових проєктів на IoT Central, Time Series Insights або IoT Edge 1.5 лише тому, що статтю 2021 року рекомендують [8], [10], [12].
4. **Неправильний SKU:** планування Azure IoT Operations Essentials для заводу з верстатами OPC UA, хоча цей SKU не містить коннектора OPC UA [3].
5. **Відсутня модель станів:** перенесення специфічних для верстатів кодів статусів без фільтрації. Порівняння заводів стає неможливим.
6. **Усе в хмару:** надсилання сирих даних у повній роздільній здатності та здивування від рахунку.
7. **Безпека OT як другорядне питання:** розміщення кластера edge у мережі без концепції зон і залишення відкритим доступу на запис до контролерів.
8. **Забуті мітки:** запуск предиктивного обслуговування без структурованої історії відмов.
9. **KPI без визначень:** побудова панелей OEE до того, як заводи погодять визначення доступності.
10. **Недооцінка експлуатації:** регулярні релізи, оновлення Kubernetes, ротація сертифікатів і буфер брокера, який можна налаштувати лише під час початкового розгортання [40], і без відповідальної особи.
11. **Залишення людей осторонь:** працівники виробничої дільниці дізнаються про проєкт тоді, коли планшет установлюють на їхньому робочому місці.
12. **Ігнорування обсягу відповідності:** передача креслень або специфікацій для оборонних деталей у спільний робочий простір Fabric без рішення щодо визначення обсягу CMMC.

## FAQ

### Що таке Azure для виробництва?

Azure для виробництва — це набір хмарних і edge-сервісів Microsoft, які виробники використовують для підключення заводів, зберігання та аналізу виробничих даних і створення AI-застосунків та застосунків для робочого місця на цій основі. У 2026 році основу становлять Azure IoT Operations на Arc-enabled Kubernetes на заводі, Microsoft Fabric як платформа даних, а також Foundry, Power BI і Copilot для аналітики та AI [3], [17]. Microsoft подає галузеву пропозицію як "Microsoft for Manufacturing", яка поєднує Azure, Dynamics 365 та Microsoft 365 [1].

### У чому різниця між Azure IoT Hub і Azure IoT Operations?

IoT Hub — це хмарний сервіс, до якого окремі пристрої підключаються безпосередньо. Azure IoT Operations — це рівень даних, що працює на заводі на Arc-enabled Kubernetes і через OPC UA та інші конектори підключає верстати до локального MQTT-брокера [3]. Для заводів із багатьма верстатами Azure IoT Operations зазвичай є правильною відправною точкою; IoT Hub підходить для розподілених, безпосередньо підключених пристроїв. Компроміси між IoT Edge і Azure IoT Operations розглянуто тут: [Azure IoT Edge vs Azure IoT Operations: Choosing the Right Industrial Architecture](https://www.m365.fm/community/u/mirko-p/blog/azure-iot-edge-vs-azure-iot-operations/).

### Чи виводиться з експлуатації Azure IoT Central?

Так. З 23 вересня 2026 року створювати нові застосунки IoT Central неможливо; наявні застосунки працюватимуть до 20 вересня 2029 року. Microsoft рекомендує як цільову архітектуру IoT Hub з Device Provisioning Service, Azure Device Registry і Microsoft Fabric; дашборди й аналітика переходять до Fabric Real-Time Intelligence [8], [64]. Повідомлення про виведення з експлуатації на 31 березня 2027 року, яке з'явилося в порталі Azure у лютому 2024 року, Microsoft тоді відкликала як помилкове системне повідомлення [9]. Оголошення 2026 року, навпаки, є звичайним повідомленням із трирічним періодом переходу.

### Чим замінено Azure Time Series Insights?

Time Series Insights було виведено з експлуатації 7 липня 2024 року. Microsoft називає ціллю міграції Eventhouse у Microsoft Fabric Real-Time Intelligence [10]. Якщо Fabric не використовується, альтернативою є Azure Data Explorer, який також працює з KQL [19].

### Що сталося з Microsoft Cloud for Manufacturing?

Галузева пропозиція тепер називається "Microsoft for Manufacturing" і об'єднує можливості Azure, Dynamics 365 та Microsoft 365 [1]. Окремі попередні версії "Manufacturing data solutions" і "Factory Operations Agent" було виведено з експлуатації 30 травня 2025 року, а "Factory Safety Agent" — 23 червня 2025 року [2]. Окремого повідомлення про "Manufacturing data solutions in Microsoft Fabric" немає; не закладайте це в нові проєкти.

### Які сервіси Azure потрібні для розумного заводу?

Для типового підключення заводу: Azure Arc і кластер Kubernetes на заводі, поверх них Azure IoT Operations (брокер, конектор OPC UA, потоки даних), Azure Device Registry для активів, Microsoft Fabric з Eventstream, Eventhouse і Activator для даних у реальному часі та Power BI для звітності [3], [17]. Будівельні блоки AI (Fabric Data Science, Azure Machine Learning, Microsoft Foundry) і цифрові двійники додаються пізніше. Рамку формують Entra ID, Azure Policy, Cost Management і рішення для безпеки OT.

### У чому різниця між Azure IoT Operations Essentials і Standard?

Standard пропонує повний набір функцій. Essentials, доступний із релізу 2610, — це дешевший варіант для великих розгортань; він працює лише на одновузлових кластерах і не включає конектор OPC UA [3]. Для заводів з верстатами OPC UA відправною точкою є Standard.

### Чи потрібні навички Kubernetes для Azure IoT Operations?

Так, принаймні для експлуатації. Azure IoT Operations працює на кластерах Arc-enabled Kubernetes і налаштовується у стилі Kubernetes [3]. Для початку Microsoft документує встановлення на Ubuntu і на Windows з AKS Edge Essentials [3]. Плануйте розвиток навичок або залучення партнера з експлуатації.

### Чи продовжується виробництво, якщо інтернет-з'єднання зникає?

За даними Microsoft, Azure IoT Operations може працювати офлайн максимум 72 години, можливо з деградацією, і відновлює повну функціональність після повторного підключення [3]. Скільки повідомлень буферизується за цей час, залежить від конфігурації брокера, яка задається під час початкового розгортання [40]. Функції керування ніколи не повинні залежати від хмари; керування залишається в ПЛК і локальних системах.

### Azure Digital Twins чи digital twin builder у Fabric?

Azure Digital Twins є загальнодоступною службою з моделями DTDL та доступом через API [14]. Digital twin builder входить до складу Fabric Real-Time Intelligence, працює з онтологіями на даних OneLake і перебуває в попередньому перегляді [15]. Для продуктивних, розроблених розробниками двійників безпечним вибором сьогодні є Azure Digital Twins; для аналітичних двійників на платформі Fabric варто провести пілотний проєкт із digital twin builder. Mirko Peters пояснює пов'язане розрізнення між device twin у IoT Hub і Azure Digital Twins в статті [Device Twin vs Azure Digital Twins: Choosing the Right Layer for Industrial IoT](https://www.m365.fm/community/u/mirko-p/blog/device-twin-vs-azure-digital-twins/).

### Які дані потрібні для предиктивного обслуговування?

Змінні стану з відповідною частотою дискретизації, синхронізовані мітки часу, експлуатаційний контекст (замовлення, продукт, стан верстата) і, понад усе, маркована історія відмов із служби технічного обслуговування. Без історії відмов спочатку можливе лише виявлення аномалій.

### Що означає виведення з експлуатації Defender for IoT для безпеки ОТ?

2 листопада 2026 року Microsoft офіційно оголосила, що повністю виведе з експлуатації компонент безпеки ОТ у Defender for IoT у жовтні 2029 року; до того часу передбачені лише оновлення безпеки та виправлення помилок [22]. Партнерський блог Microsoft натомість називає датою завершення підтримки 31 травня 2028 року [39]. Власного замінника від Microsoft немає; компанія пропонує конектори для Armis, Dragos і Forescout, рішення яких ліцензуються окремо [22]. Плануйте заміну так, щоб вона була завершена до середини 2028 року.

### Чи варто і надалі використовувати IoT Edge?

IoT Edge як продукт і досі підтримується. Версія 1.5 LTS досягла кінця підтримки 10 листопада 2026 року; поточна версія 1.6 LTS підтримується до 14 листопада 2028 року [12]. Для наявних парків Linux-пристроїв прямим шляхом є оновлення до 1.6. Для Windows-пристроїв на EFLOW 1.5 на сторінці версій немає EFLOW 1.6 LTS; уточніть цільовий шлях там. Для нових шарів даних на заводі розгляньте Azure IoT Operations.

### Чи відповідає Azure вимогам CMMC?

Сертифікації CMMC для самого Azure немає, оскільки CMMC стосується систем підрядника, а не хмарної платформи [55]. Microsoft стверджує, що Azure і Azure Government мають авторизації FedRAMP High, що охоплюють NIST SP 800-171, що ви можете отримати сертифікацію CMMC для рішень в obох хмарах і що більшість оборонних підрядників найкраще відповідають Azure Government [55]. Правило DFARS, яке вносить вимоги CMMC до контрактів DoD, поетапно впроваджується з 10 листопада 2025 року [54].

### Яку систему безпеки має використовувати американський виробник для Azure і ОТ?

Використовуйте їх разом. NIST CSF 2.0 дає структуру управління та спільну мову з керівництвом, страховиками і клієнтами [49]; ISA/IEC 62443 дає технічну модель для ОТ (зони, канали, рівні безпеки) [27]; NIST SP 800-82 Rev. 3 поєднує їх за допомогою рекомендацій, специфічних для ОТ, і накладок на заходи контролю [50]. Додайте CMMC, якщо ви працюєте з FCI або CUI для DoD [53], і NIS2 для підприємств у ЄС [41].

### Скільки коштує Azure для виробництва?

Надійної загальної цифри немає. Витрати залежать від кількості заводів і верстатів, обсягу даних, термінів зберігання, обраної ємності Fabric, периферійного обладнання та ліцензій. Найбільший важіль — агрегування даних на периферії. Скористайтеся калькулятором цін Azure і впроваджуйте практики FinOps починаючи з другої фази [25].

### Яку роль відіграє Microsoft 365 у виробництві?

Microsoft 365 є робочим шаром: Teams для комунікації змін і сповіщень, Power BI для KPI, Power Apps для збору даних на робочому місці та Copilot для підсумків і запитань щодо даних. Для компаній з усталеним середовищем Microsoft 365 це зв'язування часто є найшвидшим способом зробити дані з виробничого цеху придатними до використання.

### З чого почати, якщо ви адміністратор Microsoft 365 або Azure?

З завдань, які й так належать центральному ІТ: ролі Entra ID для співробітників ОТ і партнерів, посадкова зона Azure з політиками тегів для кожного заводу, тестовий кластер Arc, включно з погодженням брандмауерів через ланцюг проксі, і структура робочих просторів Fabric. Паралельно зустріньтеся з керівником ОТ, щоб зрозуміти модель зон заводу. Докладніше — у розділі «З чого почати, якщо ви адміністратор Microsoft 365 або Azure» на початку цього посібника.

## Висновок

Azure для виробництва у 2026 році стосується меншою мірою вибору сервісів, а більшою — дисципліни. Технічна основа зрозуміла: Azure IoT Operations on Arc на заводі, Microsoft Fabric як платформа даних, а Foundry, Power BI та Copilot — для аналітики і робочого місця. Водночас виведення з експлуатації Time Series Insights і виробничих попередніх версій, а також запланований вивід з експлуатації IoT Central і безпеки OT у Defender for IoT показують, що управління життєвим циклом є частиною роботи над архітектурою.

Три речі роблять різницю: власна незалежна від інструментів модель даних на основі ISA-95, проєкт безпеки на основі ISA/IEC 62443 і NIST CSF 2.0, який також охоплює CMMC або NIS2 там, де вони застосовні, а також послідовна увага до сценаріїв використання з виміряною базовою лінією. Якщо працювати так, ви створите платформу, яка обслуговує профілактичне обслуговування, простежуваність, цифрові двійники та ШІ на одній основі даних і яка переживе наступне перейменування Microsoft.
