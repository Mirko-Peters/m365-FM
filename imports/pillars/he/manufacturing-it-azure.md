# Azure לייצור: המדריך המלא ל-IT ייצורי על Microsoft Azure (נובמבר 2026)

**תשובה קצרה:** בסוף 2026, Azure לייצור מתמצה בשלוש שכבות: Azure IoT Operations על Kubernetes מופעל ב-Azure Arc במפעל, Microsoft Fabric (Real-Time Intelligence ו-OneLake) כפלטפורמת הנתונים, ו-Microsoft Foundry, Power BI ו-Copilot לניתוח, לבינה מלאכותית ולעבודה השוטפת. אבני הבניין הישנות יצאו משימוש (Time Series Insights וסוכני הייצור בתצוגה מקדימה) או מתוכננות לפרישה (IoT Central ב-2029, אבטחת OT ב-Defender for IoT). ההצלחה תלויה פחות בשירותים ויותר בכך שתחזיקו במודל הנתונים שלכם, בתכנון אבטחת OT המיושר עם ISA/IEC 62443 והנחיות NIST, ובבחירת מקרי שימוש עם בסיס מדוד.

**עיקרי הדברים**

- תכננו חיבורים חדשים של מפעל על **Azure IoT Operations**, ולא על IoT Central או על שרשראות מודולי IoT Edge שנבנו ביד. בחרו ב-SKU **Standard** אם המכונות שלכם מדברות OPC UA; מנוי Essentials אינו כולל את מחבר OPC UA.
- השתמשו ב-**Microsoft Fabric Real-Time Intelligence** (Eventstream, Eventhouse, Activator) לנתוני סדרות עיתיות. Time Series Insights יצא משימוש ב-7 ביולי 2024.
- שמרו את הלוגיקה העסקית הרחק משירותים בתצוגה מקדימה. Microsoft הפסיקה את תצוגות המקדימה של מודל הנתונים הייצורי ושל סוכן המפעל ב-2025, כשנה לאחר ההשקה.
- תכננו עכשיו את ההחלפה של **ניטור OT**. Microsoft תפרוש לחלוטין את אבטחת OT ב-Defender for IoT באוקטובר 2029; בלוג של שותף של Microsoft מצוין 31 במאי 2028 כתאריך סיום התמיכה.
- מפו את תוכנית האבטחה שלכם ל-**ISA/IEC 62443** (אזורים ותעלות תקשורת) ול-**NIST CSF 2.0**; ספקי הגנה צריכים גם **CMMC** למערכות שמטפלות ב-FCI או ב-CUI.
- התחילו ממקרי שימוש שיש להם בסיס ובעלים: OEE בזמן אמת ומעקב אחר מוצרים (traceability) בדרך כלל מניבים תשואה לפני תחזוקה חזויה.

## מה Azure עבור הייצור משמעו כיום

לפני חמש שנים, חיפוש של "Azure for manufacturing" או "Azure IoT for manufacturing" החזיר רשימה מוכרת: IoT Hub, IoT Edge, Stream Analytics, Time Series Insights ו-Synapse. הרשימה הזו כבר אינה מתארת את המצב ב-2026. מיקרוסופט בנתה מחדש את אסטרטגיית ה-IoT התעשייתי שלה בשלושה כיוונים:

1. **Edge במקום התקן:** איסוף הנתונים במפעל פועל כעת על **Azure IoT Operations**, קבוצת שירותי נתונים על אשכולות Kubernetes הנשלטים מהענן באמצעות **Azure Arc**. מיקרוסופט מתארת את השירות כ"מישור נתונים מאוחד לקצה" [3]. הזמינות הכללית הוכרזה בנובמבר 2024 [5].
2. **פלטפורמת נתונים במקום שירותי נקודה:** סדרות זמן, אירועים ונתוני מאסטר נכנסים ל-**Microsoft Fabric**, בפרט ל-Real-Time Intelligence עם Eventstream, Eventhouse ו-Activator. מיקרוסופט הפסיקה את Time Series Insights והפנתה את הלקוחות ל-Fabric Eventhouse כיעד המעבר [10].
3. **פלטפורמה במקום יישום ארוז:** ב-IoT ובייצור, מיקרוסופט נסוגה מהיישומים המוגדרים מראש שלה. IoT Central הפסיק לקבל יישומים חדשים ב-23 בספטמבר 2026 ותוצא משימוש ב-20 בספטמבר 2029 [8], [64]. התצוגות המקדימות הספציפיות לתעשייה "Manufacturing data solutions" ו-"Factory Operations Agent" הוצאו משימוש ב-30 במאי 2025 [2].

ההצעה התעשייתית נקראת כעת **Microsoft for Manufacturing** (לשעבר "Microsoft Cloud for Manufacturing"). מיקרוסופט מארגנת אותה בארבעה תחומי פתרונות: הנדסה דיגיטלית, שרשראות אספקה עמידות, מפעלים חכמים ולקוחות מחוברים [1]. עבור המפעל החכם, מיקרוסופט מציינת ארבעה תרחישים: מודרניזציה של הקצה והתשתית, אופטימיזציה של התפעול בעזרת AI, חיבור העובדים והעצמתם, ותחזוקה ואיכות [1]. מיקרוסופט מצביעה על Fabric כפלטפורמה ל"חוט הדיגיטלי" [1].

עבורך כמנהל IT, OT או טרנספורמציה דיגיטלית, משמעות הדבר היא שאבני הבניין הפכו לכלליות יותר, ולחלק גדול יותר מהאחריות על מודל הנתונים, האינטגרציה והתפעול יש אתך או עם השותפים שלך. מדריך זה מראה כיצד לשאת באחריות הזו בצורה מובנית. הוא מקשר בין הטכנולוגיה של Azure לנושאים שמכריעים את ההצלחה: מודל הנתונים, אבטחה, [Industry 4.0](https://www.m365.fm/entity/industry-4-0/) כנושא ארגוני, KPI ועלות.

### למי מיועד המדריך

- **מנהלי IT וצוותי ענן** שכבר מפעילים Microsoft 365 ו-Azure ונדרשו לחבר את המפעלים.
- **מהנדסי OT ואוטומציה** שרוצים להבין מה Kubernetes, MQTT ו-Fabric משמעם עבור הציוד שלהם.
- **מנהלי מפעל, איכות ותחזוקה** שמעריכים מקרי שימוש כגון תחזוקה חזויה או מעקב אחר מוצרים.
- **צוותי כספים ורכש** שצריכים להפוך את עלויות הענן בייצור לצפויות.

### מונחי ייצור למנהלי Microsoft 365 ו-Azure

אם אתם מגיעים מ-IT ארגוני, פרויקטים בייצור מביאים עמם אוצר מילים משלהם. להלן המונחים המרכזיים המשמשים במדריך זה, כל אחד במשפט אחד:

| מונח | משמעות | האנלוגיה הקרובה ביותר מעולם ה-IT |
|---|---|---|
| **OT** (טכנולוגיית תפעול, operational technology) | טכנולוגיה השולטת בתהליכים פיזיים: מכונות, בקרים ומערכות בקרה | כמו מרכז נתונים נפרד שבו השבתה עוצרת את הייצור |
| **PLC** (בקר לוגי programmable, programmable logic controller) | מחשב תעשייתי השולט במכונה בזמן אמת | מערכת משובצת (embedded) עם אורך חיים של 15 שנים ומעלה |
| **SCADA** | מערכת פיקוח להשגחה והפעלה של מספר מכונות או קווים | קונסולת ניטור עם הרשאת כתיבה |
| **MES** (מערכת ביצוע ייצור, manufacturing execution system) | שולטת ומתעדת את ביצוע הזמנות הייצור במפעל | מערכת זרימת עבודה בין ה-ERP למכונה |
| **OPC UA** | תקן תעשייתי נייטרלי מבחינת ספקים להחלפת נתונים, עם מודל מידע ואבטחה מובנית | REST API בתוספת סכמה ותעודות, עבור מכונות |
| **MQTT** | פרוטוקול קל משקל מסוג פרסום/הרשמה (publish/subscribe) | אפיק הודעות, בדומה לנושאים (topics) ב-Event Grid או ב-Service Bus |
| **Unified namespace (UNS)** | מבנה אירועים מרכזי והיררכי שבו כל המערכות מפרסמות את מצבן הנוכחי | ספריית נושאים ארגונית על פני כל הארגון |
| **OEE** (יעילות ציוד כוללת, overall equipment effectiveness) | יעילות הציוד על בסיס זמינות, ביצועים ואיכות | הסכם רמת שירות (SLA) של זמינות, אלא שעבור מכונות וכולל איכות |
| **KQL** (שפת שאילתות Kusto, Kusto Query Language) | שפת השאילתות של Fabric Eventhouse ושל Azure Data Explorer | אותה שפה שבה אתם משתמשים ב-Log Analytics וב-Microsoft Sentinel |
| **מודל פרדו (Purdue model)** | מודל ייחוס שמפריד את מערכות המפעל לשכבות, מהתקני השטח ועד לארגון; ISA-95 נשען עליו [26] | מודל חלוקה לשכבות ברשת, מה-VLAN של ההתקנים ועד ל-WAN הארגוני |

השורה של KQL היא נקודת כניסה טובה למנהלי מערכת: אם אתם מכירים KQL מ-Sentinel או מ-Log Analytics, תוכלו לבצע שאילתות על נתוני המכונות ב-Eventhouse מיד.

### מאיפה להתחיל כמנהל Microsoft 365 או Azure

אינכם צריכים להפוך למהנדסי אוטומציה כדי להוסיף ערך בפרויקט ייצור. חמש משימות נמצאות בדרך כלל באחריות ה-IT המרכזי וניתן להכין אותן לפני חיבור המכונה הראשונה:

1. **זהויות ותפקידים:** יצירת קבוצות ב-Microsoft Entra ID ותפקידי Azure RBAC לצוותי OT, לשותפים ולצוותי התפעול; שימוש ב-Privileged Identity Management כדי להגביל גישה מוגברת בזמן.
2. **Landing zone של Azure למפעלים:** הגדרת מבנה מנויים וקבוצות משאבים לכל מפעל, ושימוש ב-Azure Policy לאכיפת תגיות (מפעל, מרכז עלות, מקרה שימוש) ואזורים מותרים.
3. **בדיקת Azure Arc:** חיבור שרת ניסיון או אשכול Kubernetes ל-Arc, וקבלת אישור לנקודות הקצה היוצאות הנדרשות דרך שרשרת ה-proxy יחד עם צוות הרשת. בחברות רבות אישורי החומת האש הללו הם המשימה שלוקחת הכי הרבה זמן.
4. **יסודות Fabric:** החלטה על קיבולת, מבנה סביבות עבודה (workspaces) ומודל הגישה; העברת מדיניות הממשל הקיימת של Power BI.
5. **בניית קשר עבודה עם OT:** הבנת מודל האזורים של המפעל לפני שמציעים שינויים ברשת. ב-OT הזמינות קודמת לסודיות, וחלונות התחזוקה נקבעים לפי לוח הייצור, לא לפי Patch Tuesday.

### מה הטבלה אומרת לארכיטקטורה שלכם

**ראשית:** תכננו חיבורי מפעל חדשים ב-Azure IoT Operations, ולא ב-IoT Central ולא בשרשראות מודולים משלכם ב-IoT Edge, אלא אם יש לכם סיבה ספציפית. IoT Edge נשאר נתמך, אך הוא מודל ריצה של התקנים; Azure IoT Operations מטפל במישור הנתונים של המפעל באמצעות ברוקר, מחברים ומודל נכסים [3]. בבחירת ה-SKU שימו לב שה-Essentials אינו כולל את מחבר OPC UA [3]. במפעל טיפוסי עם מכונות OPC UA, Standard הוא נקודת ההתחלה.

**שנית:** הרחיקו את הלוגיקה העסקית משירותי תצוגה מקדימה. ההיסטוריה של פתרונות נתוני הייצור של Microsoft מראה שמודל נתונים לייצור יכול לעבור משלב התצוגה המקדימה לפרישה בפחות משנה וחצי [2]. מודל הנתונים שלכם שייך לכם, וכדאי לתעד אותו בפורמטים פתוחים (טבלאות Delta ב-OneLake, סכמות JSON בברוקר, מודלי מידע DTDL או OPC UA).

**שלישית:** בדקו מחדש את אסטרטגיית אבטחת ה-OT שלכם. ההודעה הרשמית של Azure מציינת אוקטובר 2029 כמועד סיום אבטחת OT ב-Defender for IoT, ואילו בלוג של שותף של Microsoft מופיע 31 במאי 2028 כסוף התמיכה [22], [39]. תכננו לפי התאריך המוקדם: רכש, פריסה וקבלת חיישנים חדשים לוקחים לעתים יותר משנה בסביבות מפוקחות.

**רביעית:** בדקו את צי ה-IoT Edge שלכם. התקנים שפועלים עם IoT Edge 1.5 לא קיבלו עדכוני אבטחה מאז 10 בנובמבר 2026. Microsoft מתארת את המעבר ל-1.6 LTS כפשוט, מכיוון שאין בו שינויים גדולים בתכונות [12]. אותו סיום תמיכה חל על התקנים של Windows שמריצים את IoT Edge for Linux on Windows (EFLOW) 1.5; דף הגרסאות אינו מציג EFLOW 1.6 LTS, אלא רק ערוץ שחרור מתמשך [12]. הבהירו עם Microsoft או עם ספק החומרה שלכם מהו מסלול היעד להתקנים אלה.

> **הערה על עדכניות:** טבלה זו היא תמונת מצב. לפני כל החלטה ארכיטקטונית, בדקו את דפי Microsoft המקושרים ואת פורטל Azure Updates מסונן לפי "Retirements".

## קודם מודל הנתונים: ISA-95 וה-Unified Namespace

פרויקטים רבים בתחום הייצור נכשלים לא בגלל הענן, אלא משום שאף אחד לא הגדיר מה זה "מכונה", "הזמנה" או "אירוע השבתה" במודל הנתונים. ענו על השאלה הזו לפני שאתם פורסים את שירות Azure הראשון.

### ISA-95 והפירמידה האוטומטית

סדרת התקנים **ANSI/ISA-95** (בינלאומית IEC 62264) מתארת את האינטגרציה בין מערכות ארגוניות למערכות בקרה [26]. ISA מתארת אותה כסט תקנים לשילוב מערכות לוגיסטיקה עם מערכות בקרת ייצור, המבוסס על מודל הייחוס Purdue וחל על תעשיות דיסקרטיות, רציפות ולוגיסטיות; לסדרה שמונה חלקים [26]. היא מספקת שני דברים שימושיים לכל ארכיטקטורת ענן:

- **מודל רמות:** רמות 0 עד 2 מכסות את התהליך הפיזי, חיישנים, מפעילים ובקרה (PLC, SCADA). רמה 3 היא ניהול תפעול הייצור (MES, MOM). רמה 4 היא תכנון עסקי ([ERP](https://www.m365.fm/entity/enterprise-resource-planning/)). באירופה היררכיה זו מצוירת לעתים קרובות כ"פירמידה האוטומטית"; בצפון אמריקה מודל Purdue הוא התמונה הנפוצה יותר.
- **מודל אובייקטים:** ISA-95 מגדירה מונחים כמו היררכיית הציוד (ארגון, אתר, אזור, מרכז עבודה, יחידת עבודה), חומר, כוח אדם, הזמנות ייצור ונתוני ביצועים. קרן OPC מיפתה מודל זה לתקן המשלים שלה עבור OPC UA [35].

הביקורת על הפירמידה ידועה: הנתונים נעים רק מרמה לרמה, כל ממשק הוא אינטגרציה נקודתית, ויישום חדש צריך להתחבר למספר מערכות. לעומת זאת, מודל האובייקטים נשאר בעל ערך, משום שהוא נותן ל-IT, ל-OT ולעסק שפה משותפת.

### Unified Namespace: אירועים במקום הפירמידה

ה**-unified namespace (UNS)** הוא דפוס ארכיטקטוני, לא תקן. כל המערכות מפרסמות את מצבן הנוכחי כאירועים לברוקר מרכזי בעל מבנה היררכי, בדרך כלל MQTT. הצרכנים נרשמים לנושאים שהם צריכים. היררכיית הנושאים לרוב עוקבת אחרי היררכיית הציוד של ISA-95, למשל:

```
acme/dayton-plant/assembly/line-3/station-20/state
acme/dayton-plant/assembly/line-3/station-20/order
acme/dayton-plant/assembly/line-3/station-20/quality
```

Azure IoT Operations כולל מתווך MQTT מקומי לקצה (edge-native) התומך ב-MQTT 3.1.1 וב-MQTT 5 [40]. מחבר OPC UA מפרסם נתונים משרתי OPC UA כ-JSON בפורמט OPC UA PubSub אל נושאי המתווך, ויכול גם לכתוב ערכים חזרה לצמתי OPC UA; בקשות כתיבה משתמשות בדפוס הבקשה/תשובה של MQTT 5 [4]. כך ניתן לבנות UNS במפעל בלי להפעיל מתווך נפרד.

אם כבר מפעילים UNS על מתווך אחר, אין צורך להחליף אותו: זרימות נתונים יכולות להעביר הודעות למתווכי MQTT חיצוניים [3]. השאלה אם להשתמש במתווך של Microsoft כ-UNS של המפעל או כמזין למתווך קיים היא החלטה תפעולית. העיקר הוא מוסכמה מחייבת לנושאים ולמטענים, שאינה תלויה במוצר.

### ISA-95 או UNS? שניהם.

התשובה המעשית היא: להשתמש ב-**ISA-95 כאוצר המילים** וב-**UNS כדפוס ההעברה**. בפועל:

| שאלה | המלצה |
|---|---|
| איך נותנים שמות לנכסים? | היררכיית הציוד לפי ISA-95, עקבית בכל הארגון |
| איך בונים את מבנה הנושאים? | לפי היררכיית הציוד, עם תחומים עסקיים מתחתיה (מצב, הזמנה, איכות, אנרגיה) |
| איך מתארים את המטענים? | סכמות JSON ברישום הסכמות של Azure Device Registry [3]; למכונות, עדיפות למפרטים נלווים של OPC UA |
| היכן נמצאים נתוני הבסיס? | במערכת הרשומה (ERP, MES, PLM); ה-UNS מפיץ רק הפניות ומצבים |
| איך מטפלים בהיסטוריה? | לא במתווך, אלא ב-Eventhouse או ב-Lakehouse ב-Fabric |

### מודל הנתונים המינימלי לייצור

ללא קשר לכלים, מקרי השימוש במדריך זה דורשים מודל ליבה של שבע ישויות:

1. **נכס** (מכונה, תחנה, כלי) עם מזהה ייחודי ומקום בהיררכיה
2. **אות** (תג, משתנה נמדד) עם יחידה, קצב דגימה וקישור לנכס
3. **מצב** (פועל, השבתה מתוכננת, השבתה בלתי מתוכננת, החלפת הגדרות) עם קוד סיבה
4. **הזמנה** (הזמנת ייצור, פעולה) עם קישור ל-ERP
5. **חומר ומספר אצווה/סידורי** עם קישור לרשימת החומרים
6. **אירוע** (אזעקה, ממצא איכות, תחזוקה)
7. **אדם/משמרת**, במידה שכללי הפרטיות וההסכמים הקיבוציים מתירים

אם מקשרים את שבע הישויות הללו בצורה נקייה, ניתן לספק מאותו בסיס נתונים את OEE, תחזוקה מנבאת, מעקב וחשבון דיגיטלי (digital twin). אנו דנים באופן גזירת מודל כזה מזרם ערך בפרק [Value Stream Mapping as a Live Data Model](https://www.m365.fm/show/episodes/value-stream-mapping-live-data-model/); השיטה עצמה מוסברת במדריך שלנו על [value stream mapping](https://www.m365.fm/en/learn/value-stream-mapping/).

### זרימת הנתונים בעשרה שלבים

1. The controller exposes process values through an OPC UA server.
2. The OPC UA connector in Azure IoT Operations reads the configured data points of an asset and publishes them to a broker topic, for example `azure-iot-operations/data/<asset>` [4].
3. The connector can automatically discover assets on OPC UA servers and add their configuration to Azure Device Registry [4].
4. Data flows filter, normalize, convert units and enrich with context [3], [31].
5. Local applications (for example an andon board or an inline inspection) subscribe to the broker directly.
6. A data flow forwards aggregated data to a cloud endpoint: Event Hubs/Kafka, the Event Grid MQTT broker, Data Lake Storage, Fabric OneLake or Azure Data Explorer [3].
7. In Fabric, an Eventstream ingests the data and the Eventhouse stores it for KQL queries [17].
8. Data Factory synchronizes ERP, MES, shift and cost data into OneLake [17].
9. Events are enriched with asset hierarchy and line topology; models are trained and scored, and results are stored in OneLake [17].
10. Real-Time Dashboards and Power BI visualize, Activator notifies technicians, and Copilot answers questions in natural language [17].

Microsoft sizes the Connected Factory reference at more than one million IIoT events per hour from 30,000 tags across 40 factories [17]. Treat that as orientation, not as a performance guarantee for your environment.

### Lessons from projects

The consultancy b.telligent describes three lessons from projects with Azure IoT Operations and Fabric [31]:

- **Configure broker storage:** Without persistent storage configured, messages that cannot be forwarded can fill up memory. Microsoft confirms the point indirectly: the broker's disk-backed message buffer can only be set during the initial deployment, not afterwards [40]. Decide on the memory profile and buffer before rollout.
- **Keep schemas stable:** Changing JSON structures make downstream processing fragile. A uniform envelope with metadata and payload helps.
- **Consolidate Eventstreams:** Because every Eventstream carries running costs, the post recommends consolidating per plant rather than per source, and doing transformations in the Eventhouse with update policies and KQL instead of in the Eventstream.

These tips come from a post from March 2025 (updated June 2025); check whether they still apply to your release.

### Alternative paths

Not every manufacturer needs the full architecture. Four variants are common:

| Variant | When it makes sense | Building blocks |
|---|---|---|
| **Cloud-direct** | Few, modern, connected devices; no latency requirements | IoT Hub, DPS, Fabric Real-Time Intelligence |
| **Edge-centric** | Many machines, OPC UA, local decisions, OT network without direct cloud connection | Azure IoT Operations on Arc, Fabric |
| **Partner edge** | Existing industrial edge platform from an automation vendor | Partner platform plus Fabric or Azure; Microsoft lists, for example, running Azure AI models on Siemens Industrial Edge as architecture guidance [2] |
| **Small start (mid-sized manufacturer, one plant)** | A few lines, no in-house Kubernetes team, first use case OEE or condition monitoring | One single-node cluster with Azure IoT Operations Standard (because of OPC UA), a small Fabric capacity, Power BI; cluster operations possibly through a partner |

For a mid-sized manufacturer with one plant, the full layer architecture is a target picture, not a starting point. Start with layers 1, 2, 4 and 8 and add semantics, AI and cross-plant governance once the first use case delivers.

## התכנסות IT/OT ואבטחה

ברגע שנתוני מכונות זורמים לענן, המפעל הופך לחלק ממשטח התקיפה שלכם. במקביל, דרישות הרגולציה והלקוחות הולכות ומתחזקות. CISA מונה את ייצור מתכות היסוד, מכונות, ציוד חשמלי ורכיבים, וציוד תחבורה כליבה של **מגזר הייצור הקריטי** בארה"ב [52], ולכן מפעלים רבים שמזינים נתונים ל-Azure שייכים למגזר תשתיות קריטיות.

סעיף זה פותח בתקנים שמעצבים את התכנון הטכני (ISA/IEC 62443, NIST CSF 2.0, NIST SP 800-82), ממשיך בחובות שחלות על קבוצות מסוימות של יצרנים (CMMC, SEC, CIRCIA) ולבסוף, עבור חברות עם פעילות באיחוד האירופי או לקוחות באיחוד, מתייחס ל-NIS2 ולתקנת החוסן הסייבר (Cyber Resilience Act).

### ISA/IEC 62443: אזורים, מעברים ורמות אבטחה

סדרת **ISA/IEC 62443** היא מסגרת הייחוס לאבטחת מערכות אוטומציה ובקרה תעשייתיות. המושגים המרכזיים שלה הם אזורים (קבוצות נכסים עם אותן דרישות הגנה), מעברים (נתיבי תקשורת מבוקרים בין אזורים) ורמות אבטחה כיעד לכל אזור, מ-SL 1 (הגנה מפני הפרה מזדמנת או מקרית) ועד SL 4 (הגנה מפני תוקפים מתוחכמים בעלי משאבים מורחבים) [27]. התקן מגדיר גם שבע דרישות יסוד, מבקרת זיהוי ואימות ועד זמינות משאבים [27]. לארכיטקטורת Azure משמעות הדבר:

- **אשכול הקצה הוא אזור עצמאי:** אשכול Kubernetes שמריץ את Azure IoT Operations אינו שייך לא לרשת המשרד ולא ישירות לרשת הבקרה, אלא לאזור ביניים (המכונה לעיתים "DMZ תעשייתי", רמת Purdue 3.5).
- **חיבורים יוצאים בלבד:** Arc וזרימות הנתונים פותחים חיבורים מהמפעל אל הענן. חיבורים נכנסים מהאינטרנט אל המפעל אינם נדרשים ואין לפתוח אותם.
- **רשתות שכבתיות:** Microsoft קובעת ש-Azure IoT Operations תומך בניהול מאובטח של התקנים ברשתות שכבתיות [3]. תכננו את שרשרת ה-proxy וחומת האש מוקדם, יחד עם אנשי אבטחת OT.
- **מתן הרשאת כתיבה במודע:** מחבר OPC UA יכול לכתוב ערכים בחזרה אל בקרים [4]. יכולת זו דורשת הערכת סיכונים ותהליך אישור משלה, ורצוי שתתחיל במצב כבוי.
- **אישורים במקום סיסמאות:** עבור OPC UA זמינים שם משתמש/סיסמה, אישורי X.509 וגישה אנונימית (לבדיקות בלבד) [4]. השתמשו באישורים וברשימת אמון, ויש לנהל חידוש אישורים כתהליך תפעולי חוזר.

### NIST CSF 2.0 ו-NIST SP 800-82: הבסיס האמריקאי

עבור רוב היצרנים בארה"ב, **מסגרת הסייבר של NIST (CSF) 2.0** היא השפה המשותפת בין המפעל, ה-IT וההנהלה. NIST פרסם אותה ב-26 בפברואר 2024; היא מרחיבה את חמש הפונקציות Identify, Protect, Detect, Respond ו-Recover עם פונקציה חדשה בשם **Govern**, והיא חלה על ארגונים מכל מגזר וגודל [49]. המסגרת וולונטרית, אך לקוחות, חברות ביטוח ומבקרים מבקשים יותר ויותר פרופיל CSF.

שני מסמכים של NIST הופכים את המסגרת לקונקרטית עבור מפעלים:

- **NIST SP 800-82 Rev. 3, Guide to Operational Technology (OT) Security** (ספטמבר 2023) מכסה ארכיטקטורות OT, איומים ואמצעי נגד, ומוסיף שכבת OT (overlay) עם בסיסי בקרה מותאמים מ-SP 800-53 למערכות OT בהשפעה נמוכה, בינונית וגבוהה [50].
- **NIST IR 8183 Rev. 2, Cybersecurity Framework 2.0 Manufacturing Profile**, פורסם כטיוטה ראשונית לציבור ב-29 בספטמבר 2025; תקופת ההערות הסתיימה ב-17 בנובמבר 2025, ונכון לנובמבר 2026 אין עדיין גרסה סופית [51]. השתמשו בו כמסמך עזר טיוטה, לא כתקן סופי.

איך החלקים משתלבים בפרויקט Azure:

| פונקציית CSF 2.0 | משמעותה עבור פלטפורמת הייצור ב-Azure |
|---|---|
| Govern | בעלים מוגדרים לפלטפורמת המפעל, קבלת סיכון לשירותי תצוגה מקדימה, רשימת ספקים (Microsoft, אינטגרטור, ספקי OT) |
| Identify | מלאי נכסי OT המותאם ל-Azure Device Registry; מפת זרימת נתונים לכל אזור ולכל conduit |
| Protect | תפקידים ב-Entra ID עם הרשאות מינימליות, PIM, אישורי OPC UA, קישוריות יוצאת בלבד, גישת כתיבה מושבתת כברירת מחדל |
| Detect | ניטור רשת OT (פתרון שותף לאחר Defender for IoT), לוגים מרכזיים מהקצה ומהענן ב-Sentinel או ב-SIEM שלכם |
| Respond | נוהל תגובה לאירועים המכסה את המפעל ואת הענן, כולל מי רשאי לנתק אשכול במהלך הייצור |
| Recover | פריסה מחדש של אשכול הקצה שנבדקה (infrastructure as code), גיבוי של תצורת ה-broker והנכסים |

יצרנים קטנים ובינוניים אינם צריכים לעשות זאת לבד: רשת השותפים הלאומית של NIST Manufacturing Extension Partnership (MEP) מציעה הערכות עצמיות מבוססות CSF, ניתוחי פערים, תוכניות לתיקון ליקויים, תוכניות תגובה לאירועים ועזרה בדרישות DFARS [58].

### CMMC לספקי הביטחון

אם אתם מייצרים חלקים או מספקים שירותים למשרד ההגנה האמריקאי, ה-**Cybersecurity Maturity Model Certification (CMMC)** חל על המערכות שמעבדות, מאחסנות או מעבירות Federal Contract Information (FCI) או Controlled Unclassified Information (CUI). כלל התוכנית (32 CFR Part 170) נכנס לתוקף ב-16 בדצמבר 2024 [53]. כלל ה-DFARS שמכניס את CMMC לחוזים נכנס לתוקף ב-10 בנובמבר 2025, עם הטמעה שלבית: שלב 1 החל באותו תאריך, שלב 2 ב-10 בנובמבר 2026, ושלב 3 מתוכנן ל-10 בנובמבר 2027 [54]. הרמות הן Level 1 (הערכה עצמית, FCI), Level 2 (הערכה עצמית או הערכה של גוף צד שלישי C3PAO, בהתבסס על NIST SP 800-171) ו-Level 3 (הערכת DIBCAC, המוסיפה את פרקטיקות NIST SP 800-172) [53], [54].

המשמעות עבור Azure:

- **הגדירו את היקף הנתונים, לא את הענן.** CMMC חל על המערכות שלכם, לא על Azure כפלטפורמה; אין תעודת CMMC ל-Azure עצמו [55]. טלמטריית מכונות רגילה עשויה שלא להיות CUI, בעוד שרטוטים, מפרטים וחלק מפרמטרי התהליך לחלקי ביטחון עשויים להיות; הסימונים של CUI ותנאי החוזה מהלקוח שלכם הם שקובעים. החליטו אילו נתונים ב-UNS וב-OneLake נכללים בהיקף.
- **בחרו את סביבת הענן בכוונה.** Microsoft מציינת ש-Azure commercial וגם Azure Government מחזיקים באישורי FedRAMP High המכסים את NIST SP 800-171, ושניהם יכולים לקבל אישור CMMC לפתרונות; Azure Government מוסיף אישורי DoD IL4/IL5 והתחייבויות חוזיות לגבי אחסון נתונים בארה"ב ואנשי צוות אמריקאים שעברו בדיקה, ו-Microsoft רואה בו את ההתאמה הטובה יותר לרוב קבלני הביטחון [55]. שימו לב שדף ה-CMMC של Microsoft עודכן לאחרונה באפריל 2023, לכן בדקו את הפרטים מול איש הקשר שלכם בצוות החשבון של Microsoft.
- **בדקו זמינות תכונות.** לא every שירות במדריך זה זמין ב-Azure Government או בסביבת Microsoft 365 GCC High. ודאו את זמינות Azure IoT Operations, Fabric ו-Copilot בענן היעד שלכם לפני שאתם מתכננים סביבם [unverified for the individual services; check Microsoft's US Government feature availability pages].

### דיווח SEC ודיווח אירועי CIRCIA

שני משטרי דיווח אמריקאיים משפיעים על האופן שבו אתם מתכננים רישום לוגים ותגובה לאירועים עבור פלטפורמת המפעל:

- **חברות ציבוריות:** על פי כללי ה-SEC שאומצו ב-26 ביולי 2023, נדרשים רשומים לחשוף אירוע סייבר מהותי בטופס 8-K (Item 1.05) תוך ארבעה ימי עסקים מרגע שנקבע שהוא מהותי, ולתאר את ניהול הסיכונים, האסטרטגיה והממשל בתחום הסייבר בדוח השנתי Form 10-K [56]. מתקפת כופרה שעוצרת מפעל היא מועמדת טיפוסית להערכת מהותיות, לכן נוהל ה-OT לאירועים צריך לכלול נתיב מהיר לוועדת הגילוי.
- **תשתיות קריטיות (CIRCIA):** חוק Cyber Incident Reporting for Critical Infrastructure Act דורש מישויות מכוסות לדווח ל-CISA על אירועי סייבר מכוסים תוך 72 שעות, ותשלומי כופר תוך 24 שעות, אך רק לאחר שכלל הסופי של CISA ייכנס לתוקף. נכון לאוקטובר 2026, CISA שלחה את הכלל הסופי לבית הלבן לבדיקה, והוא טרם פורסם [57]. עקבו אחר הכלל הסופי; הוא יקבע אילו יצרנים מכוסים.

### NIS2 ו-Cyber Resilience Act לפעילות באירופה

אם אתם מפעילים מפעלים באיחוד האירופי או מוכרים בו מכונות, יש שני חוקים אירופיים נוספים שחשוב להכיר. הדוגמאות הגרמניות שלהלן מגיעות מהמהדורה המקורית בגרמנית של המדריך, ומראות כיצד כללי האיחוד מיושמים בפועל.

**NIS2 (דוגמה: גרמניה).** חוק היישום הגרמני של NIS2 (NIS2UmsuCG) נכנס לתוקף ב-6 בדצמבר 2025; הרשות הפדרלית לאבטחת מידע בגרמניה (BSI) מפקחת כעת על כ-29,500 ישויות, במקום כ-4,500 קודם לכן [28]. חברות נכללות בתחום החוק אם הן שייכות לאחד מסוגי הישויות שבנספחים 1 ו-2 לחוק BSI, ועומדות בסף שבסעיף 28: לפחות 50 עובדים, או מחזור שנתי ומאזן העולים על 10 מיליון יורו כל אחד [41]. הענפים הייצורניים בנספח 2 כוללים מכשור רפואי, מחשבים, מוצרים אלקטרוניים ואופטיים, ציוד חשמלי, מכונות וכלי רכב; כימיקלים ומזון מופיעים כענפים נפרדים. החובות העיקריות:

- **רישום** בשני שלבים, דרך חשבון "Mein Unternehmenskonto" ופורטל BSI, שנפתח ב-6 בינואר 2026 [28].
- **ניהול סיכונים** עם אחריות ברמת ההנהלה.
- **אמצעים טכניים וארגוניים**, לרבות אבטחת שרשרת האספקה ואימות רב-שלבי.
- **דיווח על אירועים משמעותיים**: התראה מוקדמת תוך 24 שעות מהרגע שבו נודע האירוע, הודעה על האירוע תוך 72 שעות, ודוח סופי לא יאוחר מחודש לאחר ההודעה [41].

החברות צריכות לבדוק בעצמן אם הן נכללות בתחום החוק; ה-BSI אינו מודיע להן על כך. הרשות מציעה בדיקה עצמית מקוונת שאינה מחייבת, וממליצה על ייעוץ משפטי במקרים לא ברורים [41]. למדינות חברות אחרות באיחוד יש חוקי יישום משלהן, בעלי מבנה דומה.

**חוק החוסן הסייברי (Cyber Resilience Act).** אם אתם בונים מכונות או מוצרים עם רכיבים דיגיטליים ומשווקים אותם בשוק האירופי, חל גם **חוק החוסן הסייברי (תקנה (EU) 2024/2847)**, לרבות על יצרנים אמריקאים. מ-11 בספטמבר 2026, יצרנים חייבים לדווח על פגיעויות שמנוצלות בפועל ועל אירועים חמורים באמצעות פלטפורמת הדיווח האחידה של ENISA: התראה מוקדמת תוך 24 שעות, הודעה תוך 72 שעות, ודוח סופי לא יאוחר מ-14 ימים לאחר שתיקון זמין עבור פגיעויות, או תוך חודש בעבור אירועים [30]. מ-11 בדצמבר 2027, מוצרים חייבים לעמוד בדרישות החוסן הסייברי החיוניות לפני שיוצבו בשוק; אלה כוללות ברירות מחדל מאובטחות, רשימת חומרי תוכנה (SBOM) ועדכוני אבטחה למשך תקופת תמיכה מוצהרת, בדרך כלל לפחות חמש שנים [42]. עבור יצרני מכונות ששולחים ציוד עם שירותי ענן, ה-IT הייצורי הופך לעניין של התאמה למוצר.

לגבי ארכיטקטורת Azure, NIS2, CSF 2.0 ו-CMMC מצביעים לאותו כיוון: מלאי (מה מחובר לענן?), רישום אירועים (מי שינה מה, ומתי?), שקיפות בשרשרת האספקה (אילו שירותים ושותפים מעורבים?) ומסלול דיווח שנבדק מראש.

### ניטור OT לאחר פרישת Defender for IoT

ב-2 בנובמבר 2026 הודיעה Microsoft רשמית ב-Azure Updates כי תפסיק לחלוטין את רכיב אבטחת ה-OT של Defender for IoT באוקטובר 2029, לאחר תקופת מעבר של שלוש שנים [22]. עד אז השירות מקבל עדכוני אבטחה ותיקוני באגים, אך לא תכונות OT חדשות; הסכמים קיימים וחידושים מכובדים עד אוקטובר 2029 [22]. יכולות IoT ארגוניות ב-Defender for Endpoint, כמו גם גילוי מכשירים והערכת פגיעויות, אינן מושפעות [22]. אין מוצר תחליף מבית Microsoft [39]. Microsoft מציעה מחברים ל-Armis, Dragos ו-Forescout שמביאים נתוני נכסי OT ופגיעויות אל Microsoft Security Exposure Management ואל פורטל Defender; פתרונות השותפים דורשים רישיונות והטמעה משלהם [22], [24].

תאריכים סותרים: בלוג של שותף של Microsoft מנובמבר 2026 מציין את **31 במאי 2028** כתאריך סיום התמיכה באבטחת OT [39]. לא הובהר, בעת כתיבת שורות אלה, אם מדובר בתאריך אחר עבור סוגי חוזים מסוימים או בטעות.

המלצה: אם אתם מטמיעים ניטור OT עכשיו, הערכו ישירות את פתרונות השותפים. אם אתם מפעילים את Defender for IoT, תכננו את ההחלפה כך שתושלם לפני אמצע 2028, ואשרו מול איש הקשר שלכם בחשבון Microsoft את התאריך החל על החוזה שלכם.

## מקרה שימוש 1: תחזוקה חזויה ב-Azure

תחזוקה חזויה היא אחד ממקרי השימוש בייצור שמוזכרים לעיתים קרובות ב-Azure, וגם אחד שבו פיילוטים רבים נכשלים. סיבה נפוצה: המודל בא לפני הנתונים. אנו מרחיבים על כך בפרק [Predictive Maintenance on Azure: What You Actually Need Before the Model](https://www.m365.fm/show/episodes/predictive-maintenance-on-azure-for-manufacturers-what-you-actually-need-before-the-model/).

### הפרידו בין המונחים

| אסטרטגיה | טריגר | נתונים נדרשים |
|---|---|---|
| תחזוקה תגובתית | תקלה | אין |
| תחזוקה מונעת | מרווח זמן או מונה | שעות הפעלה, מחזורים |
| תחזוקה מבוססת מצב (ניטור מצב) | חריגה מסף | משתני מצב (רטט, טמפרטורה, זרם) |
| תחזוקה חזויה | תחזית של אורך חיים שנותר או הסתברות לתקלה | משתני מצב, בתוספת היסטוריית תקלות מתויגת והקשר תפעולי |
| תחזוקה preskriptivית | פעולה מומלצת | בתוספת ידע על הגורמים והפעולות |

חברות רבות משיגות את רוב היתרון באמצעות תחזוקה מבוססת מצב בלבד. מודלים חזויים משתלמים כאשר תקלות יקרות, תכופות מספיק וניתנות לחיזוי פיזי מראש. [Total Productive Maintenance](https://www.m365.fm/entity/total-productive-maintenance/) מספק את האסטרטגיה הכוללת; העמודים שלו, תחזוקה אוטונומית ותחזוקה מתוכננת, פועלים גם ללא AI.

### דרישות מוקדמות לנתונים

לפני שמאמנים מודל, יש לוודא שניתן לענות בחיוב על השאלות הבאות:

1. **האם קיימת היסטוריית תקלות?** מודל מונחה דורש תקלות עם חותמות זמן וסוגי תקלה. נתונים אלה נמצאים בדרך כלל במערכת התחזוקה (למשל SAP PM או CMMS) ונדירים להיות מקודדים בצורה נקייה.
2. **האם חותמות הזמן מסונכרנות?** זמן החיישנים, זמן הבקרים וזמן הרישום ב-ERP חייבים להיות ניתנים להתאמה. לא במקרה Microsoft הוסיפה להודעות הבריאות של חיישני Defender for IoT הודעות ייעודיות לשרתי NTP חסרים או לא נגישים [23]; אותו דבר חל על צינור הנתונים שלכם. מחבר OPC UA נושא את חותמת הזמן במקור של כל ערך [4]; השתמשו בה ולא בזמן ההגעה לענן.
3. **האם קצב הדגימה מתאים למנגנון הכשל?** נזק למסב נראה בספקטרום הרטט בטווח הקילוהרץ; בלאי של רצועות חימום נראה בערכים בדקות. תג OPC UA ברזולוציה של שנייה מספיק לאחד, לא לשני.
4. **האם קיים הקשר תפעולי?** ללא מידע על מוצר, מתכון, הזמנה ומצב (החלפה, ייצור, השבתה), המודל יתייחס לכל החלפת מוצר כאל חריגה.
5. **האם הפעולה מוגדרת?** מי מגיב לאזהרה, עם כמה זמן מוקדם, וכיצד מדווחת התוצאה בחזרה?

### שישה שלבים

1. **בחירת מועמדים:** נכסים עם עלויות תקלה גבוהות, מצבי כשל חוזרים וחיישנים קיימים. ניתוח פארטו של סיבות השבתה מתוך ה-MES נותן לכם את הרשימה.
2. **חיבור הנתונים:** מחבר OPC UA ב-Azure IoT Operations, נקודות נתונים לכל נכס, זרימת נתונים אל Fabric [3], [4]. צברו נתוני רטט בתדירות גבוהה בקצה לכדי מאפיינים (RMS, קורטוזיס, אנרגיות פסי תדר).
3. **ניטור מצב תחילה:** ספים וזיהוי חריגות פשוט ב-Eventhouse וב-Activator. Activator יכול להודיע ישירות לטכנאים [17]. זה מניב ערך תוך שבועות ולא חודשים, ובאותה עת אוסף תוויות.
4. **יצירת תוויות:** שייכו הוראות עבודת תחזוקה עם קודי תקלה לסדרות הזמן. כאן טמון המאמץ האמיתי. תכננו כלי לכך: מיקרוסופט הפסיקה את תכונת תיוג הנתונים המובנית ב-Azure Machine Learning ב-30 בספטמבר 2026 והפנתה לספקים חיצוניים [38]. לתוויות סדרות זמן ממערכת התחזוקה, לעיתים קרובות די ב-Power App שכותב בחזרה למערכת התחזוקה.
5. **אימון המודל:** ב-Fabric Data Science או ב-Azure Machine Learning; אחסנו את התוצאות ב-OneLake [17]. התחילו בשיטות בנות פירוש (gradient boosting על מאפיינים) לפני שתשתמשו בלמידה עמוקה.
6. **הפעלה תפעולית:** שלחו תחזיות כאירועים לתהליך התחזוקה (התראה במערכת התחזוקה, הודעת Teams, טופס Power Apps למשוב). נטרו את איכות המודל והסחף שלו.

### מדדי הצלחה

מדדו את ההשפעה התפעולית, לא את דיוק המודל: השבתות בלתי מתוכננות, זמן ממוצע בין תקלות (MTBF), זמן ממוצע לתיקון (MTTR), שיעור שעות התחזוקה המתוכננות מתוך סך שעות התחזוקה, ומלאי חלפים. מדדי [KPI](https://www.m365.fm/entity/key-performance-indicator/) אלה דורשים קו בסיס לפני תחילת הפרויקט; אחרת לא תוכלו להוכיח שום תועלת. המדריך שלנו ל[מדדי KPI בייצור](https://www.m365.fm/en/learn/manufacturing-kpis/) מכסה את ההגדרות.

### קצה או ענן להסקה?

| קריטריון | הסקה בענן | הסקה בקצה |
|---|---|---|
| השהיה | שניות עד דקות | מילישניות |
| נפח נתונים | נשלחים רק נתונים מצטברים | הנתונים הגולמיים נשארים מקומית |
| תפעול | פשוט יותר (מודלים מרכזיים) | פריסות מבוזרות, ניהול גרסאות לכל מפעל |
| עמידות | תלויה בקישוריות | פועל במצב לא מקוון |
| שימוש טיפוסי | אורך חיים שנותר, תכנון תחזוקה | כיבוי מהיר, איכות בתוך הקו |

לתחזוקה חזויה קלאסית, הסקה בענן על נתונים מצטברים מספיקה ברוב המקרים. החל מגרסה 2603, מיקרוסופט מיצבה במפורש את Azure IoT Operations לתרחישי AI קרובים יותר למכונה ("Physical AI") [6]; להסקה בקצה, בדקו את הערות השחרור העדכניות [7].

### תחזוקה חזויה ב-Azure: אבני הבניין במבט אחד

| שלב | אבן בניין של Azure ומיקרוסופט | חלופה |
|---|---|---|

| אחסון וניתוח סדרות זמן | Fabric Eventhouse עם KQL [17] | Azure Data Explorer [19] |
| ספים והתראות | Fabric Activator [17] | Azure Monitor או לוגיקה מותאמת אישית |
| אימון המודל | Fabric Data Science, Azure Machine Learning [17], [37] | היישום של יצרן המכונה |
| הפעלת פעולה | Power Automate, Teams, Power Apps, מערכת התחזוקה | API ישיר ל-CMMS |

## מקרה שימוש 2: מעקב ושושלת ייצור

מעקב (Traceability) עונה על השאלה "היכן מותקן חלק זה, ומה הוא עשוי?". שושלת (Genealogy) מתארת את שרשרת המקור המלאה של מוצר: חומר, לוט, שלב תהליך, מכונה, פרמטרים, תוצאת בדיקה ומפעיל. בתעשיות מפוקחות היא חובה; בכל מקום אחר היא מאיצה טיפול בתלונות ומצמצמת את היקף ריקולים. הפרק [Traceability and Genealogy](https://www.m365.fm/show/episodes/traceability-and-genealogy/) עוסק בנושא לעומק.

### דרישות לפי תעשייה

| תעשייה / כלל | דרישת נתונים מרכזית | הערה |
|---|---|---|
| מזון, FDA Food Traceability Rule (FSMA Section 204) | אלמנטי נתונים מרכזיים (KDEs) לכל אירוע מעקב קריטי (CTE) כגון קבלה, עיבוד ומשלוח, המקושרים לקוד לוט למעקב; רשומות נמסרות ל-FDA תוך 24 שעות מבקשה, בתוספת גיליון אלקטרוני ניתן למיון בזמן פרצות מחלה או ריקולים | [59]; ה-FDA לא יאכוף לפני 20 ביולי 2028 בעקבות הנחיית הקונגרס (המועד המקורי 20 בינואר 2026) |
| מכשירים רפואיים, FDA QMSR (21 CFR Part 820) | החל מ-2 בפברואר 2026, תקנת מערכת ניהול האיכות משלבת בהפניה את ISO 13485:2016, לרבות דרישות הזיהוי והמעקב שבו | [61] |
| רשומות אלקטרוניות המפוקחות על ידי FDA, 21 CFR Part 11 | נתיבי ביקורת מאובטחים, שנוצרים על ידי מחשב ומסומנים בזמן, המתעדים רישומי מפעיל ושינויים מבלי לטשטש רישומים קודמים, ונשמרים כל עוד הרשומות קיימות | [60]; רלוונטי לתרופות, מכשירים רפואיים ורשומות מזון הנשמרות אלקטרונית |
| רכב, IATF 16949 | סעיף 8.5.2.1 משלים את דרישות הזיהוי והמעקב של ISO 9001 (לרבות תוכנית מעקב מבוססת ניתוח סיכונים); סעיף 7.5.3.2.1 עוסק בשמירת רשומות מסוימות, ומקובל לפרשו כמשך אספקת חלקי ייצור ושירות ועוד שנה קלנדרית אחת, אלא אם הלקוח או הרגולטור דורשים אחרת | נוסח התקן בתשלום; פרטים ממקורות משניים. דרישות ספציפיות של לקוחות OEM (CSRs) הולכות לעיתים רחוקות יותר |
| תעופה וחלל, AS9100D (EN 9100 באירופה, JIS Q 9100 ביפן) | מעקב לאורך מחזור החיים של המוצר, זיהוי תצורה, ויכולת לאתר מוצרים שיוצרו מאותו לוט חומר גלם או מאותה אצווה ייצור | AS9100D (2016) היא המהדורה הנוכחית; EN 9100 היא המהדורה האירופית השקולה טכנית [62]. ציטוט הסעיף (8.5.2) לא נבדק מול נוסח התקן המקורי |
| סוללות הנמכרות באיחוד האירופי, תקנת הסוללות של האיחוד האירופי (תקנה (EU) 2023/1542) | "דרכון סוללה" אלקטרוני החל מ-18 בפברואר 2027 עבור סוללות הנעה לרכבי חשמל, סוללות לאמצעי תחבורה קלים (למשל אופניים חשמליים, קורקינטים חשמליים) וסוללות תעשייתיות מעל 2 קוט"ש | [29]; לוח הזמנים לפי הנציבות האירופית הוא אינדיקטיבי; רלוונטי ליצואנים אמריקאים לאיחוד האירופי |
| מוצרים הנמכרים באיחוד האירופי במסגרת תקנת העיצוב האקולוגי (ESPR, תקנה (EU) 2024/1781) | דרכון מוצר דיגיטלי, בהתאם לפעולה מואצלת; מרשם הדרכונים הדיגיטליים של האיחוד פועל החל מ-20 ביולי 2026 (בתחילה עם סביבת בדיקה); פעולה מואצלת לברזל ופלדה מתוכננת לרבעון ד' 2026, ולטקסטיל, אלומיניום וצמיגים ב-2027; לפחות 18 חודשי מעבר לאחר אימוץ פעולה מואצלת | [29]; לוח הזמנים לפי הנציבות האירופית הוא אינדיקטיבי |

לגבי תעופה וחלל, מירקו פיטרס מסביר בפוסט שלו [Aerospace Production Planning: Lead Time and Traceability](https://www.m365.fm/community/u/mirko-p/blog/aerospace-production-planning-lead-time-traceability/) מדוע זמן אספקה ומעקב קשורים זה לזה באופן הדוק בתחום; המדריך שלנו ל[תכנון ייצור לתעופה וחלל](https://www.m365.fm/en/learn/aerospace-production-planning/) מכסה את ההקשר של AS9100, FAA ובקרת יצוא.

### מודל הנתונים של השושלת

שושלת אמינה דורשת שלושה סוגי קשרים:

1. **חומר-בתוך-חומר:** לוט A ורכיב B נכנסים להרכבה C (הפניה ל-BOM, מספר סידורי או מספר לוט).
2. **חומר-לתהליך:** הרכבה C עובדה בפעולה 30 בתחנה 20 עם סט פרמטרים X על ידי משמרת Y.
3. **תהליך-לתוצאה:** פעולה 30 הניבה תוצאת בדיקה Z ו, במידת הצורך, אי-התאמה.

אלה הקשרים יוצרים גרף. ניתן לייצג אותו ב-Fabric כמבנה טבלאות ב-Lakehouse ולעבור עליו באמצעות KQL או SQL, או לבנות אותו כמודל גרף בתאום דיגיטלי (Fabric ontology או Azure Digital Twins) [14], [16]. מה שחשוב הוא שהזיהוי מתבצע במקור: סריקה, RFID או קודי Data Matrix בתחנה, מקושרים לאירוע ההזמנה ב-UNS.

### יישום ב-Azure

- **לכידת אירועים בקצה:** סורקים ותחנות מפרסמים "חלק X התחיל/הסתיים בתחנה Y" לברוקר ה-MQTT של Azure IoT Operations [3]. פרמטרי תהליך מגיעים דרך מחבר OPC UA [4]; "הפעלת מערך נתונים" מאפשרת לנקודת נתונים אחת להפעיל את פרסומן של נקודות אחרות, למשל "המחזור הסתיים" [4].
- **איחוד ההקשר:** ב-Fabric מצטרפים האירועים לנתוני הזמנות ו-BOM מ-ERP ומ-MES [17].
- **הבטחת אי-שינוי:** רשומות רגולטוריות דורשות אחסון בלתי ניתן לשינוי, או לפחות יומן שינויים עמיד בפני זיוף (לרשומות שכפופות ל-FDA, דרישת נתיב הביקורת של Part 11 [60]). מדיניות האי-שינוי של OneLake חלה כיום רק על יומני אבחון, ולא על נתונים עסקיים [43]. לארכיוני מעקב עמידים לביקורת יש להוסיף Azure Blob Storage עם מדיניות אחסון בלתי ניתן לשינוי (WORM); Fabric נשארת שכבת הניתוח.
- **מתן שאילתות:** שאילתות טיפוסיות הן מעקב קדימה (אילו מוצרים גמורים מכילים את המנה A?) ומעקב אחורה (ממה מורכב המספר הסידורי S?). דוח Power BI או Power App לבקרת איכות הופכים שאילתות אלה לשמישות גם ללא כישורי KQL. לפי FSMA 204, היכולת לייצא גיליון אלקטרוני הניתן למיון תוך 24 שעות [59] היא מבחן קבלה מוחשי לשכבה זו.

### מרשומת מעקב לדרכון מוצר דיגיטלי

דרכון מוצר דיגיטלי הוא למעשה תמצית הנגישה מבחוץ של שושלת הייצור שלכם בתוספת נתוני קיימות וחומרים. אם תבנו היום שושלת ייצור נקייה, כבר עשיתם את עבודת היסוד הקשה ביותר. דאגו לכך שהמזהים יהיו ייחודיים וקבועים, ושתוכלו להפריד בין הנתונים שהם ציבוריים, הנתונים שמיועדים לרגולטורים לבין הנתונים הפנימיים בלבד.

## מקרה שימוש 3: תאומים דיגיטליים

המונח [תאום דיגיטלי](https://www.m365.fm/entity/digital-twin/) משמש לדברים שונים מאוד: מודל תלת-ממדי, מודל סימולציה, או ייצוג חי של מפעל. לצורך ארכיטקטורה, הבחנה מסוימת עוזרת. המדריך שלנו ל[תאומים דיגיטליים בייצור](https://www.m365.fm/en/learn/digital-twin-manufacturing/) חורג מעבר לתפיסה של Azure.

### שלושה סוגים של תאומים

| סוג | השאלה | נתונים | כלים באקוסיסטם של Microsoft |
|---|---|---|---|
| **תאום מידע** | מה נמצא איפה, וכיצד הוא מחובר? | היררכיית נכסים, קשרים, מצבים חיים | בונה תאומים דיגיטליים ב-Fabric (תצוגה מקדימה) [15], אונטולוגיית Fabric IQ (תצוגה מקדימה) [16], Azure Digital Twins [14] |
| **תאום סימולציה** | מה קורה אם …? | לוגיקת תהליך, זמנים, קיבולות, התנהגות בהפרעות | יישומי תעשייה לזרימת חומרים וסימולציית תהליכים, אפשרית על תשתית Azure |
| **תאום הנדסי** | איך המוצר או המכונה מתנהגים פיזית? | CAD, CAE, לוגיקת בקרה | PLM/CAE על Azure; Microsoft מפרסמת הנחיות ארכיטקטורה ל-Siemens NX על Azure Virtual Desktop עם מכונות וירטואליות GPU ול-Ansys Discovery על מכונות וירטואליות GPU, בין היתר [2] |

[הפעלה וירטואלית (Virtual commissioning)](https://www.m365.fm/entity/virtual-commissioning/) מחברת בין תאום ההנדסה לתאום הסימולציה: קוד הבקרה נבדק מול מודל של המפעל לפני שהציוד האמיתי קיים.

### Azure Digital Twins או Fabric?

Microsoft עצמה מציינת ש-בונה תאומים דיגיטליים ב-Fabric הוא מוצר שונה מ-Azure Digital Twins [14], [15]. ההבדלים המעשיים:

| קריטריון | Azure Digital Twins | בונה תאומים דיגיטליים ב-Fabric |
|---|---|---|
| סטטוס | פעיל, ללא הודעת הוצאה משימוש בעמוד הסקירה [14] | תצוגה מקדימה [15] |
| מודלים | DTDL (Digital Twins Definition Language), גרסה 3 [14] | אונטולוגיה עם סוגי ישויות וקשרים [15] |
| אחסון | גרף תאומים משלו; היסטוריה דרך היסטוריית נתונים ל-Azure Data Explorer [14] | OneLake; הנתונים חייבים להיות קודם ב-lakehouse של Fabric [15] |
| אינטגרציה | ניתוב אירועים ל-Event Hubs, Event Grid, Service Bus [14] | מובנית ב-Fabric Real-Time Intelligence, Power BI |
| קהל יעד | צוותי פיתוח, מונחי API | צוותי נתונים ועסקים, קוד נמוך |
| הדמיה | 3D Scenes Studio (תצוגה מקדימה) [14] | חוויות Fabric, Power BI |

**המלצה:** אם פלטפורמת הנתונים שלכם היא Fabric ואתם זקוקים לתאומים אנליטיים עבור KPI וניתוח שורש הבעיה, עקבו אחר digital twin builder ואונטולוגיית Fabric IQ וערכו להם פיילוט, אך אל תקשרו את מודל הנתונים שלכם לגרסת תצוגה מקדימה. Microsoft טרם תיעדה כיצד יתפתחו שני אבני הבניין הללו ביחס זה לזה; האונטולוגיה כבר עברה שינוי חוויה אחד עם מיגרציה חובה [16]. אם אתם בונים כיום יישום תאום ייצורי מבוסס API, Azure Digital Twins הוא השירות הזמין לכלל הלקוחות. בכל מקרה, שמרו עותק של האונטולוגיה שלכם בפורמט שאינו תלוי בכלי מסוים.

### מאיפה מתחילים?

הטעות הנפוצה ביותר היא להתחיל מהמחשה תלת-ממדית. התחילו משאלה שהתאום צריך לענות עליה, למשל "אילו הזמנות ייפגעו אם תחנה 20 תיפול?". שאלה זו קובעת אילו ישויות וקשרים דרושים לכם. Mirko Peters מתאר גישה זו ב-[Digital Twin in Manufacturing: Where to Start](https://www.m365.fm/community/u/mirko-p/blog/digital-twin-manufacturing-where-to-start/) ואת המסלול מ-ERP ועד תאום קומת הייצור ב-[From ERP to Shop Floor: Building the Digital Twin](https://www.m365.fm/community/u/mirko-p/blog/erp-to-shop-floor-digital-twin/). אנו דנים ביישום הטכני ב-Azure בפרק [Digital Twins on Azure](https://www.m365.fm/show/episodes/digital-twins-on-azure/).

## מקרה שימוש 4: KPI בזמן אמת, OEE וזרמי ערך

KPI בזמן אמת הם לרוב הדרך המהירה ביותר להפיק ערך מחיבור קומת הייצור. הם אינם דורשים בינה מלאכותית, אך כן דורשים מודל מצבים נקי.

### חישוב נכון של OEE

יעילות ציוד כוללת (OEE) היא המכפלה של זמינות, ביצועים ואיכות. הנוסחה פשוטה; ההגדרות אינן פשוטות:

- **זמינות:** אילו עצירות נחשבות כמתוכננות (הפסקות, תחזוקה מתוכננת, אין הזמנה)? החלטה זו משנה את ה-OEE במספר רב של נקודות אחוז.
- **ביצועים:** איזה זמן מחזור משמש כבסיס: ערך התכנון, זמן המחזור הטוב ביותר שהושג, או התקן ב-ERP?
- **איכות:** האם עבודה חוזרת נספרת כחלק טוב או כחלק פגום?

הסכימו על הגדרות אלה בין המפעלים לפני שאתם בונים לוח מחוונים. אחרת המפעלים ישוו מספרים שאינם ניתנים להשוואה.

### ארכיטקטורה ל-KPI בזמן אמת

1. מצבי מכונות ומונים של חלקים זורמים דרך OPC UA אל ה-broker [4].
2. זרימת נתונים ממפה מצבים למודל סטטוס אחיד (מיפוי קודים ספציפיים למכונה) [3].
3. ה-Eventhouse מחשב KPI מתגלגלים לפי תחנה, קו ומשמרת באמצעות KQL.
4. לוח מחוונים בזמן אמת משרת את קומת הייצור; Power BI משרת דוחות ניהוליים [17].
5. Activator מפעיל התראות כאשר ערכים יורדים מתחת לסף [17].

### זרם הערך כמודל נתונים חי

מיפוי זרם ערך הוא באופן מסורתי תרגיל על נייר. אם מחברים את תיבות התהליך של זרם ערך לנתונים חיים, מתקבל מודל נתונים פשוט אך יעיל: זמן אספקה, מלאי בין תהליכים, זמני מחזור וצווארי בקבוק הופכים למדידים. הפרק [Value Stream Mapping as a Live Data Model](https://www.m365.fm/show/episodes/value-stream-mapping-live-data-model/) מראה כיצד זה עובד בפועל. לתזמון מפורט על בסיס נתונים אלה נכנסות לתמונה מערכות [תכנון ותזמון מתקדמים](https://www.m365.fm/entity/advanced-planning-and-scheduling/); ראו את המדריך שלנו ל-[תזמון ייצור ו-APS](https://www.m365.fm/en/learn/production-scheduling-aps/). כיצד מספרים אלה משמשים בישיבות הדרג היומיות הוא נושא המדריך שלנו ל-[ניהול קומת הייצור](https://www.m365.fm/en/learn/shop-floor-management/).

### קטלוג KPI התחלתי

| KPI | מקור נתונים | רמת פירוט |
|---|---|---|
| OEE והגורמים שלו | מצב מכונה, מונים, ממצאי איכות | תחנה, משמרת |
| זמן אספקה | אירועי הזמנה (התחלה/סיום לכל פעולה) | הזמנה, מוצר |
| עבודה בתהליך | רישומי מלאי, סריקות | מאגר, קו |
| אספקה בזמן | ERP (תאריך מבוקש לעומת תאריך בפועל) | לקוח, קבוצת מוצרים |
| MTBF / MTTR | השבתות, הזמנות תחזוקה | נכס |
| אנרגיה לחלק טוב | מוני אנרגיה, ספירת חלקים | קו, מוצר |
| תשואה מעבר ראשון (First pass yield) | תוצאות בדיקה | פעולה |

## אינטגרציה של ERP ו-MES

נתוני שטח ייצור ללא הקשר של הזמנות וחומרים הם מדידות, לא מידע. האינטגרציה עם ERP ו-MES קובעת את הערך של הפלטפורמה כולה.

### איזו מערכת היא מערכת הרישום?

| אובייקט נתונים | מערכת הרישום (בדרך כלל) | תפקיד פלטפורמת Azure |
|---|---|---|
| חומר, BOM, מסלול ייצור | ERP / PLM | עותק להעשרה, ללא תחזוקה |
| הזמנת ייצור (תכנון) | ERP / APS | עותק; משוב סטטוס כאירוע |
| ביצוע פעולה, אישור | MES | אירועים ב-UNS, היסטוריה ב-Fabric |
| מצבי מכונות, ערכי תהליך | בקר / Edge | מקור הנתונים הראשי |
| הזמנות תחזוקה | תחזוקת ERP / CMMS | מופעלות על ידי תחזיות; היסטוריה לתוויות |
| ממצאי איכות | QMS / MES | מקושרים לנתוני התהליך |

### אינטגרציה עם SAP

יש כמה דרכים להעביר נתוני SAP ל-Fabric: מחברי Data Factory, פתרונות open mirroring של שותפים, ו-"SAP Business Data Cloud Connect for Microsoft Fabric", שנועד להפוך מוצרי נתונים של SAP זמינים ב-OneLake ללא העתקה; הזמינות הכללית של האחרון הוכרזה לרבעון השלישי של 2026 [44]. לא הצלחנו לאשר זמינות כללית בפועל במועד כתיבת שורות אלה [unverified: הסטטוס הנוכחי לא אומת מול מקור רשמי]; בדקו את הסטטוס העדכני ואת דרישות הרישוי בצד SAP לפני התכנון. לשילוב שטח ייצור עם SAP Digital Manufacturing פרסמה DSAG (קבוצת המשתמשים הדוברת גרמנית של SAP) במרץ 2026 את המדריך "SAP DM Shopfloor Integration"; דף הסיכום זמין באנגלית. לפי המבוא שלו, הוא מכסה ארכיטקטורה, מבני נתונים ומודלים, שינוי קנה מידה, תבניות, מודל תפעול ורכש; הטקסט המלא שמור לחברי DSAG [48]. כלל יסוד: אישורים נכנסים ל-SAP דרך ה-MES או ממשקי API מוגדרים, לא ישירות מפלטפורמת הנתונים.

### Dynamics 365

אם אתם משתמשים ב-Dynamics 365 Supply Chain Management, אתם מרוויחים מקרבתו לאקוסיסטם של Microsoft: עם "Link to Microsoft Fabric", ניתן להפוך נתוני Dataverse, כולל טבלות נבחרות של כספים ותפעול, זמינים ב-Fabric ללא צינור ETL משלכם [45]. Microsoft מתארת את ההצעה שלה לייצור כשילוב של יכולות Dynamics 365, Microsoft 365 ו-Azure [1].

### היסטוריאנים ו-SCADA קיימים

במפעלים רבים כבר פועל היסטוריאן תהליכים לצד ה-SCADA. יש להתייחס אליו כאל מקור, לא כאל משהו שצריך לעקור: ההיסטוריאן ממשיך לשרת מפעילים ומהנדסי תהליך באתר, ופלטפורמת Azure לוקחת או את האותות הגולמיים משכבת OPC UA או נתונים מאוצרים מההיסטוריאן. החליטו לכל אות איזה מסלול הוא מערכת הרישום להיסטוריה, כדי לא לאחסן ולשלם פעמיים על אותה סדרת זמן, ובדקו מול ספק ההיסטוריאן אילו ממשקים ורישיונות חלים לפני שתתכננו את זרימת הנתונים.

### זרימת נתוני שטח הייצור ל-ERP

דפוס נפוץ:

1. ה-ERP משחרר הזמנה; האירוע "הזמנה שוחררה" מגיע ל-UNS.
2. ה-MES מתחיל פעולה; האירוע "הפעולה התחילה" כולל תחנה והזמנה.
3. נתוני המכונה מועשרים בזרימת הנתונים במספר ההזמנה הנוכחי.
4. ה-MES מאשר כמויות וזמנים; ה-ERP מקיים את הרישום.
5. Fabric מאחד את כל האירועים להיסטוריית הזמנה מלאה לניתוח ולגנאלוגיה של המוצר.

## AI ו-Copilot בייצור

בינה מלאכותית גנרטיבית הגיעה לייצור, אבל בצורה שונה ממה שצפו ב-2024. Microsoft הפסיקה ב-2025 את תצוגות המקדימות של הסוכנים הייעודיים לייצור (Factory Operations Agent, Factory Safety Agent) [2], ובמקומם היא נשענת על אבני בניין פלטפורמיות כלליות: Microsoft Foundry לסוכנים ולמודלים [20], Copilot ב-Fabric לשאלות על נתונים [17], ו-Copilot Studio ו-Microsoft 365 Copilot לתרחישי עבודה משרדיים. בכנס Ignite 2025 הופיעו כתצוגות מקדימות Fabric IQ ו-Foundry IQ, שנועדו לתת לסוכנים שכבה סמנטית ובסיס ידע בהתאמה [34]. גם כאן חשובה תמונת מחזור החיים: prompt flow, כלי נפוץ ליישומי LLM מוקדמים ב-Foundry וב-Azure Machine Learning, מפסיק לפעול ב-20 באפריל 2027; Microsoft ממליצה לעבור ל-Microsoft Agent Framework [37].

### תרחישים מציאותיים

| תרחיש | אבני בניין | תנאי מוקדם |
|---|---|---|
| שאלות בשפה טבעית על נתוני ייצור ("מדוע קו 3 היה איטי יותר אתמול?") | Copilot ב-Fabric, סוכני נתונים של Fabric, אונטולוגיה [16], [17] | מודל נתונים נקי, שמות טבלאות ועמודות מובנים, KPI מוגדרים |
| סיכום מסירות משמרת ודוחות אירועים | Microsoft 365 Copilot, Teams, Copilot Studio | תיעוד מובנה, למשל בטפסים של Power Apps או Teams |
| עוזר תחזוקה (חיפוש בחוברות הפעלה ובהיסטוריית תקלות) | Microsoft Foundry עם אחזור מידע, Copilot Studio | מסמכים דיגיטליים ועדכניים, הרשאות מתוחזקות |
| בקרת איכות חזותית | מודלים של ראייה ממוחשבת, הסקה בקצה (edge) | נתוני תמונה מתויגים (כלי תיוג של צד שלישי, מאחר ששירות תיוג הנתונים של Azure ML הופסק [38]), תאורה יציבה |
| עוזר תכנון (השוואת תרחישים) | יישום תעשייתי (APS, סימולציה) בתוספת AI | מודל תכנון תקף |

### Microsoft 365 כגשר לרצפת הייצור

לארגונים שכבר מפעילים את Microsoft 365, המנוף הקצר-טווח הגדול ביותר נמצא לעיתים קרובות לא ב-Azure, אלא בחיבור אירועי רצפת הייצור לסביבת העבודה:

- **Teams לעובדי קו:** תקשורת משמרת, משימות והתראות מ-Activator או מ-Power Automate ישירות ב-Teams [17].
- **Power BI:** דוחות KPI להנהלה ולהנהלת המפעל, המבוססים על אותם נתוני Fabric.
- **Power Apps:** תיעוד סיבות להשבתה, ממצאי איכות ומשוב תחזוקה על טאבלטים בתחנת העבודה. כך נוצרות בדיוק התוויות שתחזוקה חזויה צריכה.
- **Copilot:** סיכומים של דוחות משמרת, ניתוחי סטיות ותזכירי ישיבות של ניהול רצפת הייצור.
- **לברר רישוי מוקדם:** עובדי רצפת הייצור מקבלים בדרך כלל רישיונות Frontline (Microsoft 365 F1 או F3). לפני ההטמעה, בדקו אילו יכולות, כגון Power Apps או Copilot, הם כוללים ואילו רישיונות נוספים נדרשים; אחרת פיילוט מוצלח ייתקע בהרחבה.

### מגבלות ותשתית ממשל

- **ללא החלטות בקרה על ידי מודלי שפה.** מודלי שפה שייכים לעזרה ולא ללולאת הבקרה הסגורה של מכונה.
- **להשתמש במסגרת סיכונים.** **NIST AI Risk Management Framework (AI RMF 1.0)**, שפורסמה ב-26 בינואר 2023, היא מסגרת וולונטרית המאורגנת סביב ארבע פונקציות: Govern, Map, Measure ו-Manage [63]. זו דרך מעשית לתעד סיכוני AI בבקרת איכות או בתכנון, עבור לקוחות ומבקרים.
- **חוק ה-AI של האיחוד האירופי לפעילות באירופה:** אם אתם מפעילים מערכות AI במפעלים באירופה או מוכרים שם מוצרים עם AI, בדקו אם המערכת משמשת כרכיב בטיחות של מוצר או לניהול עובדים; עלולות לחול חובות בסיכון גבוה. "Digital Omnibus on AI" (תקנה (EU) 2026/1744, בתוקף מסוף יולי 2026) דחה את המועדים האלה: ל-2 בדצמבר 2027 עבור מערכות בסיכון גבוה עצמאיות (למשל במשאבי אנוש) ול-2 באוגוסט 2028 עבור מערכות המשובצות במוצרים. AI במכונות צפוי להיות מוסדר באמצעות מעשי האצלה במסגרת תקנת המכונות של האיחוד האירופי [46]. סיווג המערכת הספציפית שלכם דורש בדיקה משפטית.
- **כוח אדם ויחסי עבודה:** מערכות שיכולות להעריך ביצועים או התנהגות של עובדים מעוררות שאלות עבודה. במפעלים מאוגדים בארה"ב, בדקו אם הסכם ההעסקה הקיבוצי שלכם מכסה ניטור ביצועים; במפעלים בגרמניה, מערכות כאלה דורשות בדרך כלל הסכמת ועד העובדים (Betriebsrat), בעל זכויות שיתוף החלטה. יש לשתף את נציגי העובדים מוקדם בכל מקרה.
- **הרשאות:** Copilot מציג מה המשתמש מורשה לראות. שיתוף רחב מדי ב-SharePoint או ב-Fabric נחשף דרך AI.

## FinOps לניהול IT בייצור

עלויות ענן בייצור מתנהגות אחרת מעומסי IT קלאסיים: נפחי הנתונים גדלים עם כל מכונה מחוברת, העומסים רצים לאורך כל שעות היממה, וחלק מהתשתית נמצא במפעל עצמו. FinOps עוזר להפוך את העלויות האלה לצפויות ולקשור אותן לערך. הפרק [FinOps for Manufacturing IT](https://www.m365.fm/show/episodes/finops-for-manufacturing-it/) מכסה את הפרטים הספציפיים.

### מסגרת FinOps בקצרה

Microsoft מבססת את ההנחיות שלה ל-FinOps על מסגרת ה-FinOps Foundation [25]. היא כוללת שישה עקרונות (בהם "צוותים צריכים לשתף פעולה", "ערך עסקי מניע החלטות טכנולוגיות" ו"ניצול מודל העלות המשתנה של הענן") שלושה שלבי מחזור חיים (Inform, Optimize, Operate) וארבעה תחומים [25]:

| תחום | המשמעות לייצור |
|---|---|
| הבנת השימוש והעלות | הפיכת העלות לגלויה לפי מפעל, קו ומקרה שימוש (תיוג, יחידות Fabric או סביבות עבודה נפרדות) |
| כימות הערך העסקי | עלות לחלק תקין, לכל מכונה מחוברת או לכל שעת השבתה שנמנעה |
| אופטימיזציה של השימוש והעלות | צמצום נפח הנתונים בקצה, שכבות שימור ונכונות גודל של יחידות |
| ניהול פרקטיקת FinOps | אחריות, מדיניות, חיוב פנימי למפעלים |

המסגרת ממליצה להעריך את הבשלות לכל יכולת בנפרד ולא באופן גורף, ולבחון אותה כל שלושה עד שישה חודשים [25].

### עשרת מנופי העלות החשובים ביותר

1. **צבירה בקצה:** לא כל ערך ברזולוציה של שנייה אחת צריך להגיע לענן. זרימות נתונים יכולות לסנן ולצבור [3]. זהו המנוף הבודד הגדול ביותר.
2. **שליחה בעת שינוי:** כברירת מחדל, מחבר OPC UA שולח רק ערכים שהשתנו, ומוסיף מעת לעת פריימי מפתח עם כל הערכים כדי שהצרכנים יוכלו לשחזר את המצב [4]. יש גם לבדוק טווחי רגישות (deadbands) בבקר או בשרת OPC UA, כדי שרעש לא ייספר כשינוי.
3. **איחוד Eventstreams:** לפי מפעל ולא לפי מקור, עם טרנספורמציות ב-Eventhouse [31].
4. **שכבות שימור:** נתונים חמים ב-cache של ה-Eventhouse למשך ימים או שבועות, נתונים ישנים באחסון OneLake.
5. **קביעת גודל מכוון ליחידת Fabric:** ניטור הניצול באמצעות אפליקציית Capacity Metrics, הפרדת עומסי פיתוח מעומסי ייצור, והשהיית יחידות שאינן נחוצות. ההשהיה מתועדת עבור SKU מסוג F; בעת השהיה, חריגות שהצטברו מחויבות מיד, והתוכן של היחידה אינו זמין [47]. יחידה שמשרתת Eventstream או לוח מחוונים של מפעל אינה מועמדת להשהיה.
6. **בחירת SKU נכון לקצה:** החל מגרסה 2610, Azure IoT Operations מציע SKU זול יותר בשם Essentials לפריסות בנפחים גבוהים, לצד Standard. הוא מוגבל לאשכולות בצומת יחיד וללא מחבר OPC UA [3]. הוא מתאים, למשל, לאתרים שהנתונים שלהם כבר מגיעים דרך MQTT או HTTP. בדקו לכל אתר אילו תכונות אתם באמת צריכים.
7. **שימוש בהזמנות מראש ובתוכניות חיסכון** למשאבי Azure הפועלים ללא הפסקה.
8. **הקצאת עלויות:** אכיפת תגים למפעל, למרכז עלות ולמקרה שימוש (Azure Policy).
9. **הכנסת כלכלת יחידה:** דיווח על עלות הענן לכל יחידה מיוצרת או לכל מכונה מחוברת. רק כך ניתן להשוות בין מפעלים.
10. **פירוק מערכות מדור קודם:** העברת שירותים שנמצאים בתהליך הוצאה משימוש (IoT Central, IoT Edge 1.5) לפני שמבנים מקבילים מכפילים את העלויות.

### אל תשכחו את עלויות הקצה

חומרה במפעל, תפעול Kubernetes, רישיונות לשירותים מופעלים באמצעות Azure Arc והצוות שמבצע עדכונים שייכים לאותו חישוב. תיק עסקי שמתבונן רק בחשבונית של Azure מעריך בחסר באופן שיטתי את העלות הכוללת. מדריך זה נמנע בכוונה מלתת מחירים, משום שהם משתנים לעיתים קרובות; את מודלי התמחור העדכניים עבור Azure IoT Operations (Standard ו-Essentials), Azure Arc ו-Azure Local תמצאו בדפי התמחור של Azure ובמחשבון התמחור של Azure.

## בניית עסק המקרה ל-Azure בייצור

הערכות תועלת כלליות מתוך מחקרי תעשייה כמעט אינן עוזרות לקבל אישור תקציב, משום שהן אינן מכירות את נקודת המוצא שלכם. לוגיקת חישוב שאתם ממלאים במספרים שלכם חזקה יותר.

### קטגוריות תועלת

| קטגוריה | חישוב | מקור נתונים |
|---|---|---|
| הימנעות מעצירות לא מתוכננות | שעות עצירה × רווח תרומה לשעה × הפחתה צפויה | היסטוריית עצירות MES, כספים |
| OEE גבוה יותר | חלקים טובים נוספים × רווח תרומה לחלק | קו הבסיס של OEE |
| הפחתת עלויות פסולת ותיקונים | כמות פסולת × עלות ייצור × הפחתה | QMS |
| טיפול מהיר יותר בתלונות | שעות לתלונה × תעריף שעתי × הפחתה; היקף ריקול קטן יותר | היסטוריית תלונות |
| עלויות תחזוקה | מלאי חלפים, שירותי קבלנים, שעות נוספות | תחזוקה ב-ERP |
| ציות לדרישות | מאמץ שנחסך בהוכחות ידניות (ביקורות, בקשות FSMA 204, הערכות CMMC, DPP) | צוות איכות וציות |

### קטגוריות עלות

- חומרת קצה ותפעולה בכל מפעל
- צריכת Azure ו-Fabric (שוטפת)
- רישיונות (Power BI, Copilot, יישומי תעשייה, אבטחת OT במידת הצורך)
- יישום (פנימי וחיצוני)
- ניהול שינוי והדרכה
- התקנה מחדש של חיישנים למכונות ישנות

### דוגמה מעובדת עם מספרים בדיוניים

לקו יש 120 שעות של עצירה לא מתוכננת בשנה, ורווח התרומה הוא 1,600 דולר לשעה. אם ניטור מצב ותגובה מהירה יותר ימנעו 20 אחוז מהשעות האלה, זה 24 שעות × 1,600 דולר = 38,400 דולר בשנה. מולם עומדות העלויות המוקצות: חומרת קצה ותפעולה, צריכת Fabric, רישיונות ושעות פנימיות. המספרים פשוטים בכוונה. העיקר הוא שלכל הנחה יש מקור בתוך החברה שלכם (היסטוריית MES, כספים), ושאתם מודדים את ההפחתה מול קו הבסיס לאחר שלושה עד שישה חודשים.

### כלל אצבע לתעדוף

התחילו ממקרה השימוש שבו שלושה תנאים מתקיימים: קו בסיס שניתן למדידה, נתונים זמינים, ובעל תהליך שרוצה להשתמש בתוצאות. לרוב זה יהיה OEE בזמן אמת או מעקב אחר מקור (traceability) יותר מאשר תחזוקה חזויה.

## מפת דרכים: חמישה שלבים לפלטפורמת ייצור ניתנת להרחבה ב-Azure

מפת הדרכים שלהלן עוקבת אחר הדפוס הנפוץ "קודם בסיס ומקרה שימוש מוביל אחד, ואז הרחבה". משכי הזמן הם הנחיות למפעל ראשון ותלויים מאוד בנקודת המוצא שלכם, באישורי רשת ובמשאבים.

### שלב 1: בהירות (4 עד 8 שבועות)

- תיק מקרי שימוש עם הערכות תועלת; בחירת מקרה שימוש מוביל אחד או שניים
- מצב נוכחי: פארק המכונות, פרוטוקולים (האם OPC UA זמין?), רשת, מערכות קיימות
- מודל נתונים יעד (היררכיית ISA-95, מוסכמת שמות נושאים ב-UNS)
- concept אבטחה הכולל אבטחת OT, פרופיל CSF 2.0, היקף CMMC היכן שרלוונטי, פרטיות ונציגי עובדים
- בדיקת מחזור חיים של כל השירותים מול טבלת הסטטוס במדריך זה

### שלב 2: בסיס (6 עד 12 שבועות)

- תשתית קצה במפעל הפיילוט, חיבור Arc, Azure IoT Operations
- מבנה סביבת עבודה ב-Fabric, תכנון קיבולת, מודל גישה
- המכונות הראשונות מחוברות דרך OPC UA, נכסים ב-Azure Device Registry
- יסודות FinOps: תגיות, תקציבים, דוחות עלות לכל מפעל

### שלב 3: ערך ראשון (8 עד 12 שבועות)

- מקרה שימוש מוביל בייצור, למשל OEE בזמן אמת עם תיעוד סיבות עצירה ב-Power App
- לוח מחוונים לרצפת הייצור ודוח הנהלה
- מדידת קו בסיס והשפעה ראשונה

### שלב 4: העמקה (3 עד 6 חודשים)

- שילוב הקשר מ-ERP ו-MES, היסטוריית הזמנות וגנאלוגיה
- ניטור מצב, איסוף תוויות לתחזוקה חזויה
- תרחישי Copilot ראשונים על נתונים מאוצרים

### שלב 5: הרחבה (מחודש 9 עד 15, בהתאם להתקדמות)

- פריסה לקווים ומפעלים נוספים עם תשתית כקוד ו-GitOps
- KPI חוצי מפעלים עם הגדרות אחידות
- תחזוקה חזויה לנכסים נבחרים, תרחישי תאומים דיגיטליים
- מודל תפעולי: צוות פלטפורמה, בעלי מוצרי נתונים לכל תחום, ניהול שחרורים לגרסאות Azure IoT Operations שמתפרסמות בדרך כלל מדי חודש [7]

השינוי המרכזי הוא מהוכחת היתכנות למוצר ברמה מינימלית בת קיימא (MVP): PoC מוכיח שהטכנולוגיה עובדת. MVP מוכיח שאנשים עובדים טוב יותר איתה. אם תרצו לעגן את המעבר הזה בתוכנית שיפור רחבה יותר, עיינו במדריכים שלנו ל[ייצור רזה](https://www.m365.fm/en/learn/lean-manufacturing/) ול[מצוינות תפעולית](https://www.m365.fm/en/learn/operational-excellence/).

## טעויות נפוצות בפרויקטים תעשייתיים ב-Azure

1. **טכנולוגיה לפני השאלה:** בניית פלטפורמה בלי יחידה עסקית שרוצה לפתור בעיה מסוימת.
2. **גרסת תצוגה מקדימה כבסיס:** הצבת לוגיקה עסקית על שירותים בגרסת תצוגה מקדימה. הפסקת התמיכה ב-Manufacturing data solutions ובסוכני המפעל ממחישה את הסיכון [2].
3. **אבני בניין מיושנות ממדריכים ישנים:** תכנון פרויקטים חדשים על בסיס IoT Central, Time Series Insights או IoT Edge 1.5 כי מאמר מ-2021 ממליץ עליהם [8], [10], [12].
4. **SKU שגוי:** תכנון Azure IoT Operations Essentials למפעל עם מכונות OPC UA, אף שה-SKU אינו כולל את מחבר OPC UA [3].
5. **אין מודל מצבים:** קליטת קודי מצב ספציפיים למכונה ללא סינון. השוואה בין מפעלים הופכת לבלתי אפשרית.
6. **הכול לענן:** שליחת נתונים גולמיים ברזולוציה מלאה והפתעה מחשבון החיוב.
7. **אבטחת OT כמחשבה שנייה:** הצבת אשכול קצה ברשת בלי מושג אזורים, והשארת הגישה לכתיבה אל בקרים פתוחה.
8. **שכחה של תוויות:** התחלת תחזוקה חזויה בלי היסטוריית תקלות מובנית.
9. **מדדי KPI בלי הגדרות:** בניית לוחות בקרה של OEE לפני שהמפעלים הסכימו על הגדרות הזמינות.
10. **זלזול בתפעול:** עדכונים שוטפים, עדכוני Kubernetes, החלפת אישורים ובאפר של ברוקר שניתן להגדיר רק בפריסה הראשונית [40], כשאף אחד אינו אחראי לכך.
11. **השארת אנשים מאחור:** עובדי רצפת הייצור לומדים על הפרויקט כשהטאבלט מותקן בעמדת העבודה שלהם.
12. **התעלמות מהיקף הציות:** דחיפת שרטוטים או מפרטים לחלקי ביטחון לסביבת עבודה משותפת ב-Fabric ללא החלטת תחימה לפי CMMC.

Polaris VSM מופיע כהצעת SaaS ב-Microsoft Marketplace [33]; Microsoft הציגה את iFAKT כחלק מתוכנית "ISV Success for Business Applications" שלה [32]. המדריך שלנו ל-[iFAKT Polaris](https://www.m365.fm/en/learn/ifakt-polaris/) מתאר את המוצר בפירוט רב יותר.

באדריכלות של מדריך זה, יישום כזה ממוקם בשכבות 6 עד 8: הוא משתמש בנתוני תהליך והזמנות כדי למדל זרמי ערך, לסמלץ תרחישים ולבצע אופטימיזציה של תוכניות. מה משמעותה של אינטגרציה קונקרטית עם פלטפורמת הנתונים שלכם הוא עניין להבהיר מול היצרן; מאמר זה אינו טוען דבר לגביה.

ללא קשר ליצרן, ארבע שאלות עוזרות בבחירת יישומים כאלה: האם היישום קורא נתונים מפורמטים פתוחים (למשל טבלאות Delta ב-OneLake או אירועים מהברוקר), או שהוא דורש ממשקים משלו? איזו מערכת היא מערכת הרישום למידע מאסטר כמו מסלולי ייצור וקיבולות? היכן פועלים הנתונים והחישוב (אזור, טננט)? וכיצד התוצאות, כמו תוכנית מיטבית, חוזרות ל-ERP או ל-MES בצורה מבוקרת?

## שאלות נפוצות

### מהו Azure לייצור?

Azure לייצור הוא מערך שירותי הענן והקצה של Microsoft שבאמצעותם יצרנים מחברים מפעלים, מאחסנים ומנתחים נתוני ייצור ובונים מעליהם יישומי בינה מלאכותית ויישומי מקום עבודה. בשנת 2026 הליבה היא Azure IoT Operations על גבי Kubernetes עם הפעלת Arc במפעל, Microsoft Fabric כפלטפורמת הנתונים, ו-Foundry, Power BI ו-Copilot לניתוח ולבינה מלאכותית [3], [17]. Microsoft אורזת את הסיפור התעשייתי שלה כ-"Microsoft for Manufacturing", המשלב את Azure, Dynamics 365 ו-Microsoft 365 [1].

### מה ההבדל בין Azure IoT Hub ל-Azure IoT Operations?

IoT Hub הוא שירות ענן שאליו מתחברים מכשירים בודדים ישירות. Azure IoT Operations הוא מישור נתונים הפועל במפעל על גבי Kubernetes עם הפעלת Arc ומחבר מכונות באמצעות OPC UA ומחברים אחרים לברוקר MQTT מקומי [3]. למפעלים עם מכונות רבות, Azure IoT Operations הוא בדרך כלל נקודת ההתחלה הנכונה; IoT Hub מתאים להתקנים מבוזרים המחוברים ישירות. לפשרות מול IoT Edge ראו [Azure IoT Edge vs Azure IoT Operations: Choosing the Right Industrial Architecture](https://www.m365.fm/community/u/mirko-p/blog/azure-iot-edge-vs-azure-iot-operations/).

### האם Azure IoT Central מיועד לפרישה?

כן. החל מ-23 בספטמבר 2026 לא ניתן ליצור יישומי IoT Central חדשים; יישומים קיימים ימשיכו לפעול עד 20 בספטמבר 2029. Microsoft ממליצה על IoT Hub עם Device Provisioning Service, Azure Device Registry ו-Microsoft Fabric כיעד; לוחות המחוונים והאנליטיקה עוברים ל-Fabric Real-Time Intelligence [8], [64]. הודעת פרישה לתאריך 31 במרץ 2027 שהופיעה בפורטל Azure בפברואר 2024 נמשכה על ידי Microsoft באותו זמן כהודעת מערכת שגויה [9]. ההכרזה משנת 2026, לעומת זאת, היא הודעה רגילה עם תקופת מעבר של שלוש שנים.

### במה הוחלף Azure Time Series Insights?

Time Series Insights יצא משימוש ב-7 ביולי 2024. Microsoft מייעדת את ה-Eventhouse ב-Microsoft Fabric Real-Time Intelligence כיעד המעבר [10]. אם אינכם משתמשים ב-Fabric, Azure Data Explorer הוא חלופה שגם היא משתמשת ב-KQL [19].

### מה קרה ל-Microsoft Cloud for Manufacturing?

ההצעה התעשייתית נקראת כעת "Microsoft for Manufacturing" ומאגדת יכולות מ-Azure, Dynamics 365 ו-Microsoft 365 [1]. התצוגות המקדימות הספציפיות "Manufacturing data solutions" ו-"Factory Operations Agent" יצאו משימוש ב-30 במאי 2025, ו-"Factory Safety Agent" ב-23 ביוני 2025 [2]. אין הודעה נפרדת על "Manufacturing data solutions in Microsoft Fabric"; אל תתכננו אותה בפרויקטים חדשים.

### אילו שירותי Azure נדרשים למפעל חכם?

לחיבור טיפוסי של מפעל: Azure Arc ואשכול Kubernetes במפעל, Azure IoT Operations מעליהם (ברוקר, מחבר OPC UA, זרימות נתונים), Azure Device Registry לנכסים, Microsoft Fabric עם Eventstream, Eventhouse ו-Activator לנתונים בזמן אמת, ו-Power BI לדיווח [3], [17]. אבני הבניין של הבינה המלאכותית (Fabric Data Science, Azure Machine Learning, Microsoft Foundry) והתאומים הדיגיטליים באים בשלב מאוחר יותר. Entra ID, Azure Policy, Cost Management ופתרון אבטחת OT מהווים את המסגרת.

### מה ההבדל בין Azure IoT Operations Essentials ל-Standard?

Standard מציע את מלוא סט התכונות. Essentials, הזמין מגרסה 2610, הוא אפשרות בעלות נמוכה יותר לפריסות בנפח גבוה; הוא פועל רק על אשכולות צומת יחיד ואינו כולל את מחבר OPC UA [3]. למפעלים עם מכונות OPC UA, Standard הוא נקודת ההתחלה.

### האם נדרשת מיומנות Kubernetes עבור Azure IoT Operations?

כן, לפחות לצורך התפעול. Azure IoT Operations פועל על אשכולות Kubernetes עם הפעלת Arc ומוגדר בדרך של Kubernetes [3]. לתחילת העבודה, Microsoft מתעדת התקנות על Ubuntu ועל Windows עם AKS Edge Essentials [3]. יש לתכנן פיתוח מיומנויות או שותף תפעולי.

### האם הייצור ממשיך לפעול אם החיבור לאינטרנט נופל?

לפי Microsoft, Azure IoT Operations יכול לפעול במצב לא מקוון למשך 72 שעות לכל היותר, ייתכן בביצועים מופחתים, וחוזר לפעולה מלאה בעת ההתחברות מחדש [3]. כמה הודעות נשמרות במאגר זמני במהלך אותה תקופה תלוי בתצורת הברוקר, שנקבעת בפריסה הראשונית [40]. פונקציות בקרה אינן חייבות להיות תלויות בענן לעולם; הבקרה נשארת ב-PLCs ובמערכות מקומיות.

### Azure Digital Twins או digital twin builder ב-Fabric?

Azure Digital Twins הוא שירות זמין לכלל הלקוחות (generally available) עם מודלים בשפת DTDL וגישת API [14]. Digital twin builder הוא חלק מ-Fabric Real-Time Intelligence, פועל עם אונטולוגיות על נתוני OneLake ונמצא בשלב תצוגה מקדימה (preview) [15]. לתאומים דיגיטליים לייצור שמונעים על ידי מפתחים, Azure Digital Twins הוא הבחירה הבטוחה כיום; לתאומים אנליטיים בפלטפורמת Fabric, שווה לבצע פיילוט עם digital twin builder. Mirko Peters מסביר הבחנה קשורה, בין ה-device twin ב-IoT Hub לבין Azure Digital Twins, ב-[Device Twin vs Azure Digital Twins: Choosing the Right Layer for Industrial IoT](https://www.m365.fm/community/u/mirko-p/blog/device-twin-vs-azure-digital-twins/).

### אילו נתונים אני צריך לתחזוקה חזויה?

משתני מצב בקצב דגימה מתאים, חותמות זמן מסונכרנות, הקשר תפעולי (הזמנה, מוצר, מצב מכונה) ומעל הכול היסטוריית כשלים מתויגת מהתחזוקה. ללא היסטוריית כשלים, בתחילה ניתן לבצע רק זיהוי חריגות.

### מה משמעות הפסקת התמיכה ב-Defender for IoT עבור אבטחת ה-OT שלי?

ב-2 בנובמבר 2026 הודיעה Microsoft רשמית כי תפסיק לחלוטין את הרכיב של אבטחת OT ב-Defender for IoT באוקטובר 2029; עד אז יסופקו רק עדכוני אבטחה ותיקוני באגים [22]. בלוג של שותף של Microsoft מוזכר במקום זאת 31 במאי 2028 כתאריך סיום התמיכה [39]. אין תחליף מתוצרת Microsoft; Microsoft מציעה מחברים (connectors) ל-Armis, Dragos ו-Forescout, שהפתרונות שלהן מורשים בנפרד [22]. תכננו את ההחלפה כך שתושלם לפני אמצע 2028.

### האם IoT Edge עדיין שווה שימוש?

IoT Edge כמוצר עדיין נתמך. גרסה 1.5 LTS הגיעה לסוף התמיכה ב-10 בנובמבר 2026; הגרסה הנוכחית 1.6 LTS נתמכת עד 14 בנובמבר 2028 [12]. עבור צי מכשירי Linux קיים, העדכון לגרסה 1.6 הוא הדרך הישירה. עבור מכשירי Windows עם EFLOW 1.5, דף הגרסאות אינו מציין EFLOW 1.6 LTS; יש להבהיר שם את מסלול היעד. עבור מישורי נתונים חדשים במפעל, יש להעריך את Azure IoT Operations.

### האם Azure עומד בדרישות CMMC?

אין הסמכת CMMC ל-Azure עצמו, מכיוון ש-CMMC חל על המערכות של הקבלן ולא על פלטפורמת ענן [55]. Microsoft מציינת ש-Azure ו-Azure Government מחזיקים שניהם באישורי FedRAMP High המכסים את NIST SP 800-171, שניתן לקבל הסמכת CMMC לפתרונות בשני העננים, ושרוב קבלני ההגנה מתאימים בצורה הטובה ביותר ל-Azure Government [55]. כלל ה-DFARS שמכניס את דרישות CMMC לחוזי DoD נפרס בשלבים מאז 10 בנובמבר 2025 [54].

### איזו מסגרת אבטחה צריך יצרן בארה"ב להשתמש בה עבור Azure ו-OT?

השתמשו בהן יחד. NIST CSF 2.0 נותן לכם את מבנה הממשל והשפה המשותפת מול ההנהלה, חברות הביטוח והלקוחות [49]; ISA/IEC 62443 נותן לכם את המודל הטכני ל-OT (אזורים, ערוצים ורמות אבטחה) [27]; NIST SP 800-82 Rev. 3 מחבר בין השניים עם הנחיות ייעודיות ל-OT ותוספות לבקרות [50]. הוסיפו CMMC אם אתם מטפלים ב-FCI או ב-CUI עבור ה-DoD [53], ו-NIS2 עבור אתרים באיחוד האירופי [41].

### כמה עולה Azure לייצור?

אין מספר כולל אמין. העלויות תלויות במספר המפעלים והמכונות, בנפח הנתונים, בתקופת השמירה, בקיבולת Fabric שנבחרה, בחומרת הקצה וברישיונות. המנוף הגדול ביותר הוא צבירת נתונים בקצה. השתמשו במחשבון התמחור של Azure והטמיעו שיטות FinOps משלב 2 ואילך [25].

### איזה תפקיד ממלא Microsoft 365 בייצור?

Microsoft 365 הוא שכבת מקום העבודה: Teams לתקשורת משמרות והתראות, Power BI ל-KPI, Power Apps לאיסוף נתונים בעמדת העבודה ו-Copilot לסיכומים ולשאלות על נתונים. עבור חברות עם סביבת Microsoft 365 מבוססת, חיבור זה הוא לעתים קרובות הדרך המהירה ביותר להפוך נתוני רצפת הייצור לשמישים.

### מאיפה להתחיל כמנהל Microsoft 365 או Azure?

מהמשימות שנמצאות בכל מקרה באחריות ה-IT המרכזי: תפקידי Entra ID לאנשי OT ולשותפים, Azure landing zone עם מדיניות תגיות לכל מפעל, אשכול בדיקה ל-Arc הכולל אישורי חומת אש דרך שרשרת ה-proxy, ומבנה של סביבת עבודה ב-Fabric. במקביל, פגשו את אחראי ה-OT כדי להבין את מודל האזורים של המפעל. הפרטים מופיעים בסעיף "מאיפה להתחיל כמנהל Microsoft 365 או Azure" בתחילת מדריך זה.

## סיכום

Azure לייצור בשנת 2026 הוא פחות עניין של בחירת שירותים ויותר עניין של משמעת. הבסיס הטכנולוגי ברור: Azure IoT Operations על Arc במפעל, Microsoft Fabric כפלטפורמת הנתונים, ו-Foundry, Power BI ו-Copilot לאנליטיקה ולסביבת העבודה. במקביל, הפסקת התמיכה ב-Time Series Insights ובתצוגות המקדימות לייצור, וכן ההוצאה המתוכננת משימוש של IoT Central ושל אבטחת OT ב-Defender for IoT, מראים שניהול מחזור החיים הוא חלק מעבודת הארכיטקטורה.

שלושה דברים עושים את ההבדל: מודל נתונים עצמאי ונטרלי לכלים, המבוסס על ISA-95; תכנון אבטחה המבוסס על ISA/IEC 62443 ו-NIST CSF 2.0, הכולל גם את CMMC או NIS2 היכן שהם חלים; ומיקוד עקבי במקרי שימוש עם בסיס מדוד. כאשר עובדים כך, בונים פלטפורמה שמשרתת תחזוקה חזויה, מעקב אחר מוצרים, תאומים דיגיטליים ו-AI מאותו בסיס נתונים, ושורדת את השינוי השמי הבא של Microsoft.
