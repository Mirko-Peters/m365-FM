NDR 5.4.14 Hop count exceeded indicates a mail loop or routing problem in Exchange Online. Microsoft Learn names two likely causes: an accepted domain configuration problem, and misconfigured connectors in a hybrid environment. Usually only an Exchange Online admin can fix it.

## What the bounce message means

Learn says the most likely cause is that the hop count was exceeded or that the route the message takes is broken. The article covers a range of codes, 5.4.6 through 5.4.20, and says to use the information in the NDR to decide how to fix the problem.

Two codes matter most:

- `554 5.4.6 Hop count exceeded - possible mail loop` is always generated by on-premises Exchange Servers. It indicates a mail loop or routing problem on-premises, which you would likely meet in a hybrid environment.
- `5.4.14 Hop count exceeded - possible mail loop ATTR34` is always generated by Exchange Online. It indicates a mail loop or routing problem in Exchange Online.

Learn describes two likely situations behind 5.4.14:

1. Based on the domain in the recipient's address, your Exchange Online organization accepted the message but then could not route it to the recipient. The likely cause is an accepted domain configuration issue.
2. In hybrid environments, there are misconfigured connectors in your Exchange Online organization.

## If you are the sender

Learn says these issues typically can only be fixed by an Exchange Online admin and not the average email sender. Send the full bounce message to your email admin and point them to the Learn article. My advice: include the code, the text and the original recipient address.

## If you are the admin: check the accepted domain

Learn lists accepted domain issues first. Verify that the recipient's domain is configured as an authoritative accepted domain in Exchange Online.

The accepted domains page describes the two types:

- **Authoritative:** email is delivered to addresses listed for recipients in Microsoft 365 for this domain, and mail for unknown recipients is rejected. This option enables Directory-Based Edge Blocking.
- **Internal relay (also known as non-authoritative):** recipients can be in Microsoft 365 or on your own mail servers. Mail is delivered to known recipients or relayed to your own server if the recipients are unknown to Microsoft 365. That page says you should not select this option if all recipients are in Microsoft 365, and that you must create a connector to the on-premises server if you do.

To check or change the type:

1. In the Exchange admin center, go to **Mail flow** > **Accepted domains**.
2. Select the domain. Under **This accepted domain is**, read the selected type.
3. To change it, select the other type and select **Save**. Learn says the **Save** button is shown only to admins with the required permissions.

In Exchange Online PowerShell, `Get-AcceptedDomain -Identity <Name> | Format-List` shows a domain's details and `Set-AcceptedDomain -Identity <Name> -DomainType <Authoritative | InternalRelay>` changes the type. Before you switch a domain to authoritative, make sure every recipient exists in Microsoft 365, because unknown recipients are then rejected.

## Hybrid case 1: all incoming mail goes through Exchange Online

The error can happen when the MX record for your hybrid domain points to Exchange Online and the connector that routes mail from Exchange Online to your on-premises Exchange organization uses DNS routing instead of smart host routing.

The fix is a dedicated connector for hybrid that uses smart host routing, with your on-premises hybrid server as the smart host. The easiest way is to rerun the Hybrid Configuration Wizard in your on-premises Exchange organization. To verify the connector manually:

1. Open the Microsoft 365 admin center, select **Admin centers** > **Exchange**.
2. In the Exchange admin center, select **Mail Flow** > **Connectors**.
3. Open the connector used for hybrid.
4. Under **Routing**, select **Edit routing**.
5. Make sure the correct IP address or FQDN of the smart host in your on-premises organization is specified.

## Hybrid case 2: all outgoing mail goes through on-premises

This behavior depends on the `RouteAllMessagesViaOnPremises` parameter of the hybrid connector. When it is `$true`, all outgoing mail from Exchange Online goes through your on-premises hybrid server. Check it in Exchange Online PowerShell:

```powershell
Get-OutboundConnector -Identity "<Connector Name>" | Format-List Name,RouteAllMessagesViaOnPremises
```

In this configuration, Learn says the error comes from one of two problems on the connector from your on-premises organization to Exchange Online:

- There is no connector from Office 365 to your organization's email server with the **Connector Type** value **On-premises**.
- That connector is scoped to one or more accepted domains.

The fix is a dedicated connector, from Office 365 to your organization's email server, with the **Connector Type** value **On-premises** and no accepted domains in its scope. Again, rerunning the Hybrid Configuration Wizard is the easiest route. Manually, open **Mail Flow** > **Connectors** in the Exchange admin center, select the connector and then **Edit**. Under **General** verify that **On-premises** is selected, and under **Scope** verify that **Accepted domains** is empty.

## Quick decision table

| Observation | Where to look | Documented fix |
| --- | --- | --- |
| Domain not authoritative, but all mailboxes are in Exchange Online | Accepted domains | Set the domain to authoritative |
| MX points to Exchange Online, hybrid connector uses DNS routing | Connector routing | Smart host routing to the hybrid server |
| RouteAllMessagesViaOnPremises is true | Inbound connector to Exchange Online | On-premises type, no accepted domain scope |
| Code is 5.4.6 | On-premises Exchange | Check on-premises routing and hybrid setup |

The first and last rows are my reading of the accepted domains guidance and of the code description, not a documented fix in the NDR article. The other rows follow the NDR article.

## A short order of work (my advice)

This order is my suggestion, not a Microsoft procedure:

1. Read the code. 5.4.14 points to Exchange Online, 5.4.6 to on-premises.
2. Check the accepted domain type of the recipient domain.
3. If the organization is hybrid, check where the MX record points and read the connector settings above.
4. Consider rerunning the Hybrid Configuration Wizard, as Learn calls it the easiest fix.
