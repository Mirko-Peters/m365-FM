The three ways data gets into a model. There are three main ways to feed a semantic model, and they trade freshness against speed in different ways. The first is import, which copies the data into the model's memory. When it refreshes, queries fly after that because everything is already loaded in memory. The catch is that the data is only as current as the last refresh. If your refresh runs at six in the morning, your numbers are a snapshot of six in the morning. The second is direct query, which does the opposite. It leaves the data where it lives and queries the source. Every time someone opens a report. You always see the latest numbers, but the source database usually wasn't built to answer thousands of report queries. Everything slows down when traffic picks up. The third one is the interesting one, and it only exists in fabric. It's called direct lake. Instead of copying data or querying a database, it reads the delta parquet files in one lake directly. There's no copy step, no overnight refresh, and no separate database sitting between them. You get the speed of import with the freshness of direct query, which is the combination that used to be impossible. Choosing between them comes down to a few practical things. Import is the safe default for small and medium models because it's fast, flexible, and works on any license. Direct query makes sense when the data has to be live to the second, or when it lives outside fabric in something like an Azure SQL database or snowflake Direct Lake is built for the opposite end of the scale, where the tables are huge and the data is already sitting in one lake at that size. Copying all of it would be slow, expensive, or simply impossible. You can also mix them in. A single model, can hold a giant fact table in Direct Lake and a small lookup table in import.
